# INRP2P — UX-01: Interface Blueprint

**Version:** 1.1 (safety-corrected)
**Status:** Implementation blueprint for the frontend built in this pass.
**Authority:** Subordinate to TS-01.4 and, once approved, to the TS-03 server contract. Where this document describes what a customer sees about money, escrow or deal state, TS-01.4 governs the underlying truth and TS-03 governs the values delivered to the client. UX-01 may never soften a TS-01.4 guarantee into a stronger-sounding promise, and may never let the client become the source of a fact it is only supposed to display.

**Change log 1.0 → 1.1.** No change to product direction, layout, copy voice, design language or route map. Three safety boundaries were added as §2 (scenario isolation, presentation versus authority, preserved pre-auth intent). §6 was corrected because its previous wording implied scenario URLs were universally reachable.

---

## 1. Product frame

INRP2P is a **settlement rail reached through links**, not a marketplace. There is no order book, no browse, no discovery surface, and no counterparty the customer did not choose or was not sent to.

**The customer mental model, and the spine of every screen:**

```
FROM  →  AMOUNT  →  TO  →  FINAL RESULT  →  MOVE
```

Every primary surface is a restatement of that line. The landing page is the calculator. The create-deal flow is the calculator with a lock. The deal link preview is the calculator someone else already filled in. Nothing else competes for the primary action.

## 2. Frontend safety boundaries

This section is normative and binding on implementation. It exists because a settlement interface can cause loss without ever touching money — by displaying a state that is not true, by implying an authorization it does not have, or by carrying stale economics across an authentication hop.

### 2.1 Scenario isolation

Synthetic scenarios exist so that every UI state is reachable during design review, development, automated tests and Storybook without a backend. They are a **build-time capability, not a runtime feature flag.**

**Permitted only in:** mock, development, automated-test and Storybook environments.

**Hard-disabled in production.** Both entry points — the `?scenario=` query parameter and the synthetic `publicId` suffix (`INRP-7Q4M-conflict`) — resolve to the neutral default in any production build. The gate is evaluated at module load from `NODE_ENV`, and production is denied *regardless of the opt-in flag*, so a mis-set environment variable on a production deploy cannot re-enable spoofing. The default is closed: development also requires an explicit opt-in.

A scenario must never override:

- a real deal;
- real SSR output;
- Open Graph metadata;
- authorization;
- available actions;
- deal state;
- funds-location presentation.

**A production URL must never be able to fake `completed`, `refunded`, `disputed`, `verification required`, or any other state.** No sequence of query parameters, path segments, crafted public identifiers, headers or cookies may cause a production build to render a deal state that the server did not assert.

**Implementation.** `src/lib/env.ts` exposes `SCENARIOS_ENABLED`; every scenario entry point in `src/mocks/scenarios.ts` returns `DEFAULT_SCENARIO` when it is false. `DEFAULT_SCENARIO` is deliberately the neutral path and grants no elevated state, no bypassed verification and no completed settlement. When the TS-03 client replaces the mock adapter, scenario resolution is removed from the request path entirely rather than merely disabled.

**Verification.** `tests/node-harness/scenarioIsolation.check.ts` executes each environment in a fresh child process — because the gate is read at module load — and asserts that production returns the neutral default for every crafted identifier and every query value, including when the opt-in flag is forced to `true`. This test is a release gate, not documentation.

### 2.2 Presentation versus authority

`dealPresentation.ts` may centralize wording and visual presentation. **It must not become a client-side state machine.**

The TS-03 server contract is authoritative for:

- canonical deal state;
- actor obligations;
- allowed actions;
- cancellation and dispute availability;
- funds location;
- deadlines;
- authorization.

The frontend maps those canonical fields to copy and components. It may **never**:

- authorize an action;
- infer that funds moved from a client-side enum;
- treat a disabled button as a concurrency control or a permission check;
- treat an elapsed client timer as an expiry decision;
- treat a cached response as current truth.

Consequences that follow directly:

- **A disabled control is a courtesy, not a guard.** Every action is re-authorized and re-guarded server-side inside the corresponding TS-01.4 transaction boundary. The client re-enabling a button must change nothing except the error the customer sees.
- **Timers are cosmetic.** Expiry is decided against a post-lock database clock (T1–T4). The countdown reaching zero renders a *prompt to re-check*, never a state transition.
- **Losing a race is a normal outcome, not an error.** `TB-LINK-JOIN` has exactly one winner. The UI is built so the losing branch is a designed screen with a next step, not an exception surface.
- **Funds location is quoted, not computed.** The client never derives where money sits from a state name it holds locally; it renders the server's statement of custody.
- **`canCancel` / `canDispute` are display mirrors.** They exist to avoid offering an action that will certainly fail. They are not the decision. The server decides, and the server may refuse an action the client believed was available.

When client and server disagree, the server wins and the client resynchronizes. The interface must be able to say "this changed while you were looking at it" without treating that as a fault.

### 2.3 Preserved pre-auth intent

Authentication may preserve the customer's **direction, amount and destination intent** across `/login` and `/register`, so that an interrupted flow resumes without re-typing.

It must **never**:

- preserve an indicative rate as a binding quote;
- accept client-carried economics as authoritative;
- treat a pre-auth quote identifier as still firm after the hop.

**After authentication, the server must issue or validate a fresh firm quote before MOVE.** Any rate carried through the auth boundary is re-derived and re-priced; a rate that was indicative before login is still indicative after it. The customer is shown the new figure and must see it before the irreversible step. A quote that expired during authentication is replaced, never silently honoured.

**Public Open Graph metadata must exclude:**

- identities (names, handles, contact details of either party);
- bank instructions (account numbers, IFSC, UPI handles, beneficiary names);
- wallet addresses;
- payment proof (UTR, references, uploaded receipts);
- private deal evidence (dispute material, case notes, operator annotations).

A Deal Link unfurls in group chats, where the audience is unknown and the preview is fetched by third-party crawlers with no session. The unfurl may state only the public shape of the offer — direction, amount, and that a link exists. Bank instructions in particular are additionally bound by I7 and are released only at or after `ESCROW_LOCKED`, to an authenticated participant, and never to a metadata crawler.

## 3. Non-negotiable honesty rules

These are product requirements, not copy preferences. Each maps to a TS-01.4 rule.

| Rule | Why |
|---|---|
| Never say "your funds are secure/protected/guaranteed." Say **what is held, by whom, and what can move it.** | Escrow constrains movement; it does not guarantee an outcome (TS-01.4 I-13 escrow enforcement, not outcome). |
| Never present the indicative rate as binding. | Only a firm quote fixes economics (M12). Pre-quote rates move, including across authentication (§2.3). |
| Never imply a countdown performed anything. | Expiry is decided server-side against a post-lock database clock (T1–T4). The visible timer is cosmetic (§2.2). |
| Never claim Join is race-safe because a button is disabled. | Single-winner Join is a server transaction (TB-LINK-JOIN). The UI states "first-come" and handles losing gracefully. |
| Never show a fee line to retail. | The settlement fee is charged to the desk. Retail sees only exact **You send** and **You receive** (§8.6). |
| Never render bank details before the crypto leg is locked. | I7 — instructions are released only at/after `ESCROW_LOCKED`, and never in OG metadata (§2.3). |
| Never invent volume, success rates, testimonials, compliance claims or partner logos. | There is no data to support them and no registration to claim. |
| State plainly that a preview build holds no money. | `MockNotice` is a required chrome element until a money-authoritative backend exists. |

## 4. Route map

| Route | Auth | Purpose |
|---|---|---|
| `/` | public | Exchange-first landing. Calculator is the hero; the kinetic wheel sits behind it. |
| `/d/[publicId]` | public | Deal link preview with server-rendered OG unfurl metadata for chat apps, restricted per §2.3. |
| `/login`, `/register` | public | Auth that **preserves and restates** the intent carried in the query string, under §2.3. |
| `/app` | gated | Active deals, ordered by what needs the customer. |
| `/app/new` | gated | Review → lock rate → MOVE, or mint a shareable funded link. |
| `/app/deal/[dealId]` | gated | Deal room: status, funds location, single primary action, timeline. |
| `/app/history` | gated | Settled deals with their recorded rate and reference. |
| `/app/notifications` | gated | Alerts, action-tagged. |
| `/app/settings` | gated | Identity, verification ladder, security. |
| `/app/ops` | operator | Queue of deals that cannot progress without a person. |

Gating shown here is **navigational**. It is not the authorization boundary; §2.2 applies.

## 5. The deal room contract

Every state answers six questions in a fixed order, sourced from one module (`dealPresentation.ts`) so no component re-derives them:

1. **What is happening** — one-line headline.
2. **What must I do** — or explicitly nothing.
3. **What must they do** — or explicitly nothing.
4. **Where are the funds** — literal, never reassuring.
5. **What happens next** — including "if nobody acts."
6. **What if it goes wrong** — cancel and dispute paths, with their real consequences.

**Exactly one primary action** is offered per state. Cancel and dispute are secondary and disappear when TS-01.4 forbids them (cancellation is impossible once any payment is claimed).

Per §2.2 this module answers *how it is said*, never *what is permitted*.

## 6. State coverage matrix

Every state below is reachable for review in **development, test and Storybook** via `?scenario=` or a `publicId` suffix, so any of them can be inspected or screenshotted without a backend. Per §2.1 these routes resolve to the neutral default in production and cannot be used to review, demonstrate or fake a state against a live deployment.

| Surface | States implemented |
|---|---|
| Calculator | empty · typing · invalid precision · rate loading · rate unavailable · ready |
| Deal link | loading · open · **consumed (lost race)** · expired · closed/withdrawn · capacity exhausted · verification required · offline · not found |
| Deal room | preparing · awaiting payment · pay now · awaiting confirmation · confirm receipt · window lapsed · under review · disputed · on hold · completed · refunded · cancelled |
| Lists | loading · empty · error · offline · populated |
| Operator | loading · empty · **permission denied** · populated · SLA breached |
| Global | 404 · runtime error · route loading |

## 7. Design direction

**Premium restraint, not crypto theatre.**

- **Ground:** warm stone neutrals (`#FAFAF9` / `#0C0A09`), not blue-grey. Indian fintech reads warm.
- **Brand:** a single orange (`#EA580C`) reserved almost entirely for the primary action and the active nav indicator. Orange is an accent, never a background wash.
- **Type:** system stack for speed and native feel. **Tabular numerals everywhere money appears** — figures must not jitter between renders.
- **Space:** 4px base, generous vertical rhythm, one idea per card.
- **Elevation:** low and soft. No glassmorphism, no glow, no noisy gradients.
- **Motion:** the kinetic wheel is the only sanctioned decorative motion — one 34-second rotation, thin strokes, `aria-hidden`, disabled under `prefers-reduced-motion`. It sits *behind* the exchange form at reduced opacity and is hidden below `lg`. It must never make a settlement product look like a wheel of fortune.
- **Responsive:** designed at 360px first; the deal room and calculator are single-column throughout. Desktop at 1440px+ widens the shell to `max-w-5xl` and lifts the landing hero into two columns.

## 8. Accessibility floor

- Skip-to-content link on every page.
- Visible focus ring on all interactive elements (`:focus-visible`, brand-coloured, 2px + offset).
- Every money value carries an `aria-label` spelling out the amount and currency.
- Loading regions are `role="status"` with `aria-live="polite"`; errors are `role="alert"`.
- Countdown announces politely only in its final minute, to avoid screen-reader spam.
- Form fields own their label, hint and error via `aria-describedby` and `aria-invalid`.
- No colour-only status: every badge pairs tone with a word.

## 9. Adapter boundary

The UI imports **only** `@/types/services` and `useServices()`. It never imports `@/mocks`. Swapping in the TS-03 client is a one-line change in `ServicesProvider` and requires no component edits.

Methods marked `@ts03-atomic` in `src/types/services.ts` correspond to TS-01.4 transaction boundaries and are the exact seams where server-side atomicity, canonical lock ordering and CAS guards must be implemented. The mock implementations are display fixtures and are documented as not race-safe. Per §2.2, that documentation is a statement of fact about the mocks, not a gap to be closed on the client: race safety belongs to the server boundary and cannot be added to a fixture.
