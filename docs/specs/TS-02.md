## 3. Canonical encoding and derived identity

Several TS-01.4 obligations require *exact bytes*: `entry_key` equality, byte-identical term copy [M12, M12′], deterministic account identity and command identity. One encoding serves all of them. This is the resolution of **BA-4**.

### 3.1 The canonical encoding `CE`

`CE` maps an ordered field list to a byte string. It is not JSON and not locale-dependent.

```
CE(fields) := concat( for each field f in DECLARED order:
                        u32be(len(tag(f))) || utf8(tag(f)) ||
                        u8(type(f))        ||
                        u32be(len(body(f)))|| body(f) )
```

| Type | tag byte | `body` |
|---|---|---|
| null | `0x00` | empty |
| integer (all minor units) | `0x01` | ASCII base-10; no `+`; no leading zeros; no exponent; `-` permitted; zero is `0` |
| text | `0x02` | UTF-8, NFC-normalized, no trailing whitespace |
| uuid | `0x03` | 16 raw bytes, big-endian |
| timestamp | `0x04` | RFC 3339 UTC, exactly 6 fractional digits, literal `Z` |
| boolean | `0x05` | `0x00` false, `0x01` true |
| rational | `0x06` | `CE` of `[('num',int),('den',int)]`, `den > 0`, `gcd(num,den) = 1` |

Field order is **declared**, never sorted at runtime. Two encoders agreeing on the declared order produce identical bytes.

`H(x) := sha256(x)`, lower-case hex, 64 characters.

### 3.2 Derived identifiers

| Identifier | Definition |
|---|---|
| `account_id` | `inrp2p.uuid_v5(NS_ACCOUNT, inrp2p.ce_account_key(k))`, `NS_ACCOUNT = '6f2a1c4e-0b7d-5f8a-9c31-2e4d6a8b0f13'` — §3.3 |
| `term_digest` | `H(CE(term_fields))` — §4.7 |
| `entry_key` | stored as its own typed columns per journal [§13.1]; `entry_key_digest = H(CE(entry_key_fields))` is a stored generated column used only for indexing |
| `command_hash` | `H(CE(command_payload_fields))` — §8.2 |
| `cei_digest` | `H(CE(cei_fields))` — §5.9 |

**Why `account_id` is derived rather than serial.** This is the resolution of **BA-2**. [L2] exempts rows inserted inside a boundary from lock ordering, but rank 9 requires locking **every account the boundary posts to, ascending `account_id`**. With a serial key the order is unknowable until after materialization, forcing the read-then-write that [§1.2] forbids. With a UUIDv5 derived from the account key, the boundary computes the complete ordered lock list **before touching the table**, then materializes and locks in one pass (§7.2). Canonical rank-9 ordering is therefore always computable and always stable.

Application-side generation of `account_id` is prohibited.

### 3.3 `account_key`, its canonical bytes, and UUIDv5 over those bytes

**Correction (v2.1) — this was the most serious defect in v2.0.** §3.1 declared `CE`, a length-prefixed typed byte encoding, and §3.2 claimed `account_id = uuid_generate_v5(NS_ACCOUNT, CE(account_key_fields))`. The executable SQL did something else entirely:

```sql
-- v2.0, §5.3 and §7.2 — NOT CE, and not safe:
uuid_generate_v5(NS_ACCOUNT,
  asset::text || '|' || family || '|' || scope_kind || '|' || scope_id || '|' || shard::text)
```

Three defects, each independently disqualifying:

1. **It is ambiguous.** A delimiter that can occur inside a field does not separate fields. Worked counter-example, computed and verified:

   | | `asset` | `family` | `scope_kind` | `scope_id` | `shard` | joined string |
   |---|---|---|---|---|---|---|
   | **A** | `USDT` | `receivable` | `divergence` | `desk_9\|x` | `0` | `USDT\|receivable\|divergence\|desk_9\|x\|0` |
   | **B** | `USDT` | `receivable` | `divergence\|desk_9` | `x` | `0` | `USDT\|receivable\|divergence\|desk_9\|x\|0` |

   The strings are **identical**, so A and B receive the **same `account_id`** — two distinct ledger accounts silently merged into one. That breaks **M4** ("value occupies exactly one account at any instant") and **M5** (a receivable account's non-negativity would be computed over two parties' balances). Under `CE` the two encodings differ, because every field is length-prefixed and no byte sequence in a field body can be mistaken for structure.

2. **`uuid_generate_v5` cannot take `CE` output.** `uuid-ossp` exposes `uuid_generate_v5(namespace uuid, name text)`. `CE` produces **arbitrary bytes**, including `0x00` (every length prefix of a short field contains three zero bytes). PostgreSQL `text` cannot hold `0x00`, so `CE` bytes are not representable in that parameter at all. The stated definition was unimplementable as written.

3. **It is NULL-propagating.** `a || '|' || NULL` is `NULL`, and `uuid_generate_v5(ns, NULL)` is `NULL`, so a NULL `scope_id` yields a NULL `account_id` rather than an error.

The corrected contract is below. It computes UUIDv5 **over the exact `CE` bytes**, using `pgcrypto`'s `digest(bytea, 'sha1')` because that is the only builtin that accepts `bytea`.

```sql
CREATE EXTENSION IF NOT EXISTS pgcrypto;

-- The account key. Declared field order IS the CE order; it is never sorted.
-- Every component is NOT NULL by construction: `scope_id` uses '' (not NULL)
-- for unscoped accounts, so no NULL can enter the encoding.
CREATE TYPE inrp2p.account_key AS (
  asset      inrp2p.ledger_asset,
  -- `family` is drawn from the closed catalogue enumerated in full by the
  -- `ledger_account_asset_family` CHECK of §5.3; that CHECK is the definition.
  family     TEXT,
  -- `scope_kind` names what `scope_id` identifies: the wallet tier, the party
  -- kind, the receivable type, or 'shard' for the sharded families of §2.3.
  scope_kind TEXT,
  scope_id   TEXT,   -- '' when the family is unscoped
  shard      INTEGER -- 0 when the family is not sharded [§2.3]
);

-- CE field framing: u32be(len(tag)) || tag || u8(type) || u32be(len(body)) || body
CREATE FUNCTION inrp2p.ce_field(p_tag TEXT, p_type INTEGER, p_body BYTEA)
RETURNS BYTEA
LANGUAGE sql IMMUTABLE STRICT
SET search_path = pg_catalog, inrp2p
AS $fn$
  SELECT int4send(octet_length(convert_to(p_tag, 'UTF8')))
      || convert_to(p_tag, 'UTF8')
      || set_byte('\x00'::bytea, 0, p_type)
      || int4send(octet_length(p_body))
      || p_body;
$fn$;

-- CE over the account key, in declared order. STRICT: a NULL key yields NULL
-- rather than a silently truncated encoding, and the callers below reject it.
CREATE FUNCTION inrp2p.ce_account_key(p_key inrp2p.account_key)
RETURNS BYTEA
LANGUAGE plpgsql IMMUTABLE STRICT
SET search_path = pg_catalog, inrp2p
AS $fn$
BEGIN
  IF (p_key).asset IS NULL OR (p_key).family IS NULL
     OR (p_key).scope_kind IS NULL OR (p_key).scope_id IS NULL
     OR (p_key).shard IS NULL THEN
    RAISE EXCEPTION 'account_key has a NULL component: %', p_key
      USING ERRCODE = 'null_value_not_allowed';
  END IF;

  RETURN inrp2p.ce_field('asset',      2, convert_to((p_key).asset::text,  'UTF8'))
      || inrp2p.ce_field('family',     2, convert_to((p_key).family,       'UTF8'))
      || inrp2p.ce_field('scope_kind', 2, convert_to((p_key).scope_kind,   'UTF8'))
      || inrp2p.ce_field('scope_id',   2, convert_to((p_key).scope_id,     'UTF8'))
      -- integer body: ASCII base-10, no sign, no leading zeros [§3.1]
      || inrp2p.ce_field('shard',      1, convert_to((p_key).shard::text,  'UTF8'));
END;
$fn$;

-- RFC 4122 §4.3 name-based UUID with SHA-1. Takes BYTEA, not text, so it can
-- consume CE output directly.
CREATE FUNCTION inrp2p.uuid_v5(p_namespace UUID, p_name BYTEA)
RETURNS UUID
LANGUAGE plpgsql IMMUTABLE STRICT
SET search_path = pg_catalog, inrp2p
AS $fn$
DECLARE
  v_hash BYTEA;
  v_b    BYTEA;
BEGIN
  -- Namespace as its 16 raw bytes, big-endian, prepended to the name bytes.
  v_hash := digest(decode(replace(p_namespace::text, '-', ''), 'hex') || p_name, 'sha1');
  v_b    := substring(v_hash FROM 1 FOR 16);
  -- octet 6: version nibble := 5
  v_b    := set_byte(v_b, 6, (get_byte(v_b, 6) & 15) | 80);
  -- octet 8: variant bits := 10x
  v_b    := set_byte(v_b, 8, (get_byte(v_b, 8) & 63) | 128);
  RETURN encode(v_b, 'hex')::UUID;
END;
$fn$;

CREATE FUNCTION inrp2p.account_id_of(p_key inrp2p.account_key)
RETURNS UUID
LANGUAGE sql IMMUTABLE STRICT
SET search_path = pg_catalog, inrp2p
AS $fn$
  SELECT inrp2p.uuid_v5('6f2a1c4e-0b7d-5f8a-9c31-2e4d6a8b0f13'::uuid,
                        inrp2p.ce_account_key(p_key));
$fn$;

-- `class` is a total function of `family` (§2.1, §2.2), and the
-- `ledger_account_class_family` CHECK of §5.3 states exactly that mapping.
-- Deriving it here rather than carrying it in `account_key` keeps identity
-- independent of a value that is not free to vary: two rows with the same
-- key but different classes must be impossible, not merely constrained.
CREATE FUNCTION inrp2p.account_class_of(p_family TEXT)
RETURNS inrp2p.account_class
LANGUAGE sql IMMUTABLE STRICT
SET search_path = pg_catalog, inrp2p
AS $fn$
  SELECT CASE
    WHEN p_family LIKE 'wallet.%'     THEN 'ASSET'
    WHEN p_family LIKE 'receivable.%' THEN 'ASSET'
    WHEN p_family = 'staked'          THEN 'ASSET'
    WHEN p_family IN ('party.balance','desk.reserve','quote_reserved',
                      'escrow','fee_reserved','hold','withdrawal_payable')
                                      THEN 'LIABILITY'
    WHEN p_family IN ('fee_revenue','withdrawal_fee_revenue')
                                      THEN 'REVENUE'
    WHEN p_family IN ('platform_compensation_expense','reorg_loss_expense',
                      'divergence_loss_expense','gas_expense')
                                      THEN 'EXPENSE'
    WHEN p_family = 'platform_capital' THEN 'EQUITY'
  END::inrp2p.account_class;
$fn$;
```

`account_class_of` returns `NULL` for a family outside the closed catalogue, and `ledger_account.class` is `NOT NULL`, so an attempt to materialize an account outside §2.1/§2.2 fails at insert rather than creating an unclassified account.

**Byte rules, stated so two implementations cannot disagree.** Tags are ASCII and encoded UTF-8. Bodies are UTF-8, NFC-normalized, with no trailing whitespace [§3.1]. Lengths are unsigned 32-bit big-endian **byte** counts, not character counts. The type byte is `0x02` for text and `0x01` for integer. Field order is the declared order of `inrp2p.account_key` and is never sorted at runtime.

## 4. Money, assets, currencies and terms

v1.0 conflated three different kinds of quantity. They are separated here and never merged again.

### 4.1 The three kinds of quantity

| Kind | Members | Ledger? | Storage |
|---|---|---|---|
| **Ledger asset** | `USDT`, `TRX` | **Yes.** Every unit sits in some ledger account at all times | `posting.amount_minor`, `account_balance.balance_minor` |
| **Settlement / display currency** | `INR`, `USDT` | **No INR ledger balance exists.** INR appears only in terms | `*_terms` columns on `quote`, `funded_link`, `deal` |
| **Non-monetary capacity** | desk payout capacity (INR-denominated), desk intake capacity (INR-denominated), desk exposure (USDT-valued limit), reserve encumbrance | **No.** A limit is not value [§2.4] | `desk_allocation`, `reserve_encumbrance` |

**The platform holds no INR** [§2.4]. There is no `L.inr.*` account, no INR posting and no INR balance. INR settles bank-to-bank between the participants. A deal nonetheless carries an **exact INR amount** in its terms, because the participants owe each other an exact number of paise. TS-02 stores that exact amount without ever admitting it to the ledger.

An implementation that creates an INR ledger account is defective; `ledger_account.asset` is constrained to `('USDT','TRX')` (§5.3) so the database rejects it.

**Capacity is INR-denominated but is not INR.** `desk_allocation.payout_capacity_minor` counts paise of *permission to pay*, not paise held. It is never posted, never reconciled against a wallet, and never appears in a journal [§2.4].

### 4.2 Minor units

| Currency / asset | Decimals | Minor unit | Example |
|---|---|---|---|
| `INR` | 2 | paise | ₹1.00 → `100` |
| `USDT` (TRC-20) | 6 | micro-USDT | 1.000000 USDT → `1000000` |
| `TRX` | 6 | SUN | 1.000000 TRX → `1000000` |

**All amounts are integers in minor units.** No floating point exists anywhere in the schema, the functions, the transport encoding or the application. There is no `REAL`, `DOUBLE PRECISION` or `FLOAT` column in this specification.

### 4.3 The numeric domain

**`NUMERIC(38,0)` holds a maximum of `10^38 − 1`, not `10^38`.** Bounds are stated with that value:

**Correction (v2.1) — the v2.0 domain rejected nothing.** v2.0 declared:

```sql
-- v2.0, quoted in full — the scale check is dead code:
CREATE DOMAIN inrp2p.amount_minor AS NUMERIC(38,0)
  CONSTRAINT amount_minor_scale CHECK (scale(VALUE) = 0)
  CONSTRAINT amount_minor_range CHECK (
        VALUE > -100000000000000000000000000000000000000
    AND VALUE <  100000000000000000000000000000000000000);
```

A domain constraint is evaluated **after** the value has been coerced to the domain's base type. `NUMERIC(38,0)` is a *constrained* numeric: PostgreSQL rounds to scale 0 during that coercion, half-away-from-zero. So `1.5::inrp2p.amount_minor` first becomes `2`, and only then is `scale(2) = 0` tested — which passes. The check can never fail, and a fractional input is silently **rounded into money** rather than rejected. v2.0's claim that "`1.0` is rejected" was the opposite of the behaviour: `1.0` coerces to `1` and is accepted.

The base type must therefore be **unconstrained `NUMERIC`**, which preserves the input's scale so the check has something to see:

```sql
-- v2.1: unconstrained NUMERIC base, so no rounding precedes the check.
CREATE DOMAIN inrp2p.amount_minor AS NUMERIC
  CONSTRAINT amount_minor_finite CHECK (VALUE IS NOT NULL AND NOT (VALUE = 'NaN'::numeric))
  CONSTRAINT amount_minor_integral CHECK (scale(VALUE) <= 0)
  CONSTRAINT amount_minor_range CHECK (
        VALUE > -100000000000000000000000000000000000000
    AND VALUE <  100000000000000000000000000000000000000);

CREATE DOMAIN inrp2p.amount_minor_nonneg AS inrp2p.amount_minor
  CONSTRAINT amount_minor_nonneg_chk CHECK (VALUE >= 0);

CREATE DOMAIN inrp2p.amount_minor_pos AS inrp2p.amount_minor
  CONSTRAINT amount_minor_pos_chk CHECK (VALUE > 0);
```

**Why `scale(VALUE) <= 0` and not `= 0`.** PostgreSQL reports a *negative* scale for values normalized with trailing zeros before the point — `scale(1e3::numeric)` is `-3`, and that value is exactly `1000`, a legitimate integer. Requiring `= 0` would reject it. The predicate that actually means "has no fractional part" is `scale(VALUE) <= 0`, and the equivalent, more obviously correct form `trunc(VALUE) = VALUE` is asserted alongside it in `tests/constraints/numericDomain.spec.ts`.

**Behaviour, stated so it can be tested rather than assumed:**

| Input | v2.0 (`NUMERIC(38,0)` base) | v2.1 (`NUMERIC` base) |
|---|---|---|
| `1` | accepted as `1` | accepted as `1` |
| `1.0` | **rounded** to `1`, accepted (v2.0 claimed rejection) | **rejected** — `scale = 1` |
| `1.5` | **rounded to `2`, accepted** — silent money corruption | **rejected** |
| `-0.4` | **rounded to `0`, accepted** | **rejected** |
| `1e3` | accepted as `1000` | accepted — `scale = -3`, value integral |
| `'NaN'` | accepted; poisons every later comparison | **rejected** |
| `10^38` | rejected by range | rejected by range |
| `10^38 − 1` | accepted | accepted |

`'NaN'` matters independently: `NUMERIC` admits it, and `NaN` compares equal to `NaN` but greater than every other numeric in PostgreSQL's ordering, so a single `NaN` posting would satisfy a naive per-asset sum check while making every balance meaningless. It is rejected at the domain.

Both range bounds are `10^38` **exclusive**, so the largest representable magnitude is `10^38 − 1`, which is also the maximum of `NUMERIC(38,0)` — the range is stated against that value, not against `10^38`.

**Storage note.** Dropping the `(38,0)` type modifier removes PostgreSQL's own scale enforcement, which is the point: enforcement moves to a constraint that runs *before* any rounding can occur. The domain constraints are strictly stronger than the type modifier was, since they reject exactly the inputs `(38,0)` would have silently rounded.

**The application encoder rejects the same inputs earlier**, so a fractional value never reaches the database at all: `encodeMinor` takes `bigint` and `decodeMinor`'s `INTEGER_RE` rejects `'1.0'`, `'1e3'`, `'+1'` and `'01'` (§4.4). The domain is the second of two independent gates, not the only one.

**Signed postings.** `posting.amount_minor` is signed — debit positive, credit negative [§1.1]. Receivable and balance non-negativity is an *account-level* rule enforced in §6.5, not a column domain, because a posting may legitimately be negative while the resulting balance may not.

### 4.4 The PostgreSQL ↔ JavaScript codec

**PostgreSQL `NUMERIC` does not become a JavaScript `bigint` automatically.** `node-postgres` returns OID 1700 (`numeric`) as a **string**, and OID 20 (`int8`) as a string. Any code applying `Number()` to either has already lost exactness above 2^53. Drizzle's `numeric()` column maps to `string` in TypeScript and performs no conversion.

The following is mandatory and is the only permitted path:

```ts
// src/db/codec.ts — registered once, before any pool is constructed.
import pg from 'pg';

pg.types.setTypeParser(1700, (v) => v); // numeric  -> keep as string, never Number()
pg.types.setTypeParser(20,   (v) => v); // int8     -> keep as string

const INTEGER_RE = /^-?(0|[1-9][0-9]*)$/;
const LIMIT = 10n ** 38n;

/** Decode a NUMERIC(38,0) that MUST be an integer in minor units. */
export function decodeMinor(raw: unknown): bigint {
  if (typeof raw !== 'string') throw new TypeError(`expected string from NUMERIC, got ${typeof raw}`);
  if (!INTEGER_RE.test(raw)) throw new RangeError(`non-integer minor unit from database: ${raw}`);
  return BigInt(raw);
}

/** Encode a bigint as a NUMERIC(38,0) parameter. */
export function encodeMinor(v: bigint): string {
  if (v <= -LIMIT || v >= LIMIT) throw new RangeError('amount exceeds NUMERIC(38,0)');
  return v.toString(10);
}
```

Rules:

- `decodeMinor` rejects `'1.0'`, `'1e3'`, `'+1'` and `'01'`. The regex is the contract, not a convenience.
- Every money column is declared with a Drizzle custom type whose `fromDriver` is `decodeMinor` and `toDriver` is `encodeMinor`, so no call site ever sees a raw string.
- `JSON.stringify` throws on `bigint`. Money crossing the wire is serialized as a **decimal string in minor units**, never as a JSON number.
- The same rules apply to `int8` columns used for sequence numbers (`rseq`, `gas_seq`, `recognition_seq`).

### 4.5 Firm rate representation

A firm rate is an **exact rational**, never a decimal approximation.

```sql
CREATE DOMAIN inrp2p.rate_component AS NUMERIC(38,0)
  CONSTRAINT rate_component_pos CHECK (VALUE > 0 AND scale(VALUE) = 0);
```

Terms carry `rate_num` and `rate_den`, stored in **lowest terms** (`gcd = 1`), enforced in §6.6. `rate_display TEXT` carries the human string and is **presentation only**: never an input to any computation. A mismatch between `rate_display` and `rate_num/rate_den` is a display defect, not a money defect, and is detected by reconciliation rather than by a money guard.

**The rate is INR-paise per USDT-micro**, so both sides are already in minor units and no decimal-shift constant appears in any expression anywhere in the system.

### 4.6 Conversion, rounding direction and remainder

For principal `P` (minor units of the principal asset) and rate `num/den`:

```
exact := P * num / den            -- an exact rational
gross := floor( P * num / den )   -- direction table below
rem   := P * num - gross * den    -- 0 <= rem < den, always recorded
```

| `direction` | Quantity derived | Rounding | Who the remainder favours |
|---|---|---|---|
| `USDT_TO_INR` | INR paise the fiat side must pay | **floor** | the payer — a customer's obligation is never rounded up |
| `INR_TO_USDT` | USDT micro the crypto side receives | **floor** | escrow — value that was not funded is never credited |

**One rounding, at one place.** Rounding happens exactly once, when terms are frozen (`JQ1` for a quote; `JF1`/`JF1P` for a link). No later boundary re-derives an amount from the rate. `TB-MOVE`, `TB-LINK-JOIN` and `TB-COMPLETE` copy frozen terms; they never multiply. This is what makes [M12]/[M12′] checkable by digest rather than by recomputation.

`rem` is stored as `rounding_remainder_minor` beside `rate_den` so that `P * num = gross * den + rem` is checkable from the row alone (§6.6). **`rem` is not money**: it is a fractional residue of a rate, denominated in nothing, never posted, never owed, never swept.

**Permitted currency/direction combinations — the closed set:**

| `direction` | Crypto leg | Fiat leg | `principal_asset` | `term_currency` |
|---|---|---|---|---|
| `USDT_TO_INR` | USDT escrowed by the crypto side | INR paid bank-to-bank to the crypto side's nominee | `USDT` | `INR` |
| `INR_TO_USDT` | USDT released to the fiat side | INR paid bank-to-bank by the fiat side | `USDT` | `INR` |

No other combination exists. There is no INR→INR, no USDT→USDT and no TRX-denominated deal: TRX is an operational gas asset only [§2.2] and never appears in terms. Enforced in §6.6.

### 4.7 Term columns and byte-identical copy [M12, M12′]

The **term set** is exactly these eleven fields in this declared order. This list is the whole definition; there is no "and related fields".

| # | Column | Type | Note |
|---|---|---|---|
| 1 | `direction` | `inrp2p.deal_direction` | closed enum |
| 2 | `principal_asset` | `inrp2p.ledger_asset` | always `USDT` |
| 3 | `principal_minor` | `inrp2p.amount_minor_pos` | USDT micro |
| 4 | `term_currency` | `inrp2p.settlement_currency` | always `INR` |
| 5 | `term_minor` | `inrp2p.amount_minor_pos` | INR paise, post-rounding |
| 6 | `rate_num` | `inrp2p.rate_component` | lowest terms |
| 7 | `rate_den` | `inrp2p.rate_component` | lowest terms |
| 8 | `rounding_remainder_minor` | `inrp2p.amount_minor_nonneg` | `0 <= rem < rate_den` |
| 9 | `fee_minor` | `inrp2p.amount_minor_nonneg` | USDT micro, charged to the desk |
| 10 | `fee_payer` | `inrp2p.fee_payer` | closed enum, single member `DESK` |
| 11 | `settlement_deadline_s` | `INTEGER` | **seconds — a duration, not a timestamp** |

`settlement_deadline_s` is a duration deliberately: an absolute deadline computed before the boundary would be a pre-lock clock read, which [T1–T4] forbid. The absolute deadline is materialized **inside** the boundary as `decision_time() + settlement_deadline_s * INTERVAL '1 second'`.

**The copy mechanism.** Byte-identity is achieved by copying the eleven columns in one statement and *proving* it with a digest, not by trusting the copy.

```sql
CREATE FUNCTION inrp2p.ce_text(p_tag TEXT, p_val TEXT) RETURNS BYTEA
LANGUAGE sql IMMUTABLE STRICT SET search_path = pg_catalog AS $ce$
  SELECT int4send(octet_length(convert_to(p_tag,'UTF8')))
      || convert_to(p_tag,'UTF8')
      || '\x02'::bytea
      || int4send(octet_length(convert_to(normalize(p_val, NFC),'UTF8')))
      || convert_to(normalize(p_val, NFC),'UTF8');
$ce$;

CREATE FUNCTION inrp2p.ce_int(p_tag TEXT, p_val NUMERIC) RETURNS BYTEA
LANGUAGE sql IMMUTABLE STRICT SET search_path = pg_catalog AS $ce$
  SELECT int4send(octet_length(convert_to(p_tag,'UTF8')))
      || convert_to(p_tag,'UTF8')
      || '\x01'::bytea
      || int4send(octet_length(convert_to(
             trim(to_char(p_val,'FM99999999999999999999999999999999999999')),'UTF8')))
      || convert_to(
             trim(to_char(p_val,'FM99999999999999999999999999999999999999')),'UTF8');
$ce$;

CREATE FUNCTION inrp2p.term_digest(
  p_direction                inrp2p.deal_direction,
  p_principal_asset          inrp2p.ledger_asset,
  p_principal_minor          NUMERIC,
  p_term_currency            inrp2p.settlement_currency,
  p_term_minor               NUMERIC,
  p_rate_num                 NUMERIC,
  p_rate_den                 NUMERIC,
  p_rounding_remainder_minor NUMERIC,
  p_fee_minor                NUMERIC,
  p_fee_payer                inrp2p.fee_payer,
  p_settlement_deadline_s    INTEGER
) RETURNS TEXT
LANGUAGE sql IMMUTABLE STRICT
SET search_path = pg_catalog, inrp2p
AS $td$
  SELECT encode(sha256(
      inrp2p.ce_text('direction',                p_direction::text)
   || inrp2p.ce_text('principal_asset',          p_principal_asset::text)
   || inrp2p.ce_int ('principal_minor',          p_principal_minor)
   || inrp2p.ce_text('term_currency',            p_term_currency::text)
   || inrp2p.ce_int ('term_minor',               p_term_minor)
   || inrp2p.ce_int ('rate_num',                 p_rate_num)
   || inrp2p.ce_int ('rate_den',                 p_rate_den)
   || inrp2p.ce_int ('rounding_remainder_minor', p_rounding_remainder_minor)
   || inrp2p.ce_int ('fee_minor',                p_fee_minor)
   || inrp2p.ce_text('fee_payer',                p_fee_payer::text)
   || inrp2p.ce_int ('settlement_deadline_s',    p_settlement_deadline_s::numeric)
  ), 'hex');
$td$;
```

`FM` suppresses padding; the 38 nines cover the full domain; the domains guarantee `scale = 0`, so no decimal point can appear in the encoded body.

**`quote`, `funded_link` and `deal` each carry all eleven term columns plus a stored generated digest:**

```sql
term_digest TEXT NOT NULL GENERATED ALWAYS AS (
  inrp2p.term_digest(direction, principal_asset, principal_minor, term_currency,
                     term_minor, rate_num, rate_den, rounding_remainder_minor,
                     fee_minor, fee_payer, settlement_deadline_s)
) STORED
```

[M12] (deal terms byte-identical to the consumed quote) and [M12′] (deal terms byte-identical to the consumed link) are then enforced structurally by trigger (§6.6) comparing `term_digest`. A generated column cannot be written by any client, so no deal can carry a digest inconsistent with its own columns.

This replaces v1.0's `md5_term_set(...)`, which was undefined, used MD5, contained ellipses, and referenced a source alias inside `RETURNING` — which is not valid PostgreSQL.

## 5. Schema contract

Every table below states, without exception: every column, its PostgreSQL type, nullability, default, primary key, foreign keys, `CHECK` constraints, `UNIQUE`/partial-`UNIQUE` constraints, indexes, **mutability**, **owning boundary** and **TS-01.4 reference**.

### 5.0 Conventions

**Mutability classes.** Every table carries exactly one:

| Class | Meaning | Enforcement |
|---|---|---|
| `IMMUTABLE` | insert-only; no `UPDATE`, no `DELETE`, ever | `inrp2p.trg_immutable()` (§6.7) |
| `APPEND_VERSIONED` | insert-only, but a later row supersedes an earlier one under a version/sequence key | `IMMUTABLE` trigger + uniqueness on the version key |
| `CAS_MUTABLE` | updatable only through `CAS(row, version[, state])` with exactly one affected row [§1.2] | `inrp2p.trg_cas_only()` (§6.7) |
| `CATALOGUE` | reference data; changed only by the owner role during migration | `inrp2p.trg_owner_only()` (§6.7) |
| `OPERATIONAL` | non-money bookkeeping (outbox dispatch marks, reconciliation cursors) | role privilege only |

**Every `CAS_MUTABLE` table** carries `version BIGINT NOT NULL DEFAULT 0`, incremented on every update by `inrp2p.trg_bump_version()`, and is written only by `UPDATE <table> SET <the columns this boundary changes> WHERE <pk> = $1 AND version = $2 [AND state = $3]` asserting exactly one affected row. **No read-then-write** [§1.2].

**Timestamps.** Every timestamp is `TIMESTAMPTZ`. Timestamps written by a boundary are `inrp2p.decision_time()` (§6.1) — never `now()`, never `CURRENT_TIMESTAMP`, never `transaction_timestamp()`.

**Identifiers.** Surrogate keys are `UUID`. `account_id` is derived (§3.2); all others are `gen_random_uuid()` unless stated. Natural keys are declared as their own columns and constrained, never packed into a string.

**Enumerations are PostgreSQL `ENUM` types**, not text with a `CHECK`, so an unknown value cannot be inserted and the catalogue is closed by the type system.

### 5.1 Enumerated types (closed catalogues)

```sql
CREATE SCHEMA inrp2p;

CREATE TYPE inrp2p.ledger_asset         AS ENUM ('USDT','TRX');
CREATE TYPE inrp2p.settlement_currency  AS ENUM ('INR','USDT');
CREATE TYPE inrp2p.deal_direction       AS ENUM ('USDT_TO_INR','INR_TO_USDT');
CREATE TYPE inrp2p.fee_payer            AS ENUM ('DESK');
CREATE TYPE inrp2p.party_kind           AS ENUM ('USER','DESK','PLATFORM');
CREATE TYPE inrp2p.risk_mode            AS ENUM ('NORMAL','THIN','EMERGENCY');
CREATE TYPE inrp2p.account_class        AS ENUM ('ASSET','LIABILITY','REVENUE','EXPENSE','EQUITY');

-- [§1.7] Three solvency classes, not two. SIJ is the class of every cure
-- journal (JD-C1, JD-C1e, JD-C2a, JD-C2b): it cannot *reduce* FreeBuffer but
-- may take EXCLUSIVE to recompute and downgrade the mode. Omitting SIJ forces
-- every cure to be mis-declared, and SD-1's "MUST acquire EXCLUSIVE if any
-- journal it may post is SDJ" becomes unevaluable.
CREATE TYPE inrp2p.journal_class        AS ENUM ('SDJ','SNJ','SIJ');

CREATE TYPE inrp2p.receivable_type      AS ENUM
  ('deposit_reversal','desk_shortfall','divergence');

-- [§11.1] The three lineage dimensions are orthogonal and separately
-- versioned. Their value sets are closed and are quoted verbatim from
-- TS-01.4; none of them may carry a value TS-01.4 does not define.
--
-- Dimension 1 is driven ONLY by cure and write-off. Reinstatement explicitly
-- "does not rewrite dimension 1" [§11.1], so there is no reinstatement-derived
-- member here.
CREATE TYPE inrp2p.receivable_disposition   AS ENUM
  ('OPEN','CURED','WRITTEN_OFF');

-- Dimension 2 is driven ONLY by reinstatement. `NOT_APPLICABLE` is the fixed
-- value for `desk_shortfall` and `divergence` lineages [§5.2]; `PENDING` is
-- the opening value for `deposit_reversal`; `SETTLED_REINSTATED` is written
-- exactly once by the M24 CAS.
CREATE TYPE inrp2p.reinstatement_disposition AS ENUM
  ('PENDING','SETTLED_REINSTATED','NOT_APPLICABLE');

-- Dimension 3 is driven ONLY by JW-DL-R, so only `divergence` lineages can
-- ever leave `ACTIVE` [§11.1]. `loss_reversed` and `lineage_invalidated` are
-- *rejection codes* from the R-CUR-6 guard priority, not dispositions, and
-- MUST NOT appear in this type.
CREATE TYPE inrp2p.invalidation_disposition  AS ENUM
  ('ACTIVE','REVERSED_INVALIDATED');

-- [§9.1] Nine states. `ORPHANED` is one of the three terminals of the
-- CONFIRMING fan-out and is memo-only (M6), but it is a reachable state and
-- its absence would make the machine unrepresentable.
CREATE TYPE inrp2p.deposit_transfer_state AS ENUM
  ('OBSERVED','CONFIRMING','CREDITED','HELD','ORPHANED','REVERSED',
   'REINSTATED_CREDITED','REINSTATED_HELD','REINSTATED_CREDIT_HELD');

-- [R-CYC-2] The complete and only sweep lifecycle. There is deliberately no
-- transition out of REVERSED and no re-recognition state.
CREATE TYPE inrp2p.sweep_state         AS ENUM ('BROADCAST','RECOGNIZED','REVERSED');

-- [§9.3] `OBSERVED → FINALIZED → GAS_RECOGNIZED ⇄ GAS_REVERSED`. The gas
-- states are named for gas because JGX is independent of what the transaction
-- carried; a bare `REVERSED` would collide with the sweep/capital vocabulary
-- and hide that independence.
CREATE TYPE inrp2p.chain_op_state      AS ENUM
  ('OBSERVED','FINALIZED','GAS_RECOGNIZED','GAS_REVERSED');

-- [§8.7 R-CYC-1, Annex B.4] `OBSERVED → CONFIRMING → RECOGNIZED ⇄ REVERSED`.
-- R-CYC-1 states in terms: "Terminal 'reinstated' states do not exist for
-- these objects; re-recognition returns to RECOGNIZED with the sequence
-- incremented." A `RE_RECOGNIZED` member would make F147's dead-end mutation
-- the specified behaviour. `CONFIRMING` is required because §8.8 guards the
-- initial recognition as `CAS(capital_funding: CONFIRMING → RECOGNIZED)`.
CREATE TYPE inrp2p.capital_state       AS ENUM
  ('OBSERVED','CONFIRMING','RECOGNIZED','REVERSED');

CREATE TYPE inrp2p.quote_state         AS ENUM ('QUOTED','CONSUMED','EXPIRED');

-- [Annex B.4] `OPEN → CONSUMED | CLOSED`. Expiry is a *reason* a link closes,
-- not a fourth state: §7.2 makes Join, revocation and expiry "one CAS race on
-- `link.status`", all three resolving through JF2 xor JF3. The reason is
-- recorded in `funded_link.close_reason`, not in the state.
CREATE TYPE inrp2p.link_state          AS ENUM ('OPEN','CONSUMED','CLOSED');
CREATE TYPE inrp2p.link_close_reason   AS ENUM ('REVOKED','EXPIRED');
CREATE TYPE inrp2p.link_funding_source AS ENUM ('USER','DESK');

CREATE TYPE inrp2p.deal_state AS ENUM
  ('ESCROW_LOCKED','FIAT_PENDING','FIAT_CLAIMED','PAYMENT_WINDOW_LAPSED',
   'FIAT_REVIEW','DISPUTED','RESOLUTION_PENDING','OPERATOR_HOLD',
   'COMPLETED','REFUNDED','CANCELLED');

CREATE TYPE inrp2p.case_kind  AS ENUM ('DISPUTE','FAULT','SCREENING_HOLD','RECOVERY');
CREATE TYPE inrp2p.case_state AS ENUM ('OPEN','RESOLUTION_PENDING','RESOLVED','ABANDONED');

-- [§10.1] `QUEUED → AWAITING_INCLUSION → PAID*`, with exits `CANCELLED*`
-- (from QUEUED, JW3), `RELEASED*` (from AWAITING_INCLUSION, JW4) and
-- `DIVERGED` (FA-1 violation — frozen, not terminal by policy).
--
-- `REQUESTED`, `SIGNING` and `BROADCAST` are not request states in TS-01.4:
-- signing is an *attempt* concern, and "first signing atomically transitions
-- QUEUED → AWAITING_INCLUSION". Without `DIVERGED` the whole FA-1 path of
-- §10.6 and §12.5 is unrepresentable.
CREATE TYPE inrp2p.withdrawal_request_state AS ENUM
  ('QUEUED','AWAITING_INCLUSION','PAID','CANCELLED','RELEASED','DIVERGED');

-- [§10.1] The nine attempt states, verbatim. Every one is load-bearing:
--
--   PREPARED           immutable bytes/txid/expiration committed  (W2, W3)
--   BROADCAST          first node acceptance; rebroadcasts do NOT change it
--   INCLUDED_NONFINAL  seen in a non-final block; never recognized (R-FINAL)
--   FINAL_PAID         finalized WITH a matching transfer          (JW2)
--   FINAL_FAILED       finalized WITH failure and no transfer      (JGX only, W7)
--   EXPIRED_PNI        full PNI predicate proven                   (§10.3)
--   DIVERGED           post-finality reversal of a recognized cycle
--   DIVERGED_PAID      a prior TNP or DIVERGED attempt observed to have paid
--   FROZEN             active attempt frozen by a divergence on the same request
--
-- `FINAL_SUCCESS` is not the TS-01.4 name; the branch table and the
-- `ORDINARY_LIVE` / `DIVERGENT_SOURCE` / `ALREADY_RECOGNIZED` sets of §10.6
-- are stated over `FINAL_PAID`. `CREATED` and `ACKED` do not exist: §10.1
-- makes acknowledgement the `PREPARED → BROADCAST` edge, not a state.
--
-- `REPLACED` is prohibited outright by M21: "Supersession is an attribute, not
-- a state." Replacement writes `superseded_by_attempt_id` and `superseded_at`
-- while LEAVING the prior state as `EXPIRED_PNI` or `FINAL_FAILED`, precisely
-- so that TNP stays machine-checkable after any number of replacements. A
-- `REPLACED` state is the F105 mutation ("supersession overwriting the TNP
-- state"), which MUST fail the suite.
CREATE TYPE inrp2p.withdrawal_attempt_state AS ENUM
  ('PREPARED','BROADCAST','INCLUDED_NONFINAL','FINAL_PAID','FINAL_FAILED',
   'EXPIRED_PNI','DIVERGED','DIVERGED_PAID','FROZEN');

-- [§10.4] Attempt-level recognition lifecycle, carried beside
-- `current_recognition_seq`.
CREATE TYPE inrp2p.recognition_state AS ENUM ('NONE','RECOGNIZED','REVERSED');

-- [§10.5] `recognition_kind` of a withdrawal recognition cycle. These exact
-- three tokens are named by TS-01.4 and are load-bearing for JW-R1's
-- `reversal_kind_mismatch` guard (R-DSP-3) and for `payable_discharged`.
CREATE TYPE inrp2p.recognition_kind AS ENUM ('JW2','JWDP','JWDL');

CREATE TYPE inrp2p.allocation_kind  AS ENUM ('payout','intake','exposure');
CREATE TYPE inrp2p.allocation_scope AS ENUM ('QUOTE','LINK','DEAL');

-- [C2] "Each allocation record is released exactly once — by quote expiry,
-- link close, or terminal deal outcome — via
-- `CAS(record: ACTIVE→RELEASED, version)`." Re-key (C3) transfers ownership
-- inside one boundary and is explicitly "no release", so it produces no third
-- state; a `CONSUMED` member would create an unowned interval C3 forbids.
CREATE TYPE inrp2p.allocation_state AS ENUM ('ACTIVE','RELEASED');

-- [§7.6, Annex B.4] `OPEN → SETTLED`, exactly once, recording
-- `consumed = U` and `released = E_effective − U`. There is no
-- `DISCHARGED`/`RELEASED` split: C8 is a *presence-and-state* predicate, and a
-- resolved case must retain no OPEN row of any value, including zero.
CREATE TYPE inrp2p.encumbrance_state AS ENUM ('OPEN','SETTLED');

-- [§7.6] The ruling's immutable `remainder_path`, which governs `Q` only and
-- has no discretion over `U`.
CREATE TYPE inrp2p.remainder_path AS ENUM ('PLATFORM','DESK');

CREATE TYPE inrp2p.boundary_code AS ENUM (
  'TB-DEPOSIT-CREDIT-PLAIN','TB-DEPOSIT-CREDIT-CURE-DIVERGENCE',
  'TB-DEPOSIT-CREDIT-CURE-REVERSAL','TB-QUOTE-ISSUE','TB-MOVE','TB-QUOTE-EXPIRE',
  'TB-LINK-CREATE','TB-LINK-JOIN','TB-LINK-CLOSE','TB-CLAIM',
  'TB-LATE-CLAIM-OR-EVIDENCE-INSERT','TB-DISPUTE-OPEN','TB-FAULT-CASE-OPEN',
  'TB-PROPOSE','TB-APPROVE-A','TB-APPROVE-B','TB-APPROVE-C',
  'TB-COMPLETE','TB-CANCEL','TB-HOLD','TB-HOLD-RESOLVE-JH2','TB-HOLD-RESOLVE-JD3',
  'TB-SUSPEND','TB-RISK-MODE-SET',
  'TB-WITHDRAW-REQUEST','TB-WITHDRAW-SIGN','TB-WITHDRAW-ACK',
  'TB-WITHDRAW-FINALIZED-SUCCESS','TB-WITHDRAW-FAIL-PROVE','TB-WITHDRAW-EXPIRE-PROVE',
  'TB-WITHDRAW-REPLACE','TB-WITHDRAW-RELEASE','TB-WITHDRAW-CANCEL',
  'TB-SWEEP-CONFIRM','TB-GAS-RECOGNIZE','TB-CAPITAL-RECOGNIZE',

  'TB-DIVERGENCE-LOSS-REVERSE','TB-RESERVE','TB-GAS');
```

**`boundary_code` has exactly 47 members — one per §13.2 boundary/branch, and the enum is the boundary catalogue.**

**Correction (v2.1).** v2.0 declared 48 members while asserting 47. It split the single §13.2 row `TB-LATE-CLAIM / TB-EVIDENCE-INSERT` into two enum members and then claimed the total was 47 anyway. That is not a naming preference — it is a miscount that silently defeats every cardinality check built on this type, and it makes the enum disagree with the authority it is supposed to mirror.

The split is now removed. The member is `TB-LATE-CLAIM-OR-EVIDENCE-INSERT`, exactly one boundary, because TS-01.4 §7.5 states the two paths "perform an **identical atomic bundle**" over an identical lock set (`1 deal → 2 case`) — they are one boundary that admits two kinds of material, not two boundaries.

**Which material arrived is recorded as data, not as a boundary identity**, on the row the bundle inserts:

```sql
CREATE TYPE inrp2p.case_material_kind AS ENUM ('LATE_CLAIM','EVIDENCE');
```

`case_material.material_kind` carries it (§5.15), so the audit trail keeps the distinction TS-02 v2.0 was reaching for without inventing a 48th boundary. A `LATE_CLAIM` additionally carries a UTR and is subject to platform-wide `UNIQUE(utr)` [§5.3]; an `EVIDENCE` row is not. Both increment `case_evidence_seq` under the same admissibility test [§7.5].

**Cardinality is enforced, not asserted.** `scripts/manifest-check.mjs` (§12.2) parses `boundary_code` out of this document, parses the §13.2 table out of TS-01.4, and exits non-zero unless the two sets correspond one-to-one. A 48th member cannot be reintroduced without failing the check.

### 5.3 `ledger_account` — the closed account catalogue

```sql
CREATE TABLE inrp2p.ledger_account (
  account_id     UUID  NOT NULL,
  asset          inrp2p.ledger_asset  NOT NULL,
  class          inrp2p.account_class NOT NULL,
  family         TEXT  NOT NULL,
  scope_kind     TEXT  NOT NULL,
  scope_id       TEXT  NOT NULL,
  shard          INTEGER NOT NULL DEFAULT 0,
  created_at     TIMESTAMPTZ NOT NULL,
  CONSTRAINT ledger_account_pk    PRIMARY KEY (account_id),
  CONSTRAINT ledger_account_uk    UNIQUE (asset, family, scope_kind, scope_id, shard),
  CONSTRAINT ledger_account_shard CHECK (shard >= 0),
  CONSTRAINT ledger_account_asset_family CHECK (
    (asset = 'USDT' AND family IN (
        'wallet.deposit','wallet.hot','wallet.warm','wallet.cold','wallet.buffer',
        'receivable.deposit_reversal','receivable.desk_shortfall','receivable.divergence',

        'platform_compensation_expense','reorg_loss_expense','divergence_loss_expense',
        'platform_capital'))
 OR (asset = 'TRX'  AND family IN (
        'wallet.gas','staked','gas_expense','platform_capital'))),
  CONSTRAINT ledger_account_class_family CHECK (
    (class = 'ASSET'     AND family LIKE 'wallet.%')
 OR (class = 'ASSET'     AND family LIKE 'receivable.%')
 OR (class = 'ASSET'     AND family = 'staked')
 OR (class = 'LIABILITY' AND family IN ('party.balance','desk.reserve','quote_reserved',
                                        'escrow','fee_reserved','hold','withdrawal_payable'))
 OR (class = 'REVENUE'   AND family IN ('fee_revenue','withdrawal_fee_revenue'))
 OR (class = 'EXPENSE'   AND family IN ('platform_compensation_expense','reorg_loss_expense',
                                        'divergence_loss_expense','gas_expense'))
 OR (class = 'EQUITY'    AND family = 'platform_capital')),
  CONSTRAINT ledger_account_shardable CHECK (
    shard = 0 OR family IN ('fee_revenue','withdrawal_fee_revenue',
                            'platform_compensation_expense','reorg_loss_expense',
                            'divergence_loss_expense','gas_expense')),
  -- v2.1: derived over the canonical CE bytes (§3.3), not over a
  -- pipe-delimited string. `account_id_of` is IMMUTABLE, which is what makes
  -- it legal inside a CHECK.
  CONSTRAINT ledger_account_id_derived CHECK (
    account_id = inrp2p.account_id_of(
      ROW(asset, family, scope_kind, scope_id, shard)::inrp2p.account_key))
);

CREATE INDEX ledger_account_family_ix ON inrp2p.ledger_account (family, asset);
```

- **Mutability:** `IMMUTABLE`. An account is never updated and never deleted. Its definition is its identity.
- **Owning boundary:** materialized by whichever boundary first posts to it, via `inrp2p.ensure_accounts()` (§7.2).
- **TS-01.4:** §2.1, §2.2, §2.3, §2.4, [L3].
- The two `CHECK`s together **close the catalogue**: the `(asset, family)` pair and the `(class, family)` pair are both enumerated, so no account outside §2.1/§2.2 can exist. `ledger_account_shardable` restricts sharding to exactly the six families listed in §2.3.
- `ledger_account_id_derived` makes the derived-identity rule a **database** guarantee, not a convention: a row whose `account_id` was not derived from its own key cannot be inserted. This is what allows a boundary to compute its rank-9 lock order before reading the table (§3.2).
- The delimiter `|` is safe because `asset`, `family` and `scope_kind` are drawn from closed sets that contain no `|`, and `scope_id` is constrained to `[0-9a-zA-Z:._-]+` by `inrp2p.ensure_accounts()`.

### 5.7 `reversal_lineage` — rank 8b (the v1.0 contradiction, repaired)

v1.0 declared `reversal_lineage` without `party_id` or `opened_at`, yet its indexes and reconciliation queries referenced both; and it used a **scalar** `lineage_key` in foreign keys where the lineage is identified by a **composite**. Both are repaired here: the composite is the key, and the two missing columns are declared because they are genuinely needed.

```sql
CREATE TABLE inrp2p.reversal_lineage (
  receivable_type    inrp2p.receivable_type NOT NULL,
  source_object_id   TEXT NOT NULL,
  source_seq         BIGINT NOT NULL,

  party_id           UUID NOT NULL,
  opened_at          TIMESTAMPTZ NOT NULL,
  opened_by_entry    UUID NOT NULL,

  delta0_minor       inrp2p.amount_minor_pos NOT NULL,
  rho_minor          inrp2p.amount_minor_nonneg NOT NULL DEFAULT 0,
  kappa_minor        inrp2p.amount_minor_nonneg NOT NULL DEFAULT 0,
  omega_minor        inrp2p.amount_minor_nonneg NOT NULL DEFAULT 0,
  sigma_r_minor      inrp2p.amount_minor_nonneg NOT NULL DEFAULT 0,
  sigma_w_minor      inrp2p.amount_minor_nonneg NOT NULL DEFAULT 0,
  iota_r_minor       inrp2p.amount_minor_nonneg NOT NULL DEFAULT 0,
  iota_c_minor       inrp2p.amount_minor_nonneg NOT NULL DEFAULT 0,
  iota_w_minor       inrp2p.amount_minor_nonneg NOT NULL DEFAULT 0,

  receivable_disp    inrp2p.receivable_disposition    NOT NULL DEFAULT 'OPEN',
  reinstatement_disp inrp2p.reinstatement_disposition NOT NULL DEFAULT 'NONE',
  invalidation_disp  inrp2p.invalidation_disposition  NOT NULL DEFAULT 'VALID',

  version            BIGINT NOT NULL DEFAULT 0,
  updated_at         TIMESTAMPTZ NOT NULL,

  CONSTRAINT reversal_lineage_pk
    PRIMARY KEY (receivable_type, source_object_id, source_seq),
  CONSTRAINT reversal_lineage_control_fk
    FOREIGN KEY (party_id, receivable_type)
    REFERENCES inrp2p.party_receivable_control (party_id, receivable_type),
  CONSTRAINT reversal_lineage_open_fk
    FOREIGN KEY (opened_by_entry) REFERENCES inrp2p.journal_entry (entry_id),
  CONSTRAINT reversal_lineage_seq_nonneg CHECK (source_seq >= 0),
  CONSTRAINT reversal_lineage_conservation CHECK (
    rho_minor + kappa_minor + omega_minor + sigma_r_minor + sigma_w_minor
      + iota_r_minor + iota_c_minor + iota_w_minor = delta0_minor)
);

CREATE INDEX reversal_lineage_party_ix
  ON inrp2p.reversal_lineage (party_id, receivable_type, opened_at);

CREATE INDEX reversal_lineage_eligible_ix
  ON inrp2p.reversal_lineage (party_id, receivable_type, opened_at, source_object_id, source_seq)
  WHERE receivable_disp = 'OPEN' AND invalidation_disp = 'VALID';
```

- **Mutability:** `CAS_MUTABLE`. **TS-01.4:** §4.1 rank 8b, §11.1–§11.4, [M22], [M23], [R-CUR-1..8].
- **The extended lineage conservation identity is a row-level `CHECK`.** `ρ + κ + ω + σ_r + σ_w + ι_r + ι_c + ι_w = Δ₀` references only this row, so it is enforceable directly and permanently. A boundary cannot leave a lineage in a non-conserving state even transiently within its own statement.
- **Every foreign key to a lineage is the full composite** `(receivable_type, source_object_id, source_seq)`. **There is no scalar `lineage_key` column anywhere in this schema.** Any table referencing a lineage declares all three columns.
- `party_id` is declared and is part of the FK into `party_receivable_control`, so a lineage cannot belong to a party whose control row does not exist — which is what makes the rank-8a1 lock sufficient to stabilize the eligible set.
- `opened_at` is declared and is the tiebreak in the eligible-set ordering, so `[R-CUR-2]`'s "same eligible set" is a deterministic ordered read, not a set comparison.
- **The eligible-set read is exactly:**

```sql
SELECT receivable_type, source_object_id, source_seq,
       delta0_minor, rho_minor, receivable_disp, invalidation_disp
  FROM inrp2p.reversal_lineage
 WHERE party_id = $1
   AND receivable_type = $2
   AND receivable_disp = 'OPEN'
   AND invalidation_disp = 'VALID'
 ORDER BY opened_at, source_object_id, source_seq;
```

  taken **after** the rank-8a1 lock. Under [R-CUR-2] the step-3 and step-6 reads MUST be identical; any difference is a severity-1 `allocation_snapshot_conflict` (§10.4), not a retry.
- **Guard priority** is fixed and is `loss_reversed` **before** `lineage_invalidated` [R-CUR-6]: a lineage whose `invalidation_disp = 'LOSS_REVERSED'` reports `loss_reversed` even though it is also not `VALID`.

### 5.19 Outbox and inbox

**Correction (v2.1) — `event_key` was missing entirely.** TS-01.4 [O2] states: "Every outbox record carries a deterministic `event_key` under `UNIQUE(outbox.event_key)`; retried boundaries produce the same key and therefore one record", and §5.3 lists `UNIQUE(outbox.event_key)` in the uniqueness catalogue. TS-02 v2.0 contained **no occurrence of `event_key` anywhere in the document**. Without it, [O2] is unimplemented, [O3]'s "every consumer is idempotent by `event_key`" has no key to be idempotent on, and K-R34 / F72 ("the same `event_key` delivered ×100 → one consumer effect") are untestable. The column below is mandatory, `NOT NULL`, and uniquely constrained.

```sql
CREATE TABLE inrp2p.outbox (
  outbox_id     BIGINT GENERATED ALWAYS AS IDENTITY,
  -- [O2] Deterministic logical identity of the effect. Derived, never random:
  -- a retried boundary MUST recompute the identical value, which is what makes
  -- "one record per logical effect" hold across crash and replay.
  event_key     TEXT NOT NULL,
  entry_id      UUID NULL,
  boundary_code inrp2p.boundary_code NOT NULL,
  topic         TEXT NOT NULL,
  payload       JSONB NOT NULL,
  created_at    TIMESTAMPTZ NOT NULL,
  txid          BIGINT NOT NULL,
  dispatched_at TIMESTAMPTZ NULL,
  dispatch_attempts INTEGER NOT NULL DEFAULT 0,
  CONSTRAINT outbox_pk PRIMARY KEY (outbox_id),
  -- [§5.3] "UNIQUE(outbox.event_key) | One record per logical effect;
  -- duplicate delivery is a consumer no-op."
  CONSTRAINT outbox_event_key_uq UNIQUE (event_key),
  CONSTRAINT outbox_event_key_shape CHECK (
    event_key ~ '^[A-Z0-9-]{3,40}:[0-9a-z._:-]{1,180}$'),
  CONSTRAINT outbox_entry_fk FOREIGN KEY (entry_id) REFERENCES inrp2p.journal_entry (entry_id),
  CONSTRAINT outbox_payload_obj CHECK (jsonb_typeof(payload) = 'object'),
  CONSTRAINT outbox_attempts CHECK (dispatch_attempts >= 0)
);

CREATE INDEX outbox_pending_ix ON inrp2p.outbox (outbox_id) WHERE dispatched_at IS NULL;

CREATE TABLE inrp2p.inbox (
  source        TEXT NOT NULL,
  external_id   TEXT NOT NULL,
  received_at   TIMESTAMPTZ NOT NULL,
  payload       JSONB NOT NULL,
  processed_at  TIMESTAMPTZ NULL,
  processed_entry UUID NULL,
  CONSTRAINT inbox_pk PRIMARY KEY (source, external_id),
  CONSTRAINT inbox_entry_fk FOREIGN KEY (processed_entry) REFERENCES inrp2p.journal_entry (entry_id),
  CONSTRAINT inbox_payload_obj CHECK (jsonb_typeof(payload) = 'object'),
  CONSTRAINT inbox_source CHECK (source IN ('CHAIN_WATCHER','PRICING','BANK_FEED','OPERATOR_TOOL'))
);
```

**`event_key` derivation — deterministic, and never a random or clock value.**

```
event_key := <BOUNDARY-CODE> ':' <effect-discriminator>
```

The discriminator is the **already-immutable natural identity of the effect**, so recomputation is automatic rather than remembered:

| Effect | `event_key` |
|---|---|
| Broadcast a signed withdrawal attempt [O5] | `TB-WITHDRAW-SIGN:broadcast.<txid>` |
| Rebroadcast of the same attempt | *the same key* — [O5] replays persisted bytes, so it is the same logical effect, not a new one |
| Notify a journal-bearing effect | `<boundary>:entry.<entry_key_digest>` |
| Notify a deal state change | `<boundary>:deal.<deal_id>.v<version>` |
| Anchor an audit segment | `TB-RISK-MODE-SET:anchor.<segment_no>` |

Because every discriminator is a committed immutable identity (`txid` is immutable from `PREPARED` [W3]; `entry_key_digest` is the journal's own identity; `version` is the CAS-guarded value written in the same transaction), a retry of the boundary recomputes the same string and the unique constraint collapses it to one row — which is exactly the [O2] guarantee, obtained structurally.

**`event_key` carries no value semantics** [O4]: no journal is implied or scheduled by an outbox record. It identifies an *effect*, never an amount.

- **Mutability:** `outbox` `OPERATIONAL` (only `dispatched_at` and `dispatch_attempts` are updatable, and only by `inrp2p_relay`); `event_key`, `entry_id`, `boundary_code`, `topic`, `payload`, `created_at` and `txid` are append-only, enforced by the `outbox_append_only_bu` trigger of §6.7.
- **TS-01.4:** §14, [O1]–[O5]; §5.3 `UNIQUE(outbox.event_key)`; K-R34; F72, F73, F74.
- **[O1]** is structural: the outbox row carries the same `txid` as its journal entry, so "committed in one transaction" is a checkable equality, not an assertion. `tests/outbox/atomicity.spec.ts` asserts `outbox.txid = journal_entry.txid` for every entry-linked row.
- **The inbox is the deduplication point for every external observation.** `PRIMARY KEY (source, external_id)` means a chain watcher replaying 100 duplicate observations inserts one row [F29], and recognition is driven from the inbox rather than from the network handler.

- **TS-01.4:** [B2] (audit inside the same commit, with `decision_time()`, mode version, and pre/post `FreeBuffer` for SDJ boundaries), §17 severity-1 conditions.
- **`audit_event_rejected_no_entry` is the structural half of §10**: a rejected boundary cannot reference a journal entry, so an audit row proving rejection cannot also point at money.
- **`boundary_frame` is `UNLOGGED` and keyed by `txid`.** It is written **once** by the `SECURITY DEFINER` prologue and is the mechanism that replaces v1.0's caller-settable `SET LOCAL inrp2p.boundary` (§9.4).
- **`partition_policy` is versioned and forward-only** — this is the resolution of **BA-6**. `shard_count` applies to accounts materialized **at or after** `effective_from`. Existing account rows are never re-sharded and history is never rewritten; a policy change adds shards, and reporting sums all shards regardless of the policy version that created them [§2.3].
- **`operator_config` is versioned, not invented** — the resolution of **BA-8**. TS-02 defines the representation and the fact that a value must exist; it does **not** choose the value. A boundary that reads a config key with no row fails `config_absent` and raises a severity-2 incident.

## 6. Structural enforcement

v1.0 offered an **illegal `CHECK` containing a subquery** for [M5]. PostgreSQL does not permit a subquery in a `CHECK`, and even if it did, a `CHECK` is not re-evaluated when the *other* row changes, so it would not enforce the invariant. Both problems are fixed by splitting every invariant into the part that is row-local (a real `CHECK`) and the part that spans rows (a `DEFERRABLE INITIALLY DEFERRED` constraint trigger evaluated at commit, under locks the boundary already holds).

**Why deferred constraint triggers are correct here.** A money boundary legitimately passes through intermediate states inside its own transaction — a journal exists before its postings, a control row is updated before its lineages are. Enforcing at statement time would reject correct boundaries. Enforcing at **commit** time asserts exactly what TS-01.4 asserts: the *committed* state is consistent. Because the boundary already holds the relevant Tier-A locks, the trigger reads a stable snapshot and cannot race.

### 6.1 `decision_time()`

```sql
CREATE FUNCTION inrp2p.decision_time() RETURNS TIMESTAMPTZ
LANGUAGE sql VOLATILE
SET search_path = pg_catalog
AS $dt$ SELECT clock_timestamp() $dt$;
```

- `clock_timestamp()`, never `now()`, `CURRENT_TIMESTAMP` or `transaction_timestamp()`, which are all fixed at transaction start and would make an expired object consumable by a transaction that waited on a lock [T1–T4, F4, F5, F6].
- **Call position is normative**, not stylistic: `decision_time()` is read **after** the lock that decides the outcome, exactly where §13.2 places it. `TB-MOVE` reads it after `4 quote(X)`; `TB-LINK-JOIN` after `5 link(X)`; `TB-LINK-CLOSE` after `5 link(X)`. `TB-LINK-CREATE` has **no** post-lock expiry clock at all.
- **F6 is the mutant**: substituting a transaction-start timestamp must make the suite fail.

### 6.2 Per-asset zero sum, before the entry is visible

```sql
CREATE FUNCTION inrp2p.trg_entry_balanced() RETURNS TRIGGER
LANGUAGE plpgsql
SET search_path = pg_catalog, inrp2p
AS $fn$
DECLARE
  v_bad TEXT;
BEGIN
  SELECT string_agg(asset::text || '=' || total::text, ',')
    INTO v_bad
    FROM (SELECT asset, sum(amount_minor) AS total
            FROM inrp2p.posting WHERE entry_id = NEW.entry_id
           GROUP BY asset HAVING sum(amount_minor) <> 0) s;
  IF v_bad IS NOT NULL THEN
    RAISE EXCEPTION 'journal entry % not balanced per asset: %', NEW.entry_id, v_bad
      USING ERRCODE = 'integrity_constraint_violation';
  END IF;
  IF NOT EXISTS (SELECT 1 FROM inrp2p.posting WHERE entry_id = NEW.entry_id) THEN
    RAISE EXCEPTION 'journal entry % has no postings', NEW.entry_id
      USING ERRCODE = 'integrity_constraint_violation';
  END IF;
  RETURN NULL;
END;
$fn$;

CREATE CONSTRAINT TRIGGER journal_entry_balanced_ct
  AFTER INSERT ON inrp2p.journal_entry
  DEFERRABLE INITIALLY DEFERRED
  FOR EACH ROW EXECUTE FUNCTION inrp2p.trg_entry_balanced();
```

[M1]/[M2]: every entry balances **per asset**, and no empty entry exists. Deferred to commit, so postings may be inserted after the entry header; not deferrable by the caller, because the trigger is declared `INITIALLY DEFERRED` and `SET CONSTRAINTS ALL IMMEDIATE` only tightens it.

### 6.3 Posting order inside an ordered journal

```sql
CREATE FUNCTION inrp2p.trg_posting_order() RETURNS TRIGGER
LANGUAGE plpgsql
SET search_path = pg_catalog, inrp2p
AS $fn$
DECLARE
  v_n INT; v_max INT;
BEGIN
  SELECT count(*), max(seq) INTO v_n, v_max
    FROM inrp2p.posting WHERE entry_id = NEW.entry_id;
  IF v_max <> v_n THEN
    RAISE EXCEPTION 'entry % posting seq must be 1..n contiguous (n=%, max=%)',
      NEW.entry_id, v_n, v_max USING ERRCODE = 'integrity_constraint_violation';
  END IF;
  RETURN NULL;
END;
$fn$;

CREATE CONSTRAINT TRIGGER posting_order_ct
  AFTER INSERT ON inrp2p.posting
  DEFERRABLE INITIALLY DEFERRED
  FOR EACH ROW EXECUTE FUNCTION inrp2p.trg_posting_order();
```

Ordered journals — notably `JD-C2a` + `JD-C2b`, which are the **two entries of one atomic transaction** [§13.1/JD-C2b] — depend on `seq` being contiguous from 1, so "entry 1 of 2" and "entry 2 of 2" are structurally distinguishable and a partial application is detectable.

### 6.4 Receivable allocation completeness

```sql
CREATE FUNCTION inrp2p.trg_allocation_complete() RETURNS TRIGGER
LANGUAGE plpgsql
SET search_path = pg_catalog, inrp2p
AS $fn$
DECLARE
  r RECORD;
  v_alloc NUMERIC;
BEGIN
  FOR r IN
    SELECT p.entry_id, p.account_id, abs(p.amount_minor) AS magnitude
      FROM inrp2p.posting p
      JOIN inrp2p.ledger_account a ON a.account_id = p.account_id
     WHERE p.entry_id = NEW.entry_id
       AND a.family LIKE 'receivable.%'
  LOOP
    SELECT coalesce(sum(amount_minor), 0) INTO v_alloc
      FROM inrp2p.receivable_allocation WHERE entry_id = r.entry_id;
    IF v_alloc <> r.magnitude THEN
      RAISE EXCEPTION
        'entry % posts % to a receivable account but allocates % (M22)',
        r.entry_id, r.magnitude, v_alloc
        USING ERRCODE = 'integrity_constraint_violation';
    END IF;
  END LOOP;
  RETURN NULL;
END;
$fn$;

CREATE CONSTRAINT TRIGGER allocation_complete_ct
  AFTER INSERT ON inrp2p.journal_entry
  DEFERRABLE INITIALLY DEFERRED
  FOR EACH ROW EXECUTE FUNCTION inrp2p.trg_allocation_complete();
```

[M22]: **a receivable posting without a complete allocation set cannot commit.** The boundaries that §13.2 marks "receivable allocation set required" are satisfied structurally rather than by review.

### 6.5 Account non-negativity, control agreement, and S1

```sql
CREATE FUNCTION inrp2p.trg_balance_rules() RETURNS TRIGGER
LANGUAGE plpgsql
SET search_path = pg_catalog, inrp2p
AS $fn$
DECLARE
  v_family TEXT;
BEGIN
  SELECT family INTO v_family FROM inrp2p.ledger_account WHERE account_id = NEW.account_id;

  IF v_family LIKE 'receivable.%' AND NEW.balance_minor < 0 THEN
    RAISE EXCEPTION 'receivable account % went negative (M5)', NEW.account_id
      USING ERRCODE = 'integrity_constraint_violation';
  END IF;

  IF v_family IN ('party.balance','desk.reserve','escrow','quote_reserved',
                  'fee_reserved','hold','withdrawal_payable')
     AND NEW.balance_minor > 0 THEN
    RAISE EXCEPTION 'liability account % has a debit balance', NEW.account_id
      USING ERRCODE = 'integrity_constraint_violation';
  END IF;

  IF v_family LIKE 'wallet.%' AND NEW.balance_minor < 0 THEN
    RAISE EXCEPTION 'wallet account % went negative', NEW.account_id
      USING ERRCODE = 'integrity_constraint_violation';
  END IF;

  RETURN NULL;
END;
$fn$;

CREATE CONSTRAINT TRIGGER balance_rules_ct
  AFTER INSERT OR UPDATE ON inrp2p.account_balance
  DEFERRABLE INITIALLY DEFERRED
  FOR EACH ROW EXECUTE FUNCTION inrp2p.trg_balance_rules();

CREATE FUNCTION inrp2p.trg_receivable_control_agrees() RETURNS TRIGGER
LANGUAGE plpgsql
SET search_path = pg_catalog, inrp2p
AS $fn$
DECLARE
  v_open NUMERIC; v_booked NUMERIC; v_count INT;
BEGIN
  SELECT coalesce(sum(rho_minor),0), coalesce(sum(delta0_minor),0), count(*)
    INTO v_open, v_booked, v_count
    FROM inrp2p.reversal_lineage
   WHERE party_id = NEW.party_id AND receivable_type = NEW.receivable_type;

  IF v_open <> NEW.open_minor OR v_booked <> NEW.sum_booked_minor
     OR v_count <> NEW.lineage_count THEN
    RAISE EXCEPTION
      'party_receivable_control(%,%) disagrees with its lineages (M22): open %/% booked %/% count %/%',
      NEW.party_id, NEW.receivable_type, NEW.open_minor, v_open,
      NEW.sum_booked_minor, v_booked, NEW.lineage_count, v_count
      USING ERRCODE = 'integrity_constraint_violation';
  END IF;
  RETURN NULL;
END;
$fn$;

CREATE CONSTRAINT TRIGGER receivable_control_agrees_ct
  AFTER INSERT OR UPDATE ON inrp2p.party_receivable_control
  DEFERRABLE INITIALLY DEFERRED
  FOR EACH ROW EXECUTE FUNCTION inrp2p.trg_receivable_control_agrees();
```

This is **the resolution of BA-3**, in full:

| [M5] / [M22] obligation | Enforcement |
|---|---|
| A receivable is never negative | `amount_minor_nonneg` domain on `open_minor`, plus `trg_balance_rules` on the receivable *account* balance |
| `control.open = Σ` lineage `ρ` | `receivable_control_agrees_ct`, deferred, under the rank-8a1 lock the boundary already holds |
| `control.sum_booked = Σ` committed bookings | same trigger, same read |
| Lineage conservation `ρ+κ+ω+σ_r+σ_w+ι_r+ι_c+ι_w = Δ₀` | row-level `CHECK` on `reversal_lineage` (§5.7) |
| Cure capped at the open receivable | boundary CAS (§7) plus the two above; a cure that overshoots leaves `open_minor < 0`, which the domain rejects |

No subquery `CHECK` appears anywhere in this schema.

### 6.6 Terms, rate and direction

```sql
CREATE FUNCTION inrp2p.trg_deal_terms_copied() RETURNS TRIGGER
LANGUAGE plpgsql
SET search_path = pg_catalog, inrp2p
AS $fn$
DECLARE
  v_src TEXT;
BEGIN
  IF NEW.origin_kind = 'QUOTE' THEN
    SELECT term_digest INTO v_src FROM inrp2p.quote WHERE quote_id = NEW.origin_quote_id;

  ELSE
    SELECT term_digest INTO v_src FROM inrp2p.funded_link WHERE link_id = NEW.origin_link_id;
    IF v_src IS DISTINCT FROM NEW.term_digest THEN
      RAISE EXCEPTION 'deal % terms differ from link % (M12-prime)', NEW.deal_id, NEW.origin_link_id
        USING ERRCODE = 'integrity_constraint_violation';
    END IF;
  END IF;
  RETURN NULL;
END;
$fn$;

CREATE CONSTRAINT TRIGGER deal_terms_copied_ct
  AFTER INSERT ON inrp2p.deal

  FOR EACH ROW EXECUTE FUNCTION inrp2p.trg_deal_terms_copied();

CREATE FUNCTION inrp2p.trg_terms_arithmetic() RETURNS TRIGGER
LANGUAGE plpgsql
SET search_path = pg_catalog, inrp2p
AS $fn$
BEGIN
  IF NEW.principal_minor * NEW.rate_num
       <> NEW.term_minor * NEW.rate_den + NEW.rounding_remainder_minor THEN
    RAISE EXCEPTION
      'terms fail P*num = gross*den + rem (P=% num=% gross=% den=% rem=%)',
      NEW.principal_minor, NEW.rate_num, NEW.term_minor,
      NEW.rate_den, NEW.rounding_remainder_minor
```

Together with the row `CHECK`s of §5.14 (`gcd(rate_num, rate_den) = 1`, `rounding_remainder_minor < rate_den`, and the closed direction/currency pairs), the rounding contract of §4.6 is **fully database-enforced**: an implementation cannot round the wrong way, cannot lose a remainder, cannot store an unreduced rate, and cannot invent a currency combination.

`gcd()` is a PostgreSQL 13+ built-in for `numeric`, so no extension is needed.

```sql
CREATE FUNCTION inrp2p.trg_command_complete_once() RETURNS TRIGGER

      USING ERRCODE = 'integrity_constraint_violation';

  IF NEW.command_id <> OLD.command_id OR NEW.command_hash <> OLD.command_hash
```

**`trg_bump_version` closes a real hole**: if the caller could write `version`, CAS would compare a value the caller chose. Managed by the database, `version` is a fact.

### 6.8 Write-off command integrity

```sql
CREATE FUNCTION inrp2p.writeoff_command_hash(p_cmd UUID) RETURNS TEXT
LANGUAGE sql STABLE STRICT
SET search_path = pg_catalog, inrp2p
AS $wh$
  SELECT encode(sha256(
           inrp2p.ce_text('writeoff_command_id', p_cmd::text)
        || coalesce(
             (SELECT string_agg(
                  inrp2p.ce_text('receivable_type',  l.receivable_type::text)
               || inrp2p.ce_text('source_object_id', l.source_object_id)
               || inrp2p.ce_int ('source_seq',       l.source_seq::numeric)
               || inrp2p.ce_int ('amount_minor',     l.amount_minor),
                  ''::bytea ORDER BY l.line_seq)
                FROM inrp2p.writeoff_command_line l
               WHERE l.writeoff_command_id = p_cmd), ''::bytea)
         ), 'hex');
$wh$;
```

`TB-APPROVE-C` and `TB-REORG-WRITEOFF` recompute this **after** taking the rank-0b lock and compare it to the stored `command_hash`; a mismatch is `writeoff_command_modified`, a severity-1 condition. A line added after approval therefore cannot be applied [R-CUR-4].

## 7. Transaction boundary implementation

v1.0 collapsed branches whose lock sets, guards, journals or outcomes differ — most damagingly the three link boundaries, which it merged into one incorrect row. **No branch is collapsed here.** All 47 boundaries/branches of §13.2 appear in §7.4 with their complete canonical lock sets reproduced verbatim.

### 7.1 The universal boundary skeleton

Every boundary is a `SECURITY DEFINER` function owned by `inrp2p_boundary` (§9) with this exact shape. Deviating from it is a defect, not a style choice.

```sql
CREATE TYPE inrp2p.boundary_result AS (
  ok           BOOLEAN,
  result_code  TEXT,
  entry_id     UUID,
  payload      JSONB
);
```

1. **Prologue.** Record the boundary frame — one row, one txid, un-forgeable (§9.4):

   ```sql
   INSERT INTO inrp2p.boundary_frame (txid, boundary_code, entered_at)
   VALUES (txid_current(), <this boundary>, clock_timestamp());
   ```

   A duplicate-key violation here means two boundaries were attempted in one transaction, which [B1]/[B3] forbid; it is a severity-1 `nested_boundary`.

2. **Command admission.** `INSERT INTO inrp2p.command` with `ON CONFLICT (command_id) DO NOTHING`. If the row already exists, §8.2 decides replay versus conflict **before any lock is taken**.

3. **Locks, in canonical order.** Exactly the set in §7.4 for this boundary, strictly non-decreasing in rank, ascending primary key within a rank [§4.1, L1–L7]. A boundary MUST NOT acquire a lock it does not list, and MUST NOT omit one it does.

4. **Post-lock clock**, if and only if §7.4 says so, at the stated position (§6.1).

5. **Guards**, in the stated priority order. The first failing guard determines the result code. Guard order is normative: `loss_reversed` is evaluated **before** `lineage_invalidated` [R-CUR-6].

6. **CAS writes**, each asserting exactly one affected row:

   ```sql
   UPDATE inrp2p.<table> SET <cols>, version = version   -- bumped by trigger
    WHERE <pk> = $1 AND version = $2 AND state = $3;
   GET DIAGNOSTICS v_rows = ROW_COUNT;
   IF v_rows <> 1 THEN RETURN inrp2p.reject(<code>); END IF;
   ```

7. **Journal, postings, immutable records, allocations** — all inside this transaction.

8. **Audit event**, always, with `decision_time()`, the observed `mode_version`, and for SDJ boundaries the pre- and post-`FreeBuffer` [B2].

9. **Outbox rows** for every external effect [O1]. **No boundary performs a network call** [B1] and **no boundary broadcasts** [B3].

10. **Return** the composite. **The function does not `RAISE` on an expected rejection** (§10).

### 7.2 Rank-9 account materialization and locking

This is the operational consequence of the derived `account_id` (§3.2), and the resolution of **BA-2**.

```sql
CREATE FUNCTION inrp2p.ensure_accounts(p_keys inrp2p.account_key[])
RETURNS UUID[]
LANGUAGE plpgsql
SET search_path = pg_catalog, inrp2p
AS $fn$
DECLARE
  v_ids UUID[];
BEGIN
  SELECT array_agg(k.account_id ORDER BY k.account_id) INTO v_ids
    FROM (SELECT inrp2p.account_id_of(e) AS account_id
            FROM unnest(p_keys) AS e) k;

  INSERT INTO inrp2p.ledger_account (account_id, asset, class, family, scope_kind, scope_id, shard, created_at)
  SELECT inrp2p.account_id_of(e),
         (e).asset, inrp2p.account_class_of((e).family), (e).family,
         (e).scope_kind, (e).scope_id, (e).shard,
         inrp2p.decision_time()
    FROM unnest(p_keys) AS e
  ON CONFLICT (account_id) DO NOTHING;

  PERFORM 1 FROM inrp2p.ledger_account
   WHERE account_id = ANY (v_ids)
   ORDER BY account_id
     FOR UPDATE;

  RETURN v_ids;
END;
$fn$;
```

- The lock order is `ORDER BY account_id`, which is the canonical rank-9 order, and it is **computable from the keys alone** — no read-then-write.
- `ON CONFLICT DO NOTHING` makes materialization idempotent under concurrency; [L2] exempts the freshly inserted rows from ordering because they are invisible to other transactions until commit.
- `scope_id` MUST match `^[0-9a-zA-Z:._-]+$`, asserted by `ensure_accounts` before encoding, so the `|` delimiter is unambiguous.

### 7.3 What every contract below states

| Field | Meaning |
|---|---|
| **Function** | The exact `SECURITY DEFINER` function implementing the boundary |

| **Post-lock clock** | Whether `decision_time()` is read, and exactly where |
| **Journals** | The journals this boundary may apply, verbatim |

| **Isolation / retry** | Isolation level and the retry rule |

**Retry rule, stated once and applying to all 47.** Isolation is `READ COMMITTED`. A serialization failure (`40001`) or deadlock (`40P01`) is retried by the **caller**, from the start of the boundary, re-acquiring every lock in canonical order — never from the middle, because a partially-locked retry would violate [L1]. **A CAS returning zero rows is never retried**: it is a deterministic conflict with a deterministic code, and retrying it would convert a correct rejection into a livelock.

## 8. Idempotency and compound-result inspection

### 8.1 The deleted rule

v1.0 contained:

> ~~`entry_key` unique violation → idempotent success~~

**This rule is deleted.** It is wrong, and it is dangerous in exactly the cases that matter most.

A unique violation on `journal_entry (journal_code, entry_key_digest)` proves only that *some* transaction previously inserted a journal header with that key. It does **not** prove that transaction committed the rest of its result. **A journal alone never proves a complete committed result** [R-U1]. Treating the collision as success would return "done" for a result that may be missing its postings, its recognition record, its allocation set, or its second entry.

### 8.2 Command-level idempotency (the only "same id ⇒ same result" rule)

Evaluated **before any lock**, on `inrp2p.command`:

| Observed | Outcome |
|---|---|
| No row | Insert, proceed |
| Row exists, `command_hash` differs | **`command_conflict`** — a different payload reusing an identifier. Never a silent success |
| Row exists, hash matches, `completed_at IS NULL` | **`command_in_flight`** — the caller retries later. Not a duplicate execution |
| Row exists, hash matches, `completed_at IS NOT NULL` | Return the stored `result_code` / `result_json` verbatim |

This is the **envelope**, not the money. It never substitutes for §8.3.

### 8.3 Journal replay: mandatory complete-result inspection

On an `entry_key` collision, the boundary MUST:

1. Load the **complete committed component set** for that `entry_key`.
2. Prove it consistent against the journal's declared contract in §13.1.
3. Only then return the recorded result as idempotent.

An **incomplete or inconsistent** component set is **never** idempotent success; it produces the exact severity-1 outcome TS-01.4 names for that journal.

```sql
CREATE FUNCTION inrp2p.load_committed_result(p_journal TEXT, p_digest TEXT)
RETURNS inrp2p.boundary_result
LANGUAGE plpgsql
SET search_path = pg_catalog, inrp2p
AS $fn$
DECLARE
  v_entry     inrp2p.journal_entry%ROWTYPE;
  v_postings  INT;
  v_asset_bad INT;
  v_required  TEXT[];
  v_missing   TEXT[] := ARRAY[]::TEXT[];
  r           TEXT;
  v_ok        BOOLEAN;
BEGIN
  SELECT * INTO v_entry FROM inrp2p.journal_entry
   WHERE journal_code = p_journal AND entry_key_digest = p_digest;
  IF NOT FOUND THEN
    RETURN inrp2p.reject('replay_target_missing');
  END IF;

  SELECT count(*) INTO v_postings FROM inrp2p.posting WHERE entry_id = v_entry.entry_id;
  SELECT count(*) INTO v_asset_bad
    FROM (SELECT asset FROM inrp2p.posting WHERE entry_id = v_entry.entry_id
           GROUP BY asset HAVING sum(amount_minor) <> 0) s;

  IF v_postings = 0 OR v_asset_bad > 0 THEN
    PERFORM inrp2p.raise_incident(1, 'incomplete_committed_result', p_journal, p_digest);
    RETURN inrp2p.reject('incomplete_committed_result');
  END IF;

  SELECT required_records INTO v_required
    FROM inrp2p.journal_component_contract WHERE journal_code = p_journal;

  FOREACH r IN ARRAY coalesce(v_required, ARRAY[]::TEXT[]) LOOP
    EXECUTE format('SELECT EXISTS (SELECT 1 FROM inrp2p.%I WHERE entry_id = $1)', r)
       INTO v_ok USING v_entry.entry_id;
    IF NOT v_ok THEN v_missing := v_missing || r; END IF;
  END LOOP;

  IF array_length(v_missing, 1) IS NOT NULL THEN
    PERFORM inrp2p.raise_incident(1,
      inrp2p.severity1_code_for(p_journal), p_journal,
      p_digest || ' missing=' || array_to_string(v_missing, ','));
    RETURN inrp2p.reject(inrp2p.severity1_code_for(p_journal));
  END IF;

  RETURN ROW(TRUE, 'idempotent_replay', v_entry.entry_id,
             jsonb_build_object('entry_id', v_entry.entry_id))::inrp2p.boundary_result;
END;
$fn$;

CREATE TABLE inrp2p.journal_component_contract (
  journal_code     TEXT NOT NULL,
  required_records TEXT[] NOT NULL,
  sibling_journal  TEXT NULL,
  severity1_code   TEXT NOT NULL,
  CONSTRAINT journal_component_contract_pk PRIMARY KEY (journal_code),
  CONSTRAINT journal_component_contract_fk FOREIGN KEY (journal_code)
             REFERENCES inrp2p.journal_catalogue (journal_code),
  CONSTRAINT journal_component_contract_sib_fk FOREIGN KEY (sibling_journal)
             REFERENCES inrp2p.journal_catalogue (journal_code)
);

-- Correction (v2.1): v2.0 called `severity1_code_for()` twice and described its
-- behaviour in prose, but never defined it. A migration containing the caller
-- and not the callee fails at first execution. The definition follows.
--
-- It is STRICT-by-guard rather than by decoration: a journal missing from the
-- contract catalogue is itself a catalogue defect, so the function raises
-- rather than silently returning a generic code that would mask it.
CREATE FUNCTION inrp2p.severity1_code_for(p_journal TEXT)
RETURNS TEXT
LANGUAGE plpgsql
STABLE
SECURITY DEFINER
SET search_path = inrp2p, pg_catalog
AS $fn$
DECLARE
  v_code TEXT;
BEGIN
  SELECT severity1_code INTO v_code
    FROM inrp2p.journal_component_contract
   WHERE journal_code = p_journal;

  IF v_code IS NULL THEN
    -- Closed-catalogue violation: every one of the 57 journals of §13.1 has a
    -- contract row. Reaching here means the catalogue was not seeded or a
    -- journal was emitted from outside it, which §17 B1 forbids.

$fn$;

```

- **Mutability:** `CATALOGUE`, seeded in migration `0004` with one row per journal, derived from the "Immutable records" field of §13.1. `tests/meta/conformance.spec.ts` asserts one row for each of the **57** journals.
- `severity1_code_for()` reads `severity1_code`, so each journal returns **its own** TS-01.4 severity-1 code rather than a generic one.

### 8.4 Compound results

Three families commit **more than one journal or record** as a single result. For these, inspecting the journal header — or even the header plus postings — is insufficient.

| Family | Components that MUST all be present and consistent | Severity-1 code on a partial set |
|---|---|---|
| **Recognition cycles** (`JD1`, `JD2`, `JS1`, `JGX`, `JBF1`, `JG1` and their `-R` / `-RE` counterparts) | journal + postings + `recognition_record` at the exact `rseq` + the chain object in the exact post-CAS state | `inconsistent_recognition_cycle` |
| **`JW-DR`** (divergence recovery booking) | journal + postings + `divergence_recovery_control` updated + the new lineage + its allocation set | `inconsistent_recovery_snapshot` |
| **`JW-DW`** (divergence write-off) | journal + postings + `writeoff_command` marked applied + **every** `writeoff_command_line` reflected in lineage dispositions | `inconsistent_divergence_writeoff` |
| **`JD-C2a` + `JD-C2b`** | **both** entries, contiguous `seq`, one recognition record at `rseq = 0`, complete allocation set on `JD-C2b` | `inconsistent_recognition_cycle` |

`sibling_journal` in `journal_component_contract` carries the `JD-C2a` ↔ `JD-C2b` pairing, so the check for either half looks for the other.

**`JD-C2a`/`JD-C2b` deserve emphasis.** They are the two entries of **one** transaction [§13.1/JD-C2b]; partial application is impossible by construction, so observing one without the other is not a race to be retried — it is evidence of corruption, and it must produce a severity-1 incident rather than an idempotent success.

### 8.5 State-sensitive duplicate handling [R-CYC-2a]

Sweeps are the sharp case. `BROADCAST → RECOGNIZED → REVERSED` is terminal and re-recognition is prohibited absolutely [R-CYC-2].

| Locked sweep state | Repeat finalized observation | Outcome |
|---|---|---|
| `BROADCAST` | first recognition | apply `JS1` |
| `RECOGNIZED` | consistent with the recorded initial recognition | idempotent replay via §8.3 |
| `RECOGNIZED` | **inconsistent** with the recorded initial recognition | severity-1 `inconsistent_sweep_recognition` |
| `REVERSED` | any finalized reappearance | severity-1 **`sweep_reappearance_after_reversal`** — **never** a re-recognition |

The last row is why `state_transition` (§6.9) contains no row whose `entity` is `sweep` and whose `from_state` is `REVERSED`, for any `to_state`: even a boundary that tried to re-recognize would be refused by the database.

## 9. The database security boundary

v1.0 relied on grep-based CI and a caller-settable `SET LOCAL inrp2p.boundary`. Neither is a security control: grep does not run in production, and a GUC the caller can set is a claim, not a credential. Both are replaced.

### 9.1 Roles

| Role | LOGIN | Purpose |
|---|---|---|
| `inrp2p_owner` | no | Owns the schema, types, tables and triggers. Runs migrations via `SET ROLE` from a migration operator. Never used by a running service |
| `inrp2p_boundary` | no | Owns every `SECURITY DEFINER` boundary function. **The only role with DML on money tables** |
| `inrp2p_app` | yes | The API service. `EXECUTE` on boundary functions and `SELECT` on read views. **No DML on any money table** |
| `inrp2p_relay` | yes | Outbox dispatcher. `SELECT` on `outbox`; `UPDATE` on `outbox.dispatched_at` and `outbox.dispatch_attempts` only |
| `inrp2p_recon` | yes | Reconciliation and reporting. `SELECT` only, on everything |

### 9.2 Grants and revocations

```sql
REVOKE ALL ON SCHEMA inrp2p FROM PUBLIC;
REVOKE ALL ON ALL TABLES    IN SCHEMA inrp2p FROM PUBLIC;
REVOKE ALL ON ALL FUNCTIONS IN SCHEMA inrp2p FROM PUBLIC;
REVOKE ALL ON ALL SEQUENCES IN SCHEMA inrp2p FROM PUBLIC;

GRANT USAGE ON SCHEMA inrp2p TO inrp2p_boundary, inrp2p_app, inrp2p_relay, inrp2p_recon;

-- Boundary role: the only DML on money.
GRANT SELECT, INSERT, UPDATE ON ALL TABLES IN SCHEMA inrp2p TO inrp2p_boundary;
REVOKE DELETE ON ALL TABLES IN SCHEMA inrp2p FROM inrp2p_boundary;

                 inrp2p.recognition_record, inrp2p.reinstatement_record,
                 inrp2p.hold_release, inrp2p.withdrawal_recognition,
                 inrp2p.gas_record, inrp2p.compensation_record,
                 inrp2p.case_evidence, inrp2p.payment_claim, inrp2p.approval,
                 inrp2p.writeoff_command_line
  FROM inrp2p_boundary;

-- Application role: execute boundaries, read views. Nothing else.
GRANT EXECUTE ON FUNCTION
  inrp2p.tb_move(UUID, JSONB), inrp2p.tb_quote_issue(UUID, JSONB),
```

**Consequences that are now facts rather than conventions:**

- `inrp2p_app` **cannot** `INSERT` a journal, `UPDATE` a balance, or `DELETE` anything, whatever the ORM emits. A defective query is a privilege error, not a money error.
- `DELETE` is revoked from **every** role on **every** table. Retention and archival move data by partition detach (§11, BA-5), never by row deletion.
- Immutable tables have `UPDATE` revoked from the boundary role too, so append-only is enforced by privilege **and** by trigger (§6.7). Either alone would be sufficient; both is deliberate.
- Operator-facing boundaries (`TB-APPROVE-*`, `TB-RISK-MODE-SET`, `TB-HOLD-*`, `TB-SUSPEND`) are **not** granted to `inrp2p_app`. They are executed by a separate operator service with its own role, so a compromised public API cannot reach them.

### 9.3 `SECURITY DEFINER` ownership and fixed `search_path`

Every boundary function is declared:

```sql
ALTER FUNCTION inrp2p.tb_move(UUID, JSONB) OWNER TO inrp2p_boundary;
ALTER FUNCTION inrp2p.tb_move(UUID, JSONB) SECURITY DEFINER;
ALTER FUNCTION inrp2p.tb_move(UUID, JSONB) SET search_path = pg_catalog, inrp2p;
```

- **Owned by `inrp2p_boundary`**, so the privileges it runs with are the boundary role's, never the caller's.
- **`SET search_path = pg_catalog, inrp2p`** on every function, with `pg_catalog` **first**, so a caller cannot shadow a built-in with a function in a schema they control — the classic `SECURITY DEFINER` escalation.
- Trigger functions carry the same `SET search_path`.
- `state_transition`, `journal_catalogue` and `journal_component_contract` are owned by `inrp2p_owner` with **no** grants to any other role, so the closed catalogues cannot be extended at runtime to legalize a prohibited transition or relax a component contract.

### 9.4 Preventing caller-spoofed boundary context

The boundary identity is **not** a GUC. `SET LOCAL inrp2p.boundary = 'TB-MOVE'` is a statement any client may execute, so it identifies nothing.

Instead, the `SECURITY DEFINER` prologue writes `inrp2p.boundary_frame (txid, boundary_code, entered_at)`. This is un-forgeable because:

1. `INSERT` on `boundary_frame` is granted **only** to `inrp2p_boundary`, a role with no `LOGIN`. A caller cannot insert a frame directly.
2. `PRIMARY KEY (txid)` permits **one** frame per transaction, so a boundary cannot be re-declared mid-transaction, and two boundaries in one transaction collide (severity-1 `nested_boundary`).
3. Triggers read the frame with `SELECT boundary_code FROM inrp2p.boundary_frame WHERE txid = txid_current()`. **No frame ⇒ no boundary ⇒ the write is rejected**:

```sql
CREATE FUNCTION inrp2p.current_boundary() RETURNS inrp2p.boundary_code
LANGUAGE plpgsql STABLE
SET search_path = pg_catalog, inrp2p
AS $fn$
DECLARE v inrp2p.boundary_code;
BEGIN
  SELECT boundary_code INTO v FROM inrp2p.boundary_frame WHERE txid = txid_current();
  IF NOT FOUND THEN
    RAISE EXCEPTION 'money write attempted outside a boundary'
      USING ERRCODE = 'insufficient_privilege';
  END IF;
  RETURN v;
END;
$fn$;
```

`current_boundary()` is called by the write triggers on `journal_entry`, `posting` and `account_balance`. A direct `INSERT` into `posting` — even by a role that somehow held the privilege — fails, because no frame exists.

`boundary_frame` is `UNLOGGED` and keyed by `txid`, so it costs nothing at commit and needs no cleanup: rows are dropped on crash recovery and pruned by a periodic `DELETE` from `inrp2p_owner` for txids below `txid_snapshot_xmin`. This is the single place in the schema where deletion occurs, and it touches no money.

### 9.5 What CI still does, and what it no longer has to do

Grep-based CI remains useful as a **style** check — it flags a `now()` where `decision_time()` belongs, or a raw `INSERT INTO inrp2p.posting` in application code. It is **no longer load-bearing**: every rule it checks is independently enforced by privilege, constraint or trigger. `tests/security/privileges.spec.ts` connects **as `inrp2p_app`** and asserts that each prohibited operation fails, which is a test of the deployed database rather than of the source text.

## 10. Failed-boundary auditing

TS-01.4 requires a post-lock `decision_time()` in **both** winner and loser audit events [B2], while several conflicts require **no** financial or domain writes. v1.0 left these irreconcilable. They are reconciled by a single rule.

### 10.1 The non-raising boundary pattern

**An expected rejection MUST NOT raise.** Raising aborts the transaction and discards the audit row along with everything else; and an exception handler does not save it either, because an `EXCEPTION` clause opens a subtransaction that is rolled back to its savepoint, taking any audit write inside it with it.

So a boundary function **returns** its rejection:

```sql
CREATE FUNCTION inrp2p.reject(p_code TEXT) RETURNS inrp2p.boundary_result
LANGUAGE sql IMMUTABLE
SET search_path = pg_catalog, inrp2p
AS $rj$ SELECT ROW(FALSE, p_code, NULL::UUID, '{}'::jsonb)::inrp2p.boundary_result $rj$;
```

The rejection path:

1. performs **no** financial or domain mutation — structurally, because it is taken *before* any write, and `audit_event_rejected_no_entry` (§5.20) forbids a rejected audit row from referencing a journal entry;
2. **writes the audit row**, with `outcome = 'REJECTED'`, the deterministic `result_code`, `decision_time()` read at the position §7.4 specifies, and the observed `mode_version`;
3. writes the `command` completion row with `ok = FALSE`;
4. returns `(FALSE, code, NULL, '{}')`;
5. and the transaction **COMMITS**.

Committing a rejection is the point. The audit row survives because nothing rolled back. The caller maps `ok = FALSE` to an HTTP error; the *database* transaction succeeded in recording that the attempt was correctly refused.

**The loser of a race is audited exactly as thoroughly as the winner.** In 32-way `TB-MOVE` contention [F11], one transaction commits a deal and 31 commit `quote_already_consumed` audit rows — each with its own post-lock `decision_time()`, each proving the loser reached the guard rather than failing earlier.

### 10.2 What may still raise

| Situation | Behaviour |
|---|---|
| Expected rejection (guard failed, CAS zero rows, conflict code) | **Return** `(FALSE, code)`, commit the audit row |
| Constraint or trigger violation (a defect: unbalanced entry, missing allocation set, illegal transition) | **Raise.** The transaction aborts. This is not an expected outcome and must not be normalized |
| Serialization failure `40001`, deadlock `40P01` | **Raise.** The caller retries from the start of the boundary |
| Severity-1 condition detected inside the boundary | **Return** `(FALSE, severity1_code)` **and** record the incident, so both survive the commit (§10.4) |

### 10.3 Unexpected exceptions

When the transaction aborts, no in-transaction write survives — by definition. The incident is therefore recorded on two independent paths, neither of which is trusted alone:

1. **Non-transactional log.** Before propagating, the outermost handler emits a structured `RAISE LOG` with a fixed token:

   ```
   INRP2P-INCIDENT sev=1 code=<code> boundary=<code> txid=<n> subject=<kind>:<id>
   ```

   `RAISE LOG` writes to the server log and is **not** transactional, so it survives the rollback. A log-shipping reconciler parses the token and creates the `incident` row.

2. **Application retry on a fresh connection.** The caller catches the SQLSTATE and writes the incident in a **new** transaction on a **different** connection.

Path 2 is lost if the application process dies; path 1 is lost if log shipping is broken. Requiring both, and reconciling them, is the honest design: **neither path is claimed to be sufficient**, and `tests/reconciliation/residuals.spec.ts` asserts that an incident present in the log but absent from the table is itself surfaced as a reconciliation residual.

### 10.4 Severity-1 conditions

```sql
CREATE FUNCTION inrp2p.raise_incident(
  p_severity SMALLINT, p_code TEXT, p_subject_kind TEXT, p_subject_id TEXT)
RETURNS VOID
LANGUAGE plpgsql
SET search_path = pg_catalog, inrp2p
AS $fn$
BEGIN
  INSERT INTO inrp2p.incident (severity, code, boundary_code, detected_at,
                               subject_kind, subject_id, detail)
  VALUES (p_severity, p_code, inrp2p.current_boundary(), inrp2p.decision_time(),
          p_subject_kind, p_subject_id, '{}'::jsonb);
  RAISE LOG 'INRP2P-INCIDENT sev=% code=% boundary=% txid=% subject=%:%',
    p_severity, p_code, inrp2p.current_boundary(), txid_current(), p_subject_kind, p_subject_id;
END;
$fn$;
```

A severity-1 condition detected inside a boundary — `inconsistent_recognition_cycle`, `inconsistent_divergence_writeoff`, `inconsistent_recovery_snapshot`, `allocation_snapshot_conflict`, `sweep_reappearance_after_reversal`, `inconsistent_sweep_recognition`, an M22/M23 disagreement, an S1 breach, an FA-1 violation — calls `raise_incident` and then **returns** its rejection. Both the incident row and the audit row commit. **The money mutation does not happen; the record that it was refused does.**

This is the direct answer to the reconciliation the review demanded: expected rejection performs no prohibited mutation, records the required audit result, returns the deterministic error, and **does not accidentally roll back the audit row** — because nothing rolls back.

## 11. Ambiguity register (reclassified)

v1.0 raised eight "blocking ambiguities". Most were TS-02's own decisions being deferred back to the reviewer, and one attempted to reopen a settled TS-01.4 choice. **TS-01.4 choices are not reopened here.**

Each entry is classified by what it actually blocks:

| Class | Meaning |
|---|---|
| **Decided** | TS-02 makes the decision. Nothing is blocked |
| **Blocks schema** | Migration `0001` cannot be written until answered |
| **Blocks one boundary** | Exactly one boundary is unimplementable; the rest proceed |
| **Blocks TS-04** | Chain-layer work only |
| **Blocks production launch** | Implementation and testing proceed; go-live does not |

### 11.1 Disposition

| Ref | v1.0 framing | Correct classification | Disposition |
|---|---|---|---|
| **BA-1** | "How should the rank-0a lock be represented?" | **Not open.** TS-01.4 already specifies it | Use the **literal singleton row lock**: `SELECT mode, mode_version, free_buffer_minor, version FROM inrp2p.system_money_state WHERE id IS TRUE FOR SHARE` / `FOR UPDATE`. Not advisory, not table-level, not a GUC. `id BOOLEAN PRIMARY KEY CHECK (id IS TRUE)` makes a second row impossible (§5.2) |
| **BA-2** | "How are ledger accounts materialized?" | **Decided** — a TS-02 account-materialization decision | `account_id` is `uuid_v5` over the canonical account key (§3.2); `ensure_accounts()` inserts `ON CONFLICT DO NOTHING` and locks `ORDER BY account_id` (§7.2). Consistent with [L2] and canonical rank-9 ordering, with no read-then-write |
| **BA-3** | "How is M5 enforced without a subquery CHECK?" | **Decided** — a TS-02 database-enforcement decision | Row-local half as real `CHECK`s and domains; cross-row half as `DEFERRABLE INITIALLY DEFERRED` constraint triggers evaluated at commit under locks the boundary already holds (§6.5). The illegal subquery `CHECK` is removed |
| **BA-4** | "What is the canonical encoding?" | **Decided** — a TS-02 canonical-encoding decision | `CE` with exact bytes per type, declared field order, and `H = sha256` (§3.1). Applied to `term_digest`, `entry_key_digest`, `command_hash`, `cei_digest` and `account_id` |
| **BA-5** | Retention and archival periods | **External compliance input**, scoped to retention/archival only | **Remains open. Blocks production launch only.** No table is deletable (`DELETE` revoked from every role, §9.2); archival is by partition detach. The *mechanism* is specified; only the *durations* await a compliance decision. Schema, boundaries and tests are unaffected |
| **BA-6** | Shard count `K` | **Decided** — a deployment parameter with a versioned policy | `partition_policy` (§5.20) is versioned and forward-only. `shard_count` applies to accounts materialized at or after `effective_from`; **existing accounts are never re-sharded and history is never rewritten**; reporting sums all shards across all policy versions [§2.3] |
| **BA-7** | TRON finality depth / PNI window | **Belongs to TS-04** | Moved to TS-04 chain configuration. It **must not block persistence work**: the schema stores `pni_deadline_at` and the attempt state machine without knowing the window, and every boundary except `TB-WITHDRAW-EXPIRE-PROVE` is fully implementable and testable with a configured test value |
| **BA-8** | Operator thresholds (buffer floors, gas floor, capacity defaults) | **Decided** — an operator configuration input | `operator_config` (§5.20) is versioned and append-only. TS-02 defines the representation and requires a row to exist; it **does not invent the value**. A boundary reading an absent key fails `config_absent` with a severity-2 incident |

### 11.2 What actually remains open

**One** item: **BA-5**, retention and archival durations — an external compliance input that blocks production launch and nothing else.

It does not block:

- the schema (no table is deletable in any case);
- any of the 47 boundaries;
- the F1–F321 suite;
- the K-R harness;
- TS-03 or the frontend.

**BA-7** is open but is TS-04's, and blocks only `TB-WITHDRAW-EXPIRE-PROVE`'s production configuration, not its implementation or its tests.

No other blocking ambiguity is retained. The remaining six were TS-02's own decisions and are decided above.
