# INRP2P — TS-01.4: Money Contract, Ledger, Concurrency and Outbox

**Consolidated Normative Specification**

## 0. Status, authority, scope and conformance

### 0.1 Status

TS-01.4 is the **consolidated normative specification** for the INRP2P money contract, ledger, finality, reorg, receivable, withdrawal, recovery, concurrency and outbox system.

It **supersedes in full**: TS-01, TS-01.1, TS-01.2, TS-01.3, TS-01.3A, TS-01.3A-E1, TS-01.3A-E2, TS-01.3A-E2A, TS-01.3A-E2A-E1, TS-01.3A-E2A-E1A, TS-01.3A-E2A-E1B and TS-01.3A-E2A-E1C.

TS-01.4 **changes no approved behavior**. It is an editorial and formal consolidation of the effective contract established by those documents, resolved under the precedence order they define. It is the **sole implementation source of truth** for its scope: an implementer requires no earlier TS-01 document or errata.

TS-01.4 **inherits Product Operating Model v1.2.2 (with its approved Errata E-1…E-6) without reinterpreting it**. Where this document references a product rule, it restates the inherited baseline; it does not amend it.

### 0.2 Scope

**In scope:** money contract and amount identities; double-entry ledger; accounts and ownership; per-asset balancing; solvency and `FreeBuffer`; risk modes and admission gates; quote, link, allocation, deal, reserve and dispute boundaries; wallet topology and finalized-chain delta recognition; deposits, sweeps, gas, capital funding, withdrawals; reorg, derecognition, reinstatement and repeatable recognition cycles; canonical event identity and object-bound evidence; receivable types, controls, allocations and lineage conservation; cures, write-offs, reinstatement, invalidation; withdrawal divergence loss and recovery; journal selection; lock hierarchy and transaction boundaries; CAS guards and uniqueness constraints; exactly-once behavior and idempotent replay; outbox atomicity and delivery; deterministic concurrency outcomes; standing invariants and severity-1 conditions; the complete acceptance suite F1–F321.

**Out of scope:** UI/UX design; legal analysis; roadmap; schema or ORM implementation; application code; vendor selection; new product features; any change to Product Operating Model v1.2.2.

### 0.3 Conformance

**MUST / MUST NOT / SHALL** are binding. An implementation that disagrees with any normative statement here is non-conforming. Where a rule states a rejection code, that exact code is part of the contract.

## 1. Definitions, notation and amount identities

### 1.1 Postings and journal entries

A **posting** is `⟨account, asset, amount⟩`, where `amount` is a **signed exact integer in the asset's smallest unit** (USDT 6 dp, TRX 6 dp). Floating-point representation MUST NOT appear in any layer that produces or validates postings.

- **Debit = positive. Credit = negative.** No other sign convention exists in this system.
- A **journal entry** is an ordered set of postings written atomically together with `entry_key`, `boundary`, `solvency_class` and `audit_ref`.
- **A posting whose amount is zero is omitted.** Omission never affects a per-asset balance proof, which is stated over the non-zero postings actually written.

| Class | Prefix | Natural balance | A debit means |
|---|---|---|---|
| Asset | `A.` | ≥ 0 | the platform controls more |
| Liability | `L.` | ≤ 0 | the platform owes less |
| Revenue | `R.*_revenue` | ≤ 0 | revenue reversed |
| Expense | `R.*_expense` | ≥ 0 | expense increased |
| Equity | `E.` | ≤ 0 | capital reduced |

### 1.2 Versions, CAS and isolation

Every mutable aggregate carries a `version` integer, incremented on every mutation. `CAS(row, version[, state])` is a guarded update requiring **exactly one** affected row; zero rows aborts the boundary with a deterministic conflict code. **No read-then-write.**

All money boundaries are correct at `READ COMMITTED` using explicit row locks and CAS. Correctness MUST NOT depend on a higher isolation level, and running at a higher level MUST NOT change outcomes.

### 1.3 `decision_time()`

> **`decision_time()`** ≔ a database **server wall-clock** value read **after** the boundary's controlling row lock is held, using a clock function that **advances within an open transaction**.

It MUST NOT be a transaction-start timestamp, MUST NOT come from a statement that began before lock acquisition, and MUST NOT originate from a client.

- **T1** Lock acquisition and the `decision_time()` read are separate statements; the read is strictly after the lock is granted.
- **T2** One value per boundary, bound into every temporal guard and recorded in the audit event of winners and losers.
- **T3** For any expiring object the *use* guard is `expires_at > :decision_time` and the *expire* guard is `expires_at <= :decision_time`, both evaluated under the same exclusive lock on the same row.
- **T4** If `expires_at` elapses during a lock wait, the post-lock read makes the use guard false and the boundary fails deterministically. Wall-clock time is non-decreasing, so a boundary that fails this guard can never later succeed.

### 1.4 Finality

**R-FINAL.** All chain recognition and derecognition occurs **at network finality only** (TRON: inclusion in a solidified/irreversible block). The ledger never recognizes non-final chain state.

**FA-1 (finality assumption).** Solidified blocks and the execution results they contain are **protocol-final**: an execution result observed in a solidified block does not change. All guarantees expressed as **M14** hold **under FA-1**. An observed divergence from FA-1 is not a modelled state transition but an **external-assumption failure**, handled per §10.6 and §12.5: the financial-truth journal commits, the affected object is frozen, and no automatic replacement or release is authorized.

### 1.5 Amount identities

| Identity | Meaning |
|---|---|
| `G = P + W` | Withdrawal gross = on-chain payout + INRP2P withdrawal processing charge |
| `a₁ + a₂ + a₃ = D` | Reinstatement split: receivable settled + write-off recovered + party remainder = deposit |
| `a₁ = ρ`, `a₂ = ω` | Reinstatement always fully settles the lineage (proof §11.6) |
| `U + Q = C` | Compensation = reserve-funded + unfunded remainder |
| `U = min(C, E_effective, reserve_ledger_balance)` | Mandatory reserve funding |
| `consumed + released = E_effective` | Encumbrance settlement is exhaustive |
| `O + H + Z = Σ booked K ≤ P` | Divergence recovery aggregates bounded by the loss |
| `ρ + κ + ω + σ_r + σ_w + ι_r + ι_c + ι_w = Δ₀` | **Extended lineage conservation identity (M23)** |
| `X + f` | Quote reservation = principal + platform fee (fee reserved only when the desk is crypto-side) |

### 1.6 Symbol table

`X` principal · `f` platform fee · `D` deposit · `B` clawable balance · `Δ₀` original deficit · `ρ` open receivable · `κ` cured by party · `ω` written off · `σ_r` receivable settled by reinstatement · `σ_w` write-off recovered by reinstatement · `ι_r/ι_c/ι_w` invalidation components · `R` cure deposit · `c` cure allocation to one lineage · `G` withdrawal gross · `P` on-chain payout · `W` processing charge · `S` sweep · `g` TRX spent · `r` reserve · `b` capital funding · `C` approved compensation · `E_effective` encumbrance value · `U` reserve-funded compensation · `Q` unfunded remainder · `K` recovery booking · `Z` write-off amount · `O/H/Z` divergence aggregates · `a₁/a₂/a₃` reinstatement split · `B′` post-reinstatement clawback.

### 1.7 Solvency-class taxonomy

Every journal carries an immutable `solvency_class`. **The closed-catalogue static check rejects any journal without a class**, so future journals cannot bypass the risk gate.

| Class | Definition | Gate requirement |
|---|---|---|
| **SDJ** | May reduce `FreeBuffer` | Boundary **MUST** acquire `EXCLUSIVE(system_money_state)` at rank 0a before all other locks, recompute `FreeBuffer` and write the resulting mode in the same transaction |
| **SNJ** | Cannot change `FreeBuffer` | `SHARE` suffices |
| **SIJ** | Cannot reduce `FreeBuffer` | May take `EXCLUSIVE` to recompute and downgrade the mode; **required** where a routing decision depends on the recomputed mode |

**SD-1.** A boundary MUST acquire `EXCLUSIVE` if **any** journal it may post is SDJ. Because a checker ruling may post JX2 or JXS, **TB-APPROVE always acquires EXCLUSIVE** — an accepted global serialization of operator rulings, which are low-frequency human-initiated events.

**SD-2 (financial truth precedes policy).** If an SDJ causes S1 to fail, **the journal still commits** and the transaction writes `EMERGENCY` in the same commit. Refusing to post would leave the ledger asserting value that does not exist or denying an obligation that does. This applies to JD-R1, JD-R2, JD-REe-R, JW-R1, JW-DL, JBF1-R, JG1-R and to JX2/JXS: once a ruling establishes an obligation to a user, recording it is financial truth. The checker interface shows projected `FreeBuffer` before approval; proceeding is an audited operator decision.

### 2.2 TRX

| Account | Class | Purpose |
|---|---|---|
| `A.trx.wallet.gas` | Asset | Operational TRX; increases only via chain-backed JG1 / JG1-RE or via JG2b unstaking |
| `A.trx.staked` | Asset | TRX staked for energy/bandwidth |
| `R.trx.gas_expense[shard]` | Expense | TRX actually burned or spent (JGX) |
| `E.trx.platform_capital` | Equity | Net-new TRX capital |

**Energy.** Resources drawn from staked TRX are not spent TRX and produce **no posting**; consumption is an operational metric. Staking and unstaking move value between `A.trx.wallet.gas` and `A.trx.staked` (JG2a / JG2b). Only TRX actually debited on-chain posts to `R.trx.gas_expense`.

### 2.3 Hot-account sharding

Accounts with unbounded write concurrency and no balance constraint — `R.usdt.fee_revenue`, `R.usdt.withdrawal_fee_revenue`, `R.usdt.platform_compensation_expense`, `R.usdt.reorg_loss_expense`, `R.usdt.divergence_loss_expense`, `R.trx.gas_expense` — are partitioned into **K shards**, each a distinct account row with its own `account_id`, selected deterministically (`shard = hash(object_id) mod K`). Sharding preserves lock ordering; reporting sums shards.

### 2.4 Monetary vs allocation objects

| Kind | Examples | Representation |
|---|---|---|
| **Monetary** | USDT and TRX quantities | Ledger accounts and journal entries |
| **Allocation (non-monetary)** | desk payout capacity (INR), desk intake capacity (INR), desk exposure (USDT-valued limit), reserve encumbrance | Versioned rows and scoped records. **Never posted to the ledger** — the platform holds no INR, and a limit is not value |

## 3. Standing invariants

### 3.1 Money invariants M1–M24

| # | Invariant |
|---|---|
| **M1** | Every journal entry balances **per asset**: ∀ asset `a`, Σ amounts in `a` = 0. Enforced by the ledger engine at write |
| **M2** | Global trial balance per asset = 0 at every commit |
| **M3** | No cross-asset netting; a multi-asset entry balances each asset independently |
| **M4** | Value occupies exactly one account at any instant; movements are account→account |
| **M5** | Liability accounts never hold a debit balance; asset accounts never hold a credit balance. **Every `A.usdt.receivable.*[party]` is debit-normal and MUST NEVER become negative** — every crediting posting is capped at the open balance under that account's rank-9 lock |
| **M6** | Chain recognition and derecognition post **only at finality** (R-FINAL). Observed, broadcast and included-but-not-final states are operational records, never entries |
| **M7** | Value transfers **between parties** occur only via **JC1, JC2, JX1, JX2, JXS** |
| **M8** | Escrow, quote-reservation, fee-reservation, hold and withdrawal-payable accounts have balance 0 in their owning object's terminal state |
| **M9** | The ledger is append-only; corrections are reversing entries with their own `entry_key`. No posting is updated or deleted |
| **M10** | *(Withdrawn.)* The former custodial-solvency invariant is replaced by the monitored solvency conditions **S1/S2** of §6. An unbacked receivable does not preserve custodial solvency; it consumes buffer. Identifier retained and reserved for traceability |
| **M11** | Per-asset quantity accounting is separate from functional-currency valuation; postings carry quantities only. The posting schema admits no valuation field |
| **M12** | Quote-derived deal terms are **byte-identical** to the consumed quote's term set: `{quoted rate, You Send, You Receive, platform fee, pricing source id, pricing snapshot value, pricing observed-at, expires_at}`. The copied `expires_at` is provenance, not a deal timer |
| **M12′** | Funded-link-derived deal terms are **byte-identical** to the link's term set: `{fixed rate, You Send, You Receive, platform fee, fee-payer designation, link expires_at, desk counterparty id, directional pool}`. No Pricing Service value participates |
| **M13** | No timer transfers value **between parties**. A timer may release a party's own reservation to that same party (JQ3, JF3a, JF3b) |
| **M14** | **Under FA-1**, per withdrawal request at most one chain transaction may ever pay it; net payout recognition ∈ {0, G}. An FA-1 violation is an incident (§10.6), not a modelled outcome |
| **M15** | Every temporal admission guard uses a post-lock `decision_time()` (T1–T4) |
| **M16** | Every admission-dependent boundary holds `system_money_state` in `SHARE` for its whole transaction and validates the mode inside it; **every boundary that may post an SDJ holds it `EXCLUSIVE`** and writes the recomputed mode in the same transaction |
| **M17** | **Net-new platform capital** — any posting to `E.usdt.platform_capital` or `E.trx.platform_capital` — is recognized **only** by the closed capital-funding families of §9.4, each bound to a `capital_funding` object with a unique `funding_key = (network, asset, txid, event_index)`. Wallet-asset increases arising from deposits, sweeps, sweep reversals, reinstatements, unstaking or reorg corrections are legitimate under their own chain objects and journals and **do not** reference a capital-funding event |
| **M18** | Value in `L.usdt.hold[case]` reaches spendable balance only via **JD3** or **JD3e**; reinstatement of a held transfer returns to the same hold |
| **M19** | Only bytes committed to a `withdrawal_attempt` row are ever broadcast; the same attempt's bytes are the only bytes retried; replacement bytes commit before their broadcast becomes relay-visible |
| **M20** | **No party is ever over-credited.** Cumulative party credit from a reinstatement cycle is exactly `a₃`, and `a₃` reaches spendable balance only via JD-RE (mode admits) or JD3e (explicit ruling). For any lineage, cumulative party credit ≤ `B + κ` |
| **M21** | A Terminal Non-Payment proof and a finality proof, once recorded, are **immutable and retained for audit**. Under FA-1 no ordinary transition leaves `EXPIRED_PNI`, `FINAL_FAILED` or `DIVERGED`. **A finalized-success observation MAY transition a prior TNP or `DIVERGED` attempt to `DIVERGED_PAID`**, in TB-WITHDRAW-FINALIZED-SUCCESS only, with the original proof preserved. This transition never authorizes replacement or release. Supersession is an attribute, not a state |
| **M22** | For every party `p` and receivable type `t`: `balance(A.usdt.receivable.t[p]) = Σ ρ over **all** lineages of (p, t), irrespective of disposition`. **Every posting to any receivable account carries a complete `receivable_allocation` set** naming `(receivable_type, source_object_id, source_seq, amount, entry_key)` and summing exactly to that posting; a posting without a complete set is rejected at write |
| **M23** | **Extended lineage conservation identity**, holding in every lineage state, open or terminal: `ρ + κ + ω + σ_r + σ_w + ι_r + ι_c + ι_w = Δ₀`. For `divergence` and `desk_shortfall` lineages `σ_r = σ_w = 0` |
| **M24** | Every reinstatement satisfies `a₁ = ρ`, `a₂ = ω`, `a₁ + a₂ + a₃ = D`, and performs `CAS(reinstatement_disposition: PENDING → SETTLED_REINSTATED, version)` **exactly once** |

**Lemma L-E2 (M22 filter equivalence).** For any lineage, `ρ` is only ever decreased — by cure (`−c`), write-off (`−K`), reinstatement (`−a₁`) or invalidation (`→ ι_r`) — and is never increased after opening; a subsequent reversal opens a **new** lineage rather than reopening an existing one. `receivable_disposition` leaves `OPEN` only on the transition where `ρ` reaches 0; `SETTLED_REINSTATED` sets `ρ := 0`; `REVERSED_INVALIDATED` moves `ρ` into `ι_r`. Therefore terminal, reinstated and invalidated lineages contribute 0, and the unfiltered sum equals any disposition-filtered sum. The **unfiltered** form is normative because it cannot exclude a non-zero `ρ` under any future disposition rule.

### 3.2 Allocation invariants C1–C8

| # | Invariant |
|---|---|
| **C1** | Allocated capacity/exposure is never negative and never exceeds the desk's configured pool limit |
| **C2** | Each allocation record is released **exactly once** — by quote expiry, link close, or terminal deal outcome — via `CAS(record: ACTIVE→RELEASED, version)` plus `UNIQUE(allocation_release.allocation_record_id)` |
| **C3** | Re-key (quote→deal, link→deal) transfers ownership inside one boundary; no unowned interval exists |
| **C4** | `payout` and `intake` are disjoint pools; a boundary allocates only from the pool matching the deal direction |
| **C5** | Exposure counts active quote reservations, active funded links and non-terminal deals |
| **C6** | Every boundary writing a terminal deal state releases that deal's allocation records in the same transaction. A terminal deal with an `ACTIVE` record is a detected violation |
| **C7** | One encumbrance per case (`UNIQUE(encumbrance.case_id)`), created as `min(case_compensation_cap, available_for_return)` under `X(desk_reserve_control)`, where `available_for_return = reserve_ledger_balance − Σ open_encumbrances`. **`Σ open_encumbrances ≤ reserve_ledger_balance` at all times.** Compensation reduces the reserve balance and its encumbrance atomically; each encumbrance is released exactly once |
| **C8** | **A resolved case MUST NOT retain an `OPEN` encumbrance row, whatever its balance — including a zero-valued row.** The checker predicate is presence-and-state based |

### 3.3 Product invariant inherited normatively

**I-11 (hold ≠ repricing).** A hold placed after fiat payment is documented and notified; it MUST NOT alter the deal's economic term set, silently re-quote, or retroactively void the deal. Enforced here by: JH1/JH2 touch only `L.usdt.escrow[deal]` ↔ `L.usdt.hold[case]`, and no boundary has a write path to deal term columns (M12, M12′).

## 4. Global lock hierarchy and transaction rules

### 4.1 Canonical lock order

Locks are acquired in strictly non-decreasing rank; within a rank, ascending primary key. **No boundary and no journal may acquire a lower rank after a higher one.**

| Rank | Object | Modes |
|---|---|---|
| **0a** | `system_money_state` (singleton risk gate) | `SHARE` (admission) / `EXCLUSIVE` (SDJ or mode recompute) |
| **0b** | `writeoff_command[writeoff_command_id]` (per-command mutex) | `M` (exclusive) |
| 1 | `deal` | X |
| 2 | `case` | X |
| 3 | `desk_reserve_control[desk]` | X |
| 4 | `quote` | X |
| 5 | `link` | X |
| 6 | `withdrawal_request`, then `withdrawal_attempt` | X |
| 7 | `desk_allocation` (`payout`, `intake`, `exposure` in that sub-order) | X |
| 8 | `chain_object` — `deposit_transfer` (`credit_key`), `sweep` (`txid`), `chain_op` (`network, txid`), `capital_funding` (`funding_key`) | X |
| **8a1** | `party_receivable_control[party, receivable_type]` | X |
| **8a2** | `divergence_recovery_control[loss_entry_key]` | X |
| **8b** | `reversal_lineage` (`receivable_type`, `source_object_id`, `source_seq`) | X |
| **9** | **Ledger accounts — every account the boundary posts to**, ascending `account_id`, regardless of class | X |

### 4.2 Locking rules

- **L1** No Tier-A lock (ranks 0a–8b) is acquired after any rank-9 ledger-account lock.
- **L2** Rows inserted inside the boundary are unreachable by concurrent transactions before commit and are exempt from ordering.
- **L3** Hot revenue/expense accounts are shard-partitioned (§2.3), each shard a distinct lockable row participating in the rank-9 ordering.
- **L4** Deadlock freedom follows from one total order (rank, then primary key) plus L2.
- **L5** **Lock acquisition order (canonical) and journal application order (reverse dependency) are distinct and MUST NOT be substituted for one another.** Both are asserted separately in tests.
- **L6** **No 8a2 row may be acquired after an 8b lineage.**
- **L7** **Rank 7 (`desk_allocation`) is never acquired after rank 8, 8a1, 8a2 or 8b.** A boundary that touches both allocations and receivable lineages acquires rank 7 first.

### 4.3 Boundary rules

- **B1** No boundary performs a network call.
- **B2** Every boundary writes its audit event(s) inside the same commit, including `decision_time()`, the observed risk-mode version, and for SDJ boundaries the pre- and post-`FreeBuffer`.
- **B3** No boundary broadcasts; broadcast occurs only via outbox consumption (§14).

### 5.3 Uniqueness constraints and deterministic collision outcomes

| Constraint | Collision outcome |
|---|---|
| `UNIQUE(journal_entry.entry_key)` | **Consistent idempotent return** — the master ledger guard; no catalogue journal can be double-posted |
| `UNIQUE(network, token_contract, txid, log_index)` on deposit transfers | `already_recognized` — idempotent no-op |
| `UNIQUE(network, txid)` on `sweep` | **State-sensitive; the constraint MUST NOT decide the outcome by itself.** The colliding observation first **resolves the existing sweep object and acquires `X(sweep)`**, then branches on its **locked state**: `RECOGNIZED` **and** the observation is consistent with the recorded initial recognition (same finalized inclusion, same `S`, same wallets) → **idempotent return `already_recognized`**, nothing posted. `REVERSED` → **`sweep_reappearance_after_reversal`**: **do not** return `already_recognized`; **post no journal** (neither JS1 nor any other); **do not change `rseq` or state**; **raise the severity-1 finalized-reappearance incident required by R-CYC-2**. `RECOGNIZED` **and** the observation is inconsistent with the recorded recognition → severity-1 `inconsistent_sweep_recognition`; abort with no writes |
| `UNIQUE(network, txid)` on `chain_op` | `already_recognized` — idempotent no-op |
| `UNIQUE(network, asset, txid, event_index)` on capital fundings | `already_recognized`; also prevents one canonical chain event funding more than one `capital_funding` object |
| `UNIQUE(chain_object_id, recognition_seq)` | One recognition per cycle; duplicate → idempotent |
| `UNIQUE(object_key, evidence_key)` | **`recognition_evidence_reused`** — rejection, never idempotent return |
| `UNIQUE(withdrawal_recognition_record.attempt_id, recognition_seq)` | Consistent committed cycle → **idempotent return**; inconsistent → **severity-1 `inconsistent_recognition_cycle`** |
| `UNIQUE(withdrawal_recognition_record.attempt_id, evidence_key)` | Existing record belongs to another sequence → **reject `recognition_evidence_reused`** |
| `UNIQUE(deals.quote_id)` | `quote_already_consumed` — optimistic-concurrency rejection |
| `UNIQUE(deals.link_id) WHERE link_type='funded'` | `link_consumed` — rejection |
| `UNIQUE(utr)` platform-wide | Rejection; a reused UTR is a fraud signal |
| `UNIQUE(allocation_release.allocation_record_id)` | `allocation_already_released` — idempotent no-op |
| `UNIQUE(allocation_record.scope_type, scope_id, desk_id, pool)` | One record per scope per pool |
| `UNIQUE(encumbrance.case_id)` | Resolution by `case_id` then state branch (§7.6) |
| `UNIQUE(encumbrance_settlement.encumbrance_id)` | Same ruling → **idempotent return**; different ruling → **`encumbrance_already_settled`** |
| `UNIQUE(hold_release.case_id, deposit_transfer_id, rseq)` | Idempotent return of the committed release |
| `UNIQUE(withdrawal_attempt.request_id) WHERE state IN ('PREPARED','BROADCAST','INCLUDED_NONFINAL','FINAL_PAID')` | `open_attempt_exists` — rejection (W1) |
| `UNIQUE(withdrawal_attempt.txid)` | Rejection; no two attempts share a txid |
| `UNIQUE(approval.proposal_id)` + `CHECK(approver_id <> proposer_id)` | Rejection; one approval per proposal, maker ≠ checker |
| `UNIQUE(proposal.case_id) WHERE status='PENDING'` | `proposal_exists` — rejection |
| `UNIQUE(evidence.case_id, content_digest)` | Duplicate evidence not inserted; sequence not incremented |
| `UNIQUE(divergence_recovery_booking.loss_entry_key, approval_provenance)` | **Idempotent return** of the original `booking_seq`, journal and lineage; `sum_booked` unchanged |
| `UNIQUE(divergence_writeoff.writeoff_command_id)` | Consistent set → **idempotent return**; altered fields → **`approval_command_mismatch`**; partial set → **severity-1 `inconsistent_divergence_writeoff`** |
| `UNIQUE(divergence_writeoff.lineage_key, approval_provenance, approval_line_id)` | Defence-in-depth only; never the primary guard |
| `UNIQUE(lineage_invalidation.lineage_key, loss_entry_key)` | One invalidation record per lineage per loss; duplicate → idempotent |
| `UNIQUE(receivable_allocation.entry_key, receivable_type, source_object_id, source_seq)` | Duplicate allocation row → idempotent; a missing set → rejection at write (M22) |
| `UNIQUE(outbox.event_key)` | One record per logical effect; duplicate delivery is a consumer no-op |

**R-U1.** **A journal alone never proves a complete committed result** where an immutable control or recognition record is also required. Every such compound result is inspected as a set (§10.6, §11.9).

### 5.4 Command idempotency

Every state-changing command carries a client `idempotency_key`; the store maps `(actor_id, command_type, idempotency_key) → result` under a unique constraint. A replay returns the stored result without re-execution. Keys are scoped per actor; cross-actor collision is impossible.

## 6. Risk modes, admission and `FreeBuffer`

### 6.1 Solvency terms

```
Obligations      = −Σ( L.*.balance, L.*.reserve, L.*.escrow[*], L.*.quote_reserved[*],
                       L.*.fee_reserved[*], L.*.hold[*], L.*.withdrawal_payable[*] )
ControlledAssets =  Σ A.usdt.wallet.*        (buffer included; receivables excluded)
FreeBuffer       =  ControlledAssets − Obligations
```
`RequiredBuffer` is operator-configured.
**S1:** `FreeBuffer ≥ 0` · **S2:** `FreeBuffer ≥ RequiredBuffer`.

S1/S2 are **USDT** solvency conditions (the platform owes customers no TRX). TRX is governed by a separate **operational gas floor** whose breach raises an operational alarm and pauses non-essential broadcasts; it is not a solvency condition.

### 6.2 Modes and the paused set

| Mode | Condition | Admission effect |
|---|---|---|
| `NORMAL` | S2 holds | All boundaries admit |
| `THIN` | S1 holds, S2 fails | **Paused:** TB-WITHDRAW-REQUEST, TB-WITHDRAW-SIGN, TB-WITHDRAW-REPLACE, TB-QUOTE-ISSUE, TB-MOVE, TB-LINK-CREATE, TB-LINK-JOIN, TB-RESERVE (JB2) |
| `EMERGENCY` | S1 fails | As THIN, **plus** deposits and reinstatement remainders route to hold (JD2, JD-C1e, JD-REe); **JD-C2a/JD-C2b prohibited** |

**Always open in every mode:** TB-COMPLETE, TB-CANCEL, TB-APPROVE, TB-HOLD, TB-HOLD-RESOLVE, TB-LATE-CLAIM, TB-EVIDENCE-INSERT, TB-DISPUTE-OPEN, TB-FAULT-CASE-OPEN, TB-WITHDRAW-FINALIZED-SUCCESS, TB-WITHDRAW-FAIL-PROVE, TB-WITHDRAW-EXPIRE-PROVE, TB-WITHDRAW-RELEASE, TB-REORG-REVERSE, TB-REORG-REINSTATE, TB-REORG-WRITEOFF, TB-DIVERGENCE-LOSS-REVERSE, TB-GAS-RECOGNIZE, TB-CAPITAL-RECOGNIZE, TB-SUSPEND.

### 6.3 Risk-gate serialization

- **A-lock:** every admission-dependent boundary acquires `SHARE(system_money_state)` at rank 0a **before any other lock** and holds it until commit; it reads `mode` and `version` under that lock and aborts with **`mode_not_admitting`** if the mode forbids it. The observed `version` is recorded in the audit event.
- **M-lock:** every SDJ-posting or mode-changing boundary acquires `EXCLUSIVE(system_money_state)` at rank 0a and writes the new mode **in the same transaction as its journals**.

**Theorem (no stale admission).** No admission-dependent boundary can commit using a mode superseded by an already-committed SDJ or mode-change boundary.
*Proof.* Let `A` be admission-dependent (holds SHARE from before any other lock until commit) and `M` be any SDJ or mode-change boundary (holds EXCLUSIVE on the same row). SHARE and EXCLUSIVE on one row are mutually exclusive, so their holding intervals are disjoint. Case 1: `A` acquires first — `M` blocks until `A` finishes; `A` decided and committed while the pre-change mode was the committed state, a legal serialization `A ≺ M`. Case 2: `M` acquires first — `A` blocks until `M` commits, then reads the new mode under SHARE and aborts if it forbids admission. No interleaving exists in which `A` reads the old mode and commits after `M` commits, since that requires `A` to hold SHARE across `M`'s EXCLUSIVE interval. The mode read and the commit both lie inside `A`'s SHARE interval, so admission and commit are atomic with respect to every SDJ. ∎
*Corollary.* Because SD-1 covers **every** SDJ (including future ones, via the mandatory classification), the theorem is closed under catalogue extension.

## 7. Quotes, links, allocations, deals and disputes

### 7.1 Quotes

Terms are written once at issuance; **no write path exists to term columns**. Validity is evaluated only under `X(quote)` using post-lock `decision_time()` (T1–T4). The expiry worker is **cleanup only**: if it never runs, nothing expired is consumable; if it runs late, it can neither revive nor invalidate a decided quote. The full acceptance suite MUST pass with the expiry worker disabled.

`f* = f` when the desk is the crypto-side party (INR→USDT); `f* = 0` when the user is the crypto-side party (the fee is taken from escrow proceeds at completion). **`f` is fixed at JQ1 in both directions.**

### 7.2 Links

**Offer Link — normative status.** A reusable Offer Link is **non-funded**: it reserves **no money, no capacity and no exposure**, has no escrow account and posts no journal. Opening one routes the participant into the ordinary lifecycle — fresh firm quote (where all reservation occurs) then MOVE. Only **Funded Deal Links** reserve.

**Funded Deal Link allocation contract.** A published funded link names its desk counterparty and direction, hence its pool: desk supplies USDT (user pays INR) → **intake** capacity + exposure; desk pays INR (user supplies USDT) → **payout** capacity + exposure. Allocations are reserved at creation, re-keyed at Join, released exactly once at close.

**Close guards.** Under `X(link)` then post-lock `decision_time()`: **revocation** requires the actor to be the creator or an explicitly authorized operator; **expiry** requires `expires_at <= :decision_time`; **Join** requires `expires_at > :decision_time`. Join, revocation and expiry are one CAS race on `link.status`.

### 7.3 Allocations

Deal-scoped allocation records are `ACTIVE` from re-key until a terminal deal state. Release is `CAS(allocation_record: ACTIVE→RELEASED, version)` plus insertion into `allocation_release` under its unique constraint, performed inside **TB-COMPLETE, TB-CANCEL or TB-APPROVE (branch A) — the same transaction as the terminal journal**. A standing checker asserts: no terminal deal has an `ACTIVE` allocation record, and no allocation record has two release rows.

Link-scoped allocation records are `ACTIVE` from TB-LINK-CREATE, re-keyed to deal scope at TB-LINK-JOIN (ownership transfer, no release), released exactly once at TB-LINK-CLOSE.

### 7.4 Deal terms

M12 (quote-derived) and M12′ (link-derived) are asserted **inside** TB-MOVE and TB-LINK-JOIN respectively and by a standing sweep over all deals. Any divergence raises severity-1.

### 7.5 Disputes and resolution sequencing

`case_evidence_seq` increments **only** for evidence that is (a) **admissible** — from a recognized evidence tier or accepted artifact type; (b) **non-duplicate** — distinct `content_digest`, and for claims a distinct UTR; (c) **case-relevant** — bearing on the question under review; and (d) **within the open evidence window**.

TB-LATE-CLAIM, TB-EVIDENCE-INSERT and TB-APPROVE all take `X(deal)` then `X(case)` and read/mutate `case.version`, so they serialize. TB-PROPOSE snapshots `deal_version_at_proposal` and `evidence_seq_at_proposal` and **posts no journal**. TB-APPROVE commits only if both snapshots still match.

**Atomic bundle.** TB-LATE-CLAIM and TB-EVIDENCE-INSERT perform an identical atomic bundle: validate, insert, increment `case_evidence_seq`, invalidate any pending proposal, and return the deal from `RESOLUTION_PENDING` to `FIAT_REVIEW`.

**Termination.** Inadmissible, duplicate, irrelevant and post-window submissions are recorded and audited but do not increment the sequence; once the window closes the sequence is frozen. Admissible-distinct evidence is finite and rate-limited, so proposal invalidation is finite.

**Post-approval material.** Material arriving after a committed approval creates a `RECOVERY` incident referencing the resolved deal, **posts no journal**, and never auto-reverses money; restitution requires a fresh maker-checker ruling.

### 7.6 Reserve encumbrance and compensation disposition

`desk_reserve_control[desk]` (rank 3) holds `{reserve_balance_ref, Σ open_encumbrances, version}`.

**Encumbrance creation.** On TB-DISPUTE-OPEN (when desk-fault-eligible) or TB-FAULT-CASE-OPEN, under `X(desk_reserve_control[d])`:
`enc = min(case_compensation_cap, available_for_return)` where `available_for_return = reserve_ledger_balance − Σ open_encumbrances`, with `UNIQUE(encumbrance.case_id)`. A **zero encumbrance is legal** and means the case is uncollateralized. **Reserve becomes unavailable for return from the moment the encumbrance exists.**

**State-complete lookup (TB-APPROVE branch A).** Under `X(desk_reserve_control[d])`, resolve **the unique encumbrance row by `case_id` alone**, then branch on state:

| Resolved row | `E_effective` | Settlement |
|---|---|---|
| **No row** | `0` | **No-op**: no CAS, no settlement record, no error |
| **`OPEN` row** | **`row.balance`** (may be `0`) | `CAS(OPEN→SETTLED, version)` **exactly once**, recording `consumed = U`, `released = E_effective − U` |
| **`SETTLED` row** | *not recomputed* | **Never treated as absent.** Same `ruling_id` as the committed settlement → **return the committed result idempotently**; different `ruling_id` → reject **`encumbrance_already_settled`** |

**Disposition rule.** In one TB-APPROVE (branch A) transaction, atomically and in this order:
1. `U = min(C, E_effective, reserve_ledger_balance)`; `Q = C − U`.
2. If `U > 0`: post **JX1** for `U`.
3. If `Q > 0`: post **exactly one** of **JX2** or **JXS** for `Q`, per the ruling's immutable `remainder_path ∈ {PLATFORM, DESK}`. Posting both, or neither while `Q > 0`, is rejected by the catalogue check.
4. Consume `U` from the encumbrance; release `E_free = E_effective − U`.
5. Transition the encumbrance `OPEN → SETTLED` exactly once.

**Mandatory reserve funding.** The ruling has **no discretion over `U`**; `remainder_path` governs only `Q`. Guard: `E_effective > 0 ∧ C > 0 ∧ ¬JX1 ⟹ reject **`reserve_must_fund`**`.

**Third term provably non-binding.** Under C7 and non-negativity, `E ≤ reserve_ledger_balance` holds continuously: JX1 reduces reserve and encumbrance by the same `U`; JB2 is capped by `available_for_return`; creation is capped by the same quantity. Hence `U = min(C, E_effective)`. The `reserve_ledger_balance` term is defence-in-depth and MUST never bind; a checker asserts equality at every ruling and raises severity-1 on inequality.

**`U = 0` occurs iff `C = 0` (dismissal) or `E_effective = 0`.** A JX2/JXS-only compensation therefore requires `E_effective = 0`, satisfied by **either** an absent row **or** a present zero-valued `OPEN` row; the two differ only in whether a settlement transition is performed.

**Dismissal.** Posts no compensation journal and releases the entire open encumbrance atomically with the case-resolution transition, under the same CAS and unique settlement record.

**Shortfall ordering.** If JB2 commits **before** an encumbrance exists, the return stands and is irreversible; the later ruling is capped at the remaining reserve and MUST elect, under maker-checker, either **JX2** (platform funds the shortfall) or **JXS** (desk shortfall receivable + suspension). **Compensation does not always win** — it wins only when the encumbrance exists before the return commits. The user is made whole in both branches; the funding source differs, is chosen explicitly and is audited.

### 7.7 Desk suspension

TB-SUSPEND mutates desk limits only; it **never** affects existing reservations, quotes, links or deals. A MOVE on an already-issued quote succeeds even while the desk is suspended, because the quote is collateralized and its terms are immutable.

## 8. Chain evidence, finality and canonical event identity

### 8.1 Recognition source

**Actual finalized wallet deltas are the source of ledger recognition.** Every derecognition posting is derived from the actual per-wallet `chainF` delta; the wallet named in a derecognition journal is the wallet whose finalized balance is short.

### 8.2 Canonical evidence identity (CEI)

**R-CEI-1 (server-side derivation).** The CEI is computed **server-side from validated finalized-chain data**. No component may be accepted from a caller; caller-supplied values are an unverified hint, compared and then discarded.

| Object | CEI components (canonically encoded, fixed byte encoding) |
|---|---|
| `withdrawal_attempt` | `network`, `finalized_block_id`, `txid`, **canonical transfer-event index read from the finalized receipt**, `receipt_digest` |
| `capital_funding` | `network`, `finalized_block_id`, `txid`, **canonical event index of the funding transfer event**, `receipt_digest` |
| `chain_op` (gas) | `network`, `finalized_block_id`, `txid`, **fixed receipt-level discriminator constant `RECEIPT_LEVEL`**, `receipt_digest` |

> `evidence_key ≔ hash(canonically_encoded(CEI))`

**R-CEI-2 (gas is receipt-level).** `chain_op` MUST use `RECEIPT_LEVEL` and MUST NOT use an event index: TRX consumption is a property of the transaction receipt, not of any individual event. Supplying or deriving an event index for a `chain_op` CEI is rejected **`evidence_discriminator_invalid`**.

### 8.3 Object-bound selection, not verification

**R-CEI-3.** Evidence derivation MUST **start from the locked object's immutable natural key and economic intent** and select the admissible event from the finalized receipt. It MUST NOT search the receipt for an arbitrary event and then merely verify `network` and `txid`.

**Withdrawal attempt — full payout-intent match.** From the **locked attempt**, read the immutable payout intent: `network`, `txid` (from the persisted signed bytes), token contract/asset, **controlled source wallet**, **withdrawal destination address**, **exact payout amount `P`**. Fetch the finalized receipt for that `txid`. An event is **admissible** only if it matches **all** of:

| # | Predicate |
|---|---|
| 1 | `network` and `txid` equal the attempt's |
| 2 | token contract / asset equals the attempt's |
| 3 | event source equals the **controlled source wallet** |
| 4 | event destination equals the **immutable withdrawal destination address** |
| 5 | event amount equals **exactly `P`** |
| 6 | the transaction's execution result is **successful** |
| 7 | the event's index is the **canonical transfer-event index in that receipt** |

**Uniqueness of match.** Exactly one admissible event MUST exist. **Zero matches** → **`evidence_no_matching_event`**. **Two or more matches** → **`evidence_multiple_matching_events`**. Only the uniquely matching event supplies the canonical index.

**Capital funding — index taken from the natural key.** From the **locked object** read `funding_key = (network, asset, txid, event_index)`; fetch the finalized receipt and read **the event at `funding_key.event_index`** — no search. Reject on any of:

| Predicate | Rejection code |
|---|---|
| `network`, `asset`, `txid` match `funding_key` | `evidence_object_mismatch` |
| canonical `event_index` equals `funding_key.event_index` | `evidence_index_mismatch` |
| destination wallet is the **controlled destination wallet of the funding object** | `evidence_account_mismatch` |
| token contract, **direction** (inbound to a controlled wallet) and amount match the finalized event | `evidence_intent_mismatch` |

### 8.4 Validation predicates

Every recognition record MUST prove, and the boundary MUST reject on any failure:

| # | Predicate | Rejection code |
|---|---|---|
| V1 | `CEI.network` and `CEI.txid` equal those of the **locked object** | `evidence_object_mismatch` |
| V2 | The record's `wallet` and `asset` equal the wallet and asset of the **accounts posted by the journal** | `evidence_account_mismatch` |
| V3 | The record's `amount` equals the amount in the finalized receipt/event | `evidence_amount_mismatch` |
| V4 | `finalized_block_id` and `receipt_digest` originate from the **same finalized observation** | `evidence_inconsistent_observation` |
| V5 | The event index is **derived from the receipt**, not supplied (`capital_funding`, payout recognition) | `evidence_index_not_canonical` |
| V6 | `chain_op` uses `RECEIPT_LEVEL` and no event index | `evidence_discriminator_invalid` |

### 8.5 Novelty

**R-CEI-4.** Novelty is evaluated on the **complete server-derived `evidence_key`**, enforced by `UNIQUE(object_key, evidence_key)`. Consequences, all normative:

- **Changing an unrelated field cannot manufacture a new recognition cycle**: unrelated fields are not part of the CEI, and validated fields cannot be altered by a caller.
- **A new `finalized_block_id` carrying an identical `receipt_digest` remains valid** whenever the complete canonical identity is genuinely new. It is **not** required that every individual field differ.
- Differently encoded but semantically identical inputs canonicalize to the **same** `evidence_key` and are rejected as reused, not accepted as novel.
- Rejection codes: reused → **`recognition_evidence_reused`**; missing → **`recognition_evidence_missing`**.

### 8.6 Immutable recognition records

For **every** recognition sequence, an immutable `recognition_record` is written in the same transaction as the recognizing journal, containing:

| Field | Content |
|---|---|
| `finalized_block_id` | Identifier of the finalized block establishing inclusion |
| `receipt_digest` | Digest of the finalized receipt / event set relied upon |
| `evidence_key` | Server-derived CEI hash |
| `wallet`, `asset` | The controlled wallet and asset whose balance changed |
| `amount` | The **exact recognized amount** for this sequence |
| `sequence` | `gas_seq` / `rseq` / `recognition_seq` |

`UNIQUE(object_key, sequence)`; records are append-only and never updated.

**Exact inverse.** `JGX-R`, `JBF1-R`, `JG1-R`, `JW-R1` and `JW-DL-R` reverse **exactly the amount stored in the recognition record of the currently recognized cycle** — never a recomputed or re-observed amount.

**Evidence-bearing re-recognition.** Re-recognition at `k+1` MUST present a **new `evidence_key`** not used by any prior cycle of the same object, and writes a new recognition record before its journal. **A state CAS alone can never advance a sequence**; a transition without an evidence record is rejected `recognition_evidence_missing`. The re-recognized amount at `k+1` is taken from the new evidence and MAY differ from the amount at `k`. **Re-recognition exists only for the two object families named in R-CYC-1.**

### 8.7 Recognition-cycle scope

**R-CYC-1.** The repeatable two-state cycle applies **strictly and only to `chain_op` and `capital_funding`**:

```
<CONFIRMING | FINALIZED> --recognize(seq=0)--> RECOGNIZED
RECOGNIZED               --reverse(seq=k)---->  REVERSED
REVERSED                 --recognize(seq=k+1)-> RECOGNIZED
```

Terminal "reinstated" states do not exist for these objects; re-recognition returns to `RECOGNIZED` with the sequence incremented.

**R-CYC-2 (`sweep` — final and binding).** The **complete and only** sweep lifecycle is

> **`BROADCAST → RECOGNIZED → REVERSED`**

A reversed sweep has **no re-recognition boundary, no re-recognition journal and no re-recognition transition**. `JS1` applies **only** to the initial `CAS(sweep: BROADCAST → RECOGNIZED)`. A finalized reappearance of a reversed sweep **MUST NOT be posted**; it raises a **severity-1 operator incident** and is held for a future amendment that would have to supply a complete contract. Silent inheritance of R-CYC-1 by `sweep` is prohibited, and no boundary in §13.2 lists `JS1` as a reappearance journal.

**R-CYC-2a (state-sensitive duplicate handling).** A repeat observation of an existing sweep is resolved **by natural key first and then by the object's locked state** — the `UNIQUE(network, txid)` constraint MUST NOT decide the outcome and MUST NOT suppress the incident:

| Locked sweep state | Observation | Outcome |
|---|---|---|
| `RECOGNIZED` | consistent with the recorded initial recognition (same finalized inclusion, same `S`, same source and destination wallets) | **Idempotent return `already_recognized`**; nothing posted; `rseq` and state unchanged |
| `RECOGNIZED` | inconsistent with the recorded initial recognition | Severity-1 **`inconsistent_sweep_recognition`**; abort with no writes |
| **`REVERSED`** | **finalized payout reappearance** | **`sweep_reappearance_after_reversal`** — **no `already_recognized` return; no JS1 and no other journal; no `rseq` or state change; raise the severity-1 finalized-reappearance incident of R-CYC-2** |

**R-CYC-3 (`deposit_transfer`).** The specialized `deposit_transfer` machine (§9.1) is **not** governed by R-CYC-1 and is unmodified by it. Its reinstatement journals are JD-RE, JD-REe and JD-REh only.

### 8.8 Split initial-recognition guards

| Object | Initial recognition guard | Journal | Key |
|---|---|---|---|
| **`chain_op`** | `CAS(chain_op: FINALIZED → GAS_RECOGNIZED, version)` with `gas_seq = 0`; recognition record with `evidence_key` written in the same transaction | JGX | `('JGX', network, txid, 0)` |
| **`capital_funding`** | **finalized funding evidence must be present and recorded first**, then `CAS(capital_funding: CONFIRMING → RECOGNIZED, version)` with `rseq = 0` | JBF1 / JG1 | `('JBF1', funding_key, 0)` / `('JG1', funding_key, 0)` |
| **`sweep`** | `CAS(sweep: BROADCAST → RECOGNIZED, version)` with `rseq = 0`; **initial recognition only — no later cycle exists** | JS1 | `('JS1', txid, 0)` |

Reversal (`chain_op`, `capital_funding`, `sweep`): `CAS(RECOGNIZED → REVERSED)` at the current sequence `k`, amount read from `recognition_record(object, k)`.
Re-recognition (`chain_op`, `capital_funding` **only**): `CAS(REVERSED → RECOGNIZED)` setting sequence `k+1`, new evidence required.

## 9. Deposits, sweeps, gas and capital funding

### 9.1 `DepositAddress` and `DepositTransfer`

`DepositAddress` is long-lived (`ACTIVE | RETIRED`) and has **no transfer lifecycle**. `DepositTransfer` carries the lifecycle, keyed by `credit_key`:

```
OBSERVED → CONFIRMING → { CREDITED | HELD | ORPHANED }
HELD | REINSTATED_HELD        → CREDITED                  (JD3)
REINSTATED_CREDIT_HELD        → REINSTATED_CREDITED       (JD3e)
CREDITED                      → REVERSED                  (JD-R1)
HELD | REINSTATED_HELD        → REVERSED                  (JD-R1h)
REINSTATED_CREDIT_HELD        → REVERSED                  (JD-REe-R)
REINSTATED_CREDITED           → REVERSED                  (JD-R2)
REVERSED → REINSTATED_CREDITED        (JD-RE)
REVERSED → REINSTATED_CREDIT_HELD     (JD-REe)
REVERSED → REINSTATED_HELD            (JD-REh)
```

Only `CREDITED`, `HELD`, `REVERSED`, `REINSTATED_CREDITED`, `REINSTATED_CREDIT_HELD` and `REINSTATED_HELD` carry postings. `OBSERVED`, `CONFIRMING` and `ORPHANED` are memo-only (M6).

**R-DR-1 (journal selection by locked state).** The reorg journal is selected from the transfer's **current state read under `X(deposit_transfer)`**, never from a stale or original value:

| Locked state | Journal |
|---|---|
| `CREDITED` | **JD-R1** |
| `HELD` \| `REINSTATED_HELD` | **JD-R1h** |
| `REINSTATED_CREDIT_HELD` | **JD-REe-R** |
| `REINSTATED_CREDITED` | **JD-R2** |

Every alternative journal's guard fails by construction.

**R-DR-2 (per-cycle reinstatement record).** Each reinstatement writes an immutable `reinstatement_record` keyed `(credit_key, rseq)` storing `{a₁, a₂, a₃, target ∈ {BALANCE, HOLD}, hold_case_id, mode_at_reinstatement, lineage_key}`. Subsequent reversal journals read `a₁, a₂, a₃` from that record — never recomputed.

**R-DR-3 (composite hold keying).** The hold-release record and its journal are keyed by **both `case_id` and `deposit_transfer_id`** (and `rseq`): `UNIQUE(hold_release.case_id, deposit_transfer_id, rseq)`. A hold case may therefore hold value from more than one transfer without ambiguity.

**R-DR-4 (party generality).** Any balance-owning party (`user`, `desk`) may be the destination of a deposit recognition, the subject of a reorg receivable, and the subject of an account restriction.

**R-DR-5 (hold discipline).** A transfer recognized into `L.usdt.hold[case]` retains its hold identity across reversal and reinstatement; **JD-REh returns it to the same `case` hold and screening is re-evaluated — reinstatement never routes held value into spendable balance (M18)**. In EMERGENCY mode a cure deposit settles the open receivable first and routes any excess to a hold (JD-C1e), never to spendable balance.

### 9.2 Deposit-reversal derecognition targets

**Case A — deposit vanishes, sweep survives.** Ledger: `deposit[addr] = prior + D − S`, `hot = prior_hot + S`. Finalized chain: `deposit[addr] = prior − S`, `hot = prior_hot + S`. Deltas: `deposit[addr] = −D`, `hot = 0`. **Therefore the deposit derecognition posts against `A.usdt.wallet.deposit[addr]`, not `hot`.** No sweep journal is posted, because the sweep remains in finalized state.

**Case B — deposit and sweep both vanish (`S = D`).** Deltas: `deposit[addr] = 0`, `hot = −S`.
*Lock acquisition order:* all affected chain objects locked at rank 8 in **canonical PK order** — deterministic, deadlock-free, unrelated to accounting.
*Journal application order:* **reverse dependency (topological)** — the dependent sweep first, then the deposit:
1. `JS-R1`: `+A.usdt.wallet.deposit[addr] (S)`; `−A.usdt.wallet.hot (S)` → ledger `deposit[addr] = prior + D`, `hot = prior_hot`.
2. `JD-R1`: `+L.usdt.{party}.balance (B)`; `+A.usdt.receivable.deposit_reversal (Δ₀)`; `−A.usdt.wallet.deposit[addr] (D)` → `deposit[addr] = prior`.
Final ledger equals finalized chain at both wallets. ∎ **Neither sweep is ever re-recognized afterwards (R-CYC-2); a later finalized reappearance of `S` raises the severity-1 incident instead.**

## 10. Withdrawals and recognition cycles

### 10.1 Request and attempt state machines

**Request states.** `QUEUED → AWAITING_INCLUSION → PAID*`
Exits: `CANCELLED*` (from `QUEUED`, JW3) · `RELEASED*` (from `AWAITING_INCLUSION`, JW4) · **`DIVERGED`** (FA-1 violation — frozen, not terminal by policy). (*terminal)
**First signing atomically transitions `QUEUED → AWAITING_INCLUSION`** in TB-WITHDRAW-SIGN, in the same transaction that persists the attempt.

**Attempt states.**

| State | Meaning | Journals | Exits |
|---|---|---|---|
| `PREPARED` | Immutable bytes, txid and bounded expiration committed; not yet acknowledged | none | `BROADCAST`, `EXPIRED_PNI` |
| `BROADCAST` | First node acceptance recorded. **Rebroadcasts update `last_broadcast_at` / `broadcast_count` only and never change state**; a rejected rebroadcast is an operational event | none | `INCLUDED_NONFINAL`, `FINAL_PAID`, `FINAL_FAILED`, `EXPIRED_PNI` |
| `INCLUDED_NONFINAL` | Observed in a non-final block | none | `FINAL_PAID`, `FINAL_FAILED`, `BROADCAST` (dropped), `EXPIRED_PNI` |
| `FINAL_PAID` | Finalized **with** a matching successful transfer | JW2 (+ JGX) | `DIVERGED` (via JW-R1) |
| `FINAL_FAILED` | Finalized **with** failure/revert and **no** matching transfer | **JGX only, never JW2** | `DIVERGED_PAID` (FA-1 violation only, §10.6) |
| `EXPIRED_PNI` | Full PNI predicate proven | none | `DIVERGED_PAID` (FA-1 violation only) |
| `DIVERGED` | Post-finality reversal of a recognized cycle | JW-R1 or JW-DL-R | `DIVERGED_PAID`, or new recognition at `k+1` |
| `DIVERGED_PAID` | A prior TNP or `DIVERGED` attempt observed to have paid | JW-DP or JW-DL | operator resolution only |
| `FROZEN` | Active attempt frozen by a divergence on the same request | none | recognition via the dispatcher only |

**Supersession is an attribute, not a state.** Replacement writes `superseded_by_attempt_id` and `superseded_at` while leaving the prior attempt's state as `EXPIRED_PNI` or `FINAL_FAILED`. After any number of replacements every prior attempt still satisfies the machine-checkable predicate `state ∈ {EXPIRED_PNI, FINAL_FAILED}`, so a further replacement or a JW4 release remains possible indefinitely.

### 10.2 W-rules

- **W1** At most one attempt per request occupies `{PREPARED, BROADCAST, INCLUDED_NONFINAL, FINAL_PAID}`.
- **W2** Signing MUST set and persist an explicit **bounded expiration**; signing without one is prohibited, because PNI would be unprovable.
- **W3** `raw_bytes`, `txid`, `expiration` are written once at `PREPARED` and are immutable; retries rebroadcast byte-identical bytes; no worker re-signs a retry.
- **W4** Bytes/txid/expiration and the broadcast outbox record commit in one transaction; the relay sees the record only post-commit.
- **W5** Payout recognition posts only at finality.
- **W6** A new attempt requires **∀ prior attempts TNP** and **no attempt in `DIVERGED_PAID` or `FROZEN`**.
- **W7** `FINAL_FAILED` posts no JW2 and can never pay.

### 10.3 Terminal Non-Payment and PNI

> **TNP(attempt) ≔ `state ∈ {EXPIRED_PNI, FINAL_FAILED}`** — evaluated from the immutable state, unaffected by supersession.
> **PNI(attempt)** ≔ ∃ finalized block `F`: `F.timestamp > attempt.expiration + margin` **∧** `attempt.txid ∉ finalized_chain(≤F)` **∧** the reference-block validity window has closed.
> **FINAL_FAILED** ≔ `attempt.txid ∈ finalized_chain` with a failed/reverted execution result and no matching transfer event.

Chain-verified absence alone is **insufficient** for PNI. `FINAL_FAILED` is a stronger proof: the txid is already finalized, so it can never be included again, and it demonstrably transferred nothing. Both branches are terminal and both permit replacement or release.

**PNI-1.** A `DIVERGED` attempt may reach `EXPIRED_PNI` **only by proving the complete PNI predicate**, never merely because its expiration passed.

*TRON instantiation:* `expiration` is the signed transaction's expiration field; `F` is the latest solidified block; the reference-block window is the `ref_block` horizon; execution result and transfer events are read from the finalized receipt. Networks without an equivalent expiration primitive MUST NOT be enabled.

### 10.4 Recognition sequence

**Attempt-level state.** Every `withdrawal_attempt` carries `recognition_state ∈ {NONE, RECOGNIZED, REVERSED}` and `current_recognition_seq` (undefined while `NONE`). Any of **JW2 / JW-DP / JW-DL** committed at sequence `k` sets `RECOGNIZED@k`; **JW-R1 or JW-DL-R** committed at `k` sets `REVERSED@k`.

**Candidate selection (the only permitted rule), under `X(withdrawal_attempt)`:**

| Locked `recognition_state` | `candidate_recognition_seq` | Admissibility |
|---|---|---|
| `NONE` | **`0`** | First actual payout recognition |
| `RECOGNIZED@k` | **`k`** | Duplicate observation — resolves idempotently |
| `REVERSED@k` | **`k + 1`** | Genuine reappearance — **requires new canonical finalized-success evidence** |

**R-SEQ-1 (no advance without an intervening reversal).** From `RECOGNIZED@k` the only permitted moves are: remain at `k` (idempotent return) or be reversed to `REVERSED@k` by **JW-R1** (for `JW2`/`JWDP` cycles) or **JW-DL-R** (for `JWDL` cycles). **`FINAL_PAID` and `DIVERGED_PAID` cannot advance to a new sequence without an intervening recognized reversal.** From `REVERSED@k`, an attempt may reach `DIVERGED_PAID` at `k+1`.

**R-SEQ-2 (reversal preserves history).** A reversal posts its own entry and sets `REVERSED@k`. It **does not delete** the recognition journal or the recognition record of cycle `k`; the ledger is append-only and both are retained for audit, together with the immutable TNP and finality history on the attempt.

**R-SEQ-3 (atomic commit set).** For any recognition at the candidate sequence, the following commit **in one transaction**: the new **recognition record** (with its canonical `evidence_key`); the **journal**; the **attempt-state CAS**; and the **recognition-sequence CAS** `CAS(attempt: recognition_state, current_recognition_seq → RECOGNIZED, candidate)`.

### 10.5 Immutable withdrawal recognition record

Every `withdrawal_recognition_record` stores immutably:

| Field | Content |
|---|---|
| `recognition_kind` | **`JW2` \| `JWDP` \| `JWDL`** |
| `P`, `W`, `G` | The amounts **actually posted** by that cycle's journal (`W` and `G` are zero for a `JWDL` cycle) |
| `evidence_key`, `recognition_seq` | Canonical evidence identity and cycle sequence |
| `prior_attempt_state`, `prior_request_state` | States observed under lock immediately before the cycle committed |
| `payable_discharged` | `true` for `JW2` and `JWDP`; `false` for `JWDL` |
| `loss_entry_key` | Present **iff** `recognition_kind = JWDL`; equals `('JWDL', txid, recognition_seq)` |

Constraints: `UNIQUE(withdrawal_recognition_record.attempt_id, recognition_seq)` and `UNIQUE(withdrawal_recognition_record.attempt_id, evidence_key)`.

### 10.6 The finalized-success dispatcher

**TB-WITHDRAW-FINALIZED-SUCCESS** is the single entry point for **any** observation of a finalized successful transfer for a request.

**Locks:** rank 0a `EXCLUSIVE(system_money_state)` **first** (so an SIJ or SDJ branch may be selected with no lock escalation) → 6 `withdrawal_request` → 6 all `withdrawal_attempt` rows ascending → 8 `chain_op` (gas, if unrecognized) → 9 affected ledger accounts ascending.

**Admission:** **always admitted, in every risk mode, and for `DIVERGED` requests and `FROZEN` attempts.** A request-level freeze blocks **replacement and release only**; it MUST NOT prevent chain observers from recognizing that a frozen attempt actually paid. `FROZEN` and `DIVERGED_PAID` are observable-and-recognizable states, not accounting dead ends.

**Order of operations, all under the locks above:**

1. Select `candidate_recognition_seq` from the **locked** attempt lifecycle (§10.4).
2. **Pair inspection** at `(attempt_id, candidate)`:

| Observed pair | Outcome |
|---|---|
| **Neither record nor journal exists** | Proceed to step 3 |
| **Both exist and are consistent** (same `recognition_kind`, `evidence_key`, `P`, `W`, `G`) | **Idempotent return** of the committed cycle |
| **Exactly one exists**, or **multiple recognition journals exist** for that `(txid, seq)`, or **any field disagrees** | **Severity-1 `inconsistent_recognition_cycle`**; abort; no state advances |

  **The dispatcher MUST NOT return merely because a journal exists.**
3. **Derive and validate canonical finalized-success evidence for every candidate, including `candidate = 0`** (§8.2–§8.5). `candidate = 0` MUST NOT bypass validation.
4. **When `candidate > 0`**, additionally assert that the derived `evidence_key` was not used by any previous cycle of the same attempt.
5. Select the branch from the locked payable balance and the attempt-state set, and commit the atomic set of R-SEQ-3.

**Attempt-state sets (exact and exhaustive):**

| Set | Members |
|---|---|
| **`ORDINARY_LIVE`** | `PREPARED`, `BROADCAST`, `INCLUDED_NONFINAL` |
| **`DIVERGENT_SOURCE`** | `FINAL_FAILED`, `EXPIRED_PNI`, `FROZEN`, `DIVERGED` |
| **`ALREADY_RECOGNIZED`** | `FINAL_PAID`, `DIVERGED_PAID` |

**Branch table:**

| Observed condition | Journal | State effects |
|---|---|---|
| `payable = G` ∧ paying attempt ∈ **`ORDINARY_LIVE`** | **JW2** | `CAS(attempt → FINAL_PAID)`; `CAS(request → PAID)` |
| `payable = G` ∧ paying attempt ∈ **`DIVERGENT_SOURCE`** | **JW-DP** | `CAS(attempt → DIVERGED_PAID)`; request → `DIVERGED` (**if already `DIVERGED`, remains `DIVERGED`**); all other `ORDINARY_LIVE` attempts → `FROZEN`; **the severity-1 incident remains open** |
| **`payable = 0`** (request `PAID`, `RELEASED` or `DIVERGED`) | **JW-DL** | `CAS(attempt → DIVERGED_PAID)`; request → `DIVERGED`; severity-1; SD-2 applies; a `divergence_recovery_control` row is created with `P` |

**R-DSP-1.** When `payable = 0`, **every** newly observed actual payout posts exactly one JW-DL for its own `(txid, rseq)`, **regardless of request or attempt state**. No real wallet outflow is ever left unrecognized.
**R-DSP-2.** `L.usdt.withdrawal_payable[req]` holds exactly `G`; M5 forbids a positive liability balance, so at most one of {JW2, JW-DP} commits per request; every additional outflow is recognized by its own JW-DL.
**R-DSP-3.** **JW-R1 MUST NOT be used** for a `FINAL_FAILED` divergence: JW-R1 models a previously paid withdrawal disappearing, the opposite polarity.
**R-DSP-4 (incident record).** Every FA-1 divergence records, in the incident and the audit event: request state at detection, the diverging `txid`, `P`, `W`, `G`, which journal was posted, the resulting second-payout loss (`P`) or absence thereof, and any recoverable party deficit booked.

### 10.7 Retry, replacement and release

| Situation | Action |
|---|---|
| Broadcast error, node failure, worker crash | Rebroadcast identical persisted bytes; no state change; `broadcast_count += 1` |
| Live attempt, unexpired, absent from chain | Wait. **No replacement** |
| `INCLUDED_NONFINAL` | Wait for finality |
| Finalized, transfer succeeded | Dispatcher (§10.6) |
| Finalized, execution failed, no transfer | `CAS(attempt → FINAL_FAILED)` (TB-WITHDRAW-FAIL-PROVE); **JGX posts the TRX actually spent**; request stays `AWAITING_INCLUSION`; TNP satisfied |
| PNI proven | `CAS(attempt → EXPIRED_PNI)` (TB-WITHDRAW-EXPIRE-PROVE); TNP satisfied |
| ∀ attempts TNP, none `DIVERGED_PAID` or `FROZEN` | **Replace** (prior attempts keep their TNP states and gain `superseded_by_attempt_id`; new attempt `PREPARED` with new bytes/txid/expiration + broadcast outbox record, one transaction) **or release** (JW4) |
| FA-1 violation | §10.6 / §12.5 — freeze; **no automatic replacement or release** |

### 10.8 No-double-payment proof

**Under FA-1**, suppose chain transactions `t₁ ≠ t₂` both pay request `req`. Both existed as committed attempts (W4, M19). By W1 they were never simultaneously payable, so one — say `t₁` — satisfied TNP before `t₂` was created (W6). If `t₁` was `EXPIRED_PNI`, it can never be included in any finalized state, so it did not pay. If `t₁` was `FINAL_FAILED`, it is already finalized with no transfer and cannot be re-included, so it did not pay. Contradiction. Independently, `L.usdt.withdrawal_payable[req]` holds exactly `G`; a second discharge would drive that liability positive and be rejected by M5, producing a severity-1 incident rather than a silent double payment. ∎

**If FA-1 is violated,** the financial-truth journal commits under the EXCLUSIVE gate, the attempt and request are frozen, **no automatic replacement or release is authorized**, and a severity-1 incident requires operator investigation with maker-checker resolution. M14 is scoped to FA-1 and is not claimed beyond it.

## 11. Receivable lineage and recovery

### 11.1 Lineage keying and dimensions

A lineage is keyed `(receivable_type, source_object_id, source_seq)` (§5.2). `source_seq` for `deposit_reversal` is `reversal_seq`, starting at 1 and incrementing on **every** reversal of the same transfer. **Each reversal opens a new lineage; lineages are never reopened.**

Every lineage carries **three orthogonal, separately versioned dimensions**:

| Dimension | Values | Driven by |
|---|---|---|
| `receivable_disposition` | `OPEN`, `CURED`, `WRITTEN_OFF` | **Only** cure and write-off events |
| `reinstatement_disposition` | `PENDING`, `SETTLED_REINSTATED`, `NOT_APPLICABLE` | **Only** reinstatement |
| `invalidation_disposition` | `ACTIVE`, `REVERSED_INVALIDATED` | **Only** `JW-DL-R`; therefore only `divergence` lineages can ever leave `ACTIVE` |

**Dimension-1 CAS rules:**

| Event | Rule |
|---|---|
| Opened with `ρ′ > 0` | set `OPEN` |
| Opened with `ρ′ = 0` | set `CURED` if `ω′ = 0`, else `WRITTEN_OFF` |
| Cure of `c` | `ρ −= c`, `κ += c`; if `ρ = 0`: `CAS(OPEN → CURED)` when `ω = 0`, else `CAS(OPEN → WRITTEN_OFF)` |
| Write-off of `K` or `Z` | `ρ −= amount`, `ω += amount`; if `ρ = 0`: `CAS(OPEN → WRITTEN_OFF)` |

**Reinstatement does not rewrite dimension 1.** It sets `ρ := 0`, `ω := 0` and records `σ_r`, `σ_w`, but MUST NOT change `receivable_disposition`; the historical tag is retained for audit.

**Reinstatement admissibility.** JD-RE and JD-REe are permitted when `reinstatement_disposition = PENDING`, **irrespective of `receivable_disposition`** — after an open receivable, after full cure, and after partial or full write-off. The **only** bar is a prior reinstatement of the same lineage.

### 11.2 Journal-derived lineage opening

**`deposit_reversal`** lineages open with components taken from the opening reversal journal's own postings:
- `ρ′ =` the amount **debited to `A.usdt.receivable.deposit_reversal[p]`**;
- `ω′ =` the amount **debited to `R.usdt.reorg_loss_expense[shard]`**;
- `Δ₀′ = ρ′ + ω′`; `κ = σ_r = σ_w = ι_r = ι_c = ι_w = 0`.

| Opening journal | `ρ′` | `ω′` | `Δ₀′` |
|---|---|---|---|
| **JD-R1** | `Δ₀` | `0` | `Δ₀` |
| **JD-REe-R** | `a₁` | `a₂` | `a₁ + a₂` |
| **JD-R2** | `a₁ + a₃ − B′` | `a₂` | `a₁ + a₂ + a₃ − B′` |

**`desk_shortfall`** and **`divergence`** lineages open with `Δ₀ = ρ =` the receivable debit of their opening journal (JXS: `Q`; JW-DR: `K`), and `ω = κ = σ_r = σ_w = ι_* = 0`.

**Restriction reinstatement.** Whenever **JD-REe-R** or **JD-R2** opens a new lineage with `ρ′ > 0`, the party restriction is **(re)applied atomically in the same transaction**. A new `ρ′ > 0` without an active restriction is a severity-1 defect.

### 11.3 Invalidation components

During `JW-DL-R`, for **each** source lineage, in the same transaction:

```
ι_r += ρ        ι_c += κ        ι_w += ω
ρ := 0          κ := 0          ω := 0
CAS(invalidation_disposition: ACTIVE → REVERSED_INVALIDATED, version)
```

One **immutable invalidation record per `(lineage_key, loss_entry_key)`** stores `{ι_r, ι_c, ι_w, invalidated_at, jwdlr_entry_key}` under `UNIQUE(lineage_invalidation.lineage_key, loss_entry_key)`, written in the same transaction.

This preserves: **M22** (invalidated lineages contribute 0, matching the account after `O` is removed); **historical attribution** (`ι_r/ι_c/ι_w` retain the exact open/cured/written-off split); **terminal prohibition** (the guard rejecting further cure, write-off and booking); and **provable aggregates** (`O = Σ ι_r`, `H = Σ ι_c`, `Z = Σ ι_w` over the loss's lineages).

### 11.4 Eligibility and the restriction predicate

**Universal economic predicate.** For **every** receivable type, a lineage is eligible for cure allocation only while `ρ > 0`.

**Type-specific eligibility.**

| `receivable_type` | Eligible allocation set | Ordering | Recovery control |
|---|---|---|---|
| **`divergence`** | `invalidation_disposition = ACTIVE` **AND** `ρ > 0` | oldest-first by `(opened_at, source_object_id, source_seq)` | **8a2 required** for every distinct source in the snapshot |
| **`deposit_reversal`** | `ρ > 0` (invalidation is unreachable for this type) | oldest-first by `(opened_at, credit_key, reversal_seq)` | **none — 8a2 MUST NOT be acquired** |
| **`desk_shortfall`** | `ρ > 0` (invalidation is unreachable for this type) | oldest-first by `(opened_at, ruling_id, 1)` | **none — 8a2 MUST NOT be acquired** |

**`receivable_disposition = OPEN` MUST NOT be used, alone or as a conjunct, as the eligibility predicate for `divergence`.** It is a historical audit label only. (For the other two types it is economically equivalent to `ρ > 0` by Lemma L-E2, but the economic predicate remains normative.)

**Behaviour of a `REVERSED_INVALIDATED` lineage:**

| Property | Rule |
|---|---|
| Historical label | Retains its `receivable_disposition` unchanged |
| M22 contribution | Contributes **zero** `ρ` |
| Generic cure allocation | **Silently ignored** — not in the eligible set, no error |
| Blocking | **MUST NOT block** the cure of a later `ACTIVE` lineage; allocation proceeds to the next eligible lineage |
| Direct targeting | A command that **explicitly names** it is rejected per the guard priority of R-CUR-6 |

**The asymmetry is normative: generic allocation skips; direct targeting rejects.**

**Restriction predicate.** For every party `p` and receivable type `t`:

> `restriction_required(p, t)` ⟺ `Σ ρ over all lineages of (p, t) > 0` ⟺ `balance(A.usdt.receivable.t[p]) > 0`

The two right-hand forms are equivalent by M22; both MUST agree, and disagreement is a severity-1 M22 violation.

- A **historical `OPEN` label with `ρ = 0` MUST NOT retain a restriction.**
- If **another active lineage of the same `(p, t)` still has `ρ > 0`, the restriction MUST remain.**
- The predicate is per `(party, type)`; a party may be restricted for one type and unrestricted for another.

**Atomic recomputation.** **Every boundary that mutates `ρ` for a `(party, type)` MUST recompute `restriction_required(p, t)` and apply or clear the restriction atomically in the same transaction** — cure (JD-C1, JD-C1e, JD-C2b), write-off (JD-C3, JW-DW), lineage opening (JD-R1, JD-R2, JD-REe-R, JXS, JW-DR), reinstatement (JD-RE, JD-REe), and **JW-DL-R for every affected party**. A committed disagreement between predicate and applied restriction is a severity-1 defect.

### 11.5 Cure allocation and the authoritative lock protocol

**Allocation.** A cure of amount `R` is allocated **oldest-first**, taking `min(remaining, ρ_i)` from each eligible lineage in turn until `R` is exhausted or all eligible lineages are closed; any residue follows the ordinary excess routing (party balance under NORMAL/THIN, `L.usdt.hold[case]` under EMERGENCY).

**Allocation completeness (M22).** Every posting to any receivable account MUST carry a complete `receivable_allocation` set naming `(receivable_type, source_object_id, source_seq, amount, entry_key)` summing exactly to the posting. Postings without a complete set are rejected at write.

#### 11.5.1 Generic **divergence** cure — exact protocol

This protocol governs the receivable leg of **JD-C1, JD-C1e and JD-C2b** whenever the cured receivable type is `divergence`.

1. **Rank 8** — lock the cure's chain object (the curing `deposit_transfer`), when applicable.
2. **Rank 8a1** — acquire `X(party_receivable_control[p, 'divergence'])`.
3. **Select the authoritative snapshot**: exactly the lineages satisfying `invalidation_disposition = ACTIVE ∧ ρ > 0` **at this serialization point**, oldest-first.
4. **Derive** every distinct source `loss_entry_key` **appearing in that authoritative snapshot**.
5. **Rank 8a2** — acquire **every** corresponding `divergence_recovery_control` row, **ascending by `loss_entry_key`**.
6. **Re-read and validate** the selected allocation under those locks.
7. **Require every selected source control to be `OPEN`.** A **`REVERSED`** control for a snapshot lineage is **not a race outcome**: it raises **severity-1 `inconsistent_recovery_snapshot`** and the boundary aborts with no writes (R-CUR-4).
8. **Rank 8b** — acquire every selected lineage, ascending.
9. **Rank 9** — acquire ledger accounts ascending, then commit.

**R-CUR-1 (no rank inversion).** **No 8a2 row may be acquired after an 8b lineage**, and no rank-7 allocation lock is taken by any cure boundary.

**R-CUR-2 (stable eligible set — no restart needed).** Holding `X(party_receivable_control[p,'divergence'])` from step 2 prevents insertion or mutation of that party's divergence lineages by any concurrent boundary (creation, cure, write-off, reinstatement, reallocation and `JW-DL-R` all take 8a1 for their affected parties). Therefore the step-6 re-read **must** produce the same eligible set as step 3. **Any mismatch is a severity-1 `allocation_snapshot_conflict`** — it indicates a boundary bypassing 8a1, not a legitimate race.

**R-CUR-3 (consequences of a prior reversal).** If `JW-DL-R` committed **before** the cure obtained 8a1, its invalidated lineages have `invalidation_disposition = REVERSED_INVALIDATED` and `ρ = 0`, so they are **absent from the cure snapshot**. The cure **MUST NOT** lock their reversed recovery controls merely to recreate a stale pre-reversal allocation; it cures the remaining `ACTIVE` lineages oldest-first and routes unapplied value through the residue rules. **`loss_reversed` is unreachable for a generic cure by construction**, and the absence of a formerly eligible lineage is a normal outcome, not an error.

**R-CUR-4 (snapshot-vs-control consistency).** As step 7: an `ACTIVE` snapshot lineage whose source control is `REVERSED` proves an atomicity or lock-protocol violation, because `JW-DL-R` invalidates every source lineage atomically while holding 8a1 for each affected party.

**R-CUR-5 (chain-delta preservation).** For a curing deposit of `R` with allocations `a_i`:
```
+A.usdt.wallet.deposit[addr]              (R)
−A.usdt.receivable.{t}[p]                 (Σ a_i)
−L.usdt.{party}.balance[p] | hold[case]   (R − Σ a_i)
```
Per-asset balance `R − Σ a_i − (R − Σ a_i) = 0`. The wallet asset increases by **exactly `R`** regardless of how many lineages survived into the snapshot; only the split varies. **No actual wallet delta is ever dropped.**

#### 11.5.2 Non-divergence cure — exact protocol

For `deposit_reversal` and `desk_shortfall` receivables:

1. **Rank 8** — lock the curing chain object, when applicable.
2. **Rank 8a1** — acquire `X(party_receivable_control[p, t])`.
3. Select the eligible set `ρ > 0`, oldest-first, under that lock.
4. **Rank 8b** — acquire the selected lineages, ascending.
5. **Rank 9** — acquire ledger accounts ascending, then commit.

**No `divergence_recovery_control` row is derived, required or locked for these types (R-CUR-1, §5.2).** Steps 4–5 of §11.5.1 have no counterpart here, and `loss_reversed` / `inconsistent_recovery_snapshot` are unreachable.

#### 11.5.3 Guard priority for directly targeted commands

**R-CUR-6.** A **directly targeted** command — one that explicitly names a lineage or a loss (`JW-DW`, a targeted cure, a `JW-DR` booking) and is a **genuinely fresh command** (no committed result for its command identity) — rejects using this **stated deterministic priority**:

| Order | Condition | Rejection |
|---|---|---|
| **1** | the source `divergence_recovery_control[loss_entry_key].state = REVERSED` | **`loss_reversed`** |
| **2** | otherwise, `lineage.invalidation_disposition = REVERSED_INVALIDATED` | **`lineage_invalidated`** |

Guard 1 is evaluated first because loss reversal is the root cause of lineage invalidation. Guard 2 is reachable **only in the anomalous state** where the lineage is invalidated while its source control is still `OPEN`; that state is additionally reported to the standing checker.

**A generic cure evaluates neither guard** — it skips invalidated lineages (R-CUR-3).

**A same-command `JW-DW` retry evaluates neither guard** — the result-first inspection of §11.9 returns the committed result idempotently, even after `JW-DL-R` (§11.9, R-CUR-8).

**R-CUR-7 (equivalent serialization).** Cure, JW-DW and JW-DR use the ordering `[8 →] 8a1 → [8a2 for divergence] → 8b → 9`, so booking, cure, write-off and reversal all serialize on the same control rows in the same direction; no pair can deadlock.

**R-CUR-8 (retry precedence).** For any command whose identity admits an immutable committed result set (JW-DR by `recovery_booking_id`, JW-DW by `writeoff_command_id`), **the committed-result inspection strictly precedes every economic and terminal guard**. Only a genuinely fresh command reaches R-CUR-6.

### 11.6 Reinstatement application and the no-over-credit proof

For a reappearing deposit of `D`:
1. `a₁ = min(D, ρ)` — close the still-open receivable;
2. `a₂ = min(D − a₁, ω)` — recover the attributable prior write-off (credited to `R.usdt.reorg_loss_expense`);
3. `a₃ = D − a₁ − a₂` — credit only the remainder to the party (or to hold under JD-REe).

**Theorem (M20).** Because `ρ ≤ Δ₀ ≤ D` and `ω ≤ Δ₀ − ρ − κ ≤ D − ρ`, the clamps never bind: `a₁ = ρ` and `a₂ = ω` in every reachable state, so reinstatement always drives `ρ → 0` and `ω → 0`. When `D ≥ ρ + ω`:
`a₃ = D − ρ − ω = (B + Δ₀) − ρ − ω = B + (Δ₀ − ρ − ω) = B + κ`.
The party is credited exactly the balance clawed from it plus the amount it cured out of pocket — never more. ∎ A checker asserts `a₁ = ρ ∧ a₂ = ω` at every reinstatement; violation is severity-1.

**Worked case (regression).** `D = 100`, `B = 20`, `Δ₀ = 80`, `ρ = 0`, `κ = 0`, `ω = 80`, `receivable_disposition = WRITTEN_OFF`, `reinstatement_disposition = PENDING`. Admissible by §11.1. `a₁ = 0`, `a₂ = 80`, `a₃ = 20`. Postings (zero receivable leg omitted): `+A.usdt.wallet.<delta-wallet> (100)`; `−R.usdt.reorg_loss_expense[shard] (80)`; `−L.usdt.{party}.balance[p] (20)`; balance `100 − 80 − 20 = 0`. **Platform recovers 80; party restored exactly 20.** Identity before `0+0+80+0+0+0+0+0 = 80`; after `0+0+0+0+80+0+0+0 = 80` ✓.

### 11.7 Divergence recovery control and booking

`divergence_recovery_control[loss_entry_key]` holds `{loss_amount P, Σ booked, next_booking_seq, state ∈ {OPEN, REVERSED}, version}`, created in the same transaction as its JW-DL.

**Cap.** Under `X(divergence_recovery_control[loss_entry_key])`: `Σ booked K ≤ P`, each booking requiring `0 < K ≤ P − Σ booked`; exceeding the cap → **`recovery_exhausted`**. **Two different rulings referencing the same loss can never create receivables whose total exceeds `P`.**

**Booking identity.** `recovery_booking_id ≔ (loss_entry_key, approval_provenance)` with `UNIQUE(divergence_recovery_booking.loss_entry_key, approval_provenance)`; the journal key is derived from the same identity: `entry_key = ('JWDR', loss_entry_key, approval_provenance)`.

**Booking algorithm** (one transaction, under the control lock, R-CUR-8 order):
1. Look up the booking by `recovery_booking_id`.
2. **If it exists:** return its committed `booking_seq`, lineage and journal result **idempotently**; `sum_booked` and `next_booking_seq` are **not** modified; no journal is posted; no terminal guard is evaluated.
3. **If not:** apply R-CUR-6 (fresh-command guards), then require `0 < K ≤ P − sum_booked`; set `booking_seq := next_booking_seq`; insert the booking; `sum_booked += K`; `next_booking_seq += 1`; post JW-DR; open the `divergence` lineage with `source_seq = booking_seq`; write the complete `receivable_allocation` set; apply the party restriction.

**Consistency assertion (in-transaction and standing):** `control.sum_booked = Σ (amount of committed bookings for that loss_entry_key)`. Inequality is rejected at write and is severity-1 if observed.

### 11.8 Type-dispatched write-off

Write-off is **type-dispatched by `receivable_type`**; a write-off journal is admissible only where its expense account is economically correct.

| `receivable_type` | Journal | Expense account |
|---|---|---|
| `deposit_reversal` | **JD-C3** | `R.usdt.reorg_loss_expense[shard]` |
| `divergence` | **JW-DW** | `R.usdt.divergence_loss_expense[shard]` |
| `desk_shortfall` | **undefined and prohibited** | — |

Applying JD-C3 to a `divergence` receivable is rejected **`writeoff_type_mismatch`**. A `desk_shortfall` write-off is rejected **`writeoff_undefined_for_type`** and held for a future amendment supplying its own type-correct journal, guards and tests. Silent reuse of either existing journal is prohibited.

### 11.9 `JW-DW` command identity and result-first retry

**Identity.** `writeoff_command_id` is a **server-derived immutable identity of the approved write-off command**. Where one ruling may contain several approved write-off lines, **each line carries its own immutable `approval_line_id`** and

> `writeoff_command_id ≔ hash(approval_provenance, approval_line_id)`

**The caller MUST NOT supply or alter** the approved `lineage_key`, `loss_entry_key`, `party`, `Z`, or the approval line identity. All are loaded from the authoritative approved command stored at approval time; caller-presented values are an assertion to be compared, never input.

**Boundary sequence.** `TB-APPROVE (branch C)`: **rank 0a** `EXCLUSIVE(system_money_state)` → **rank 0b** `M(writeoff_command_id)` → **load the authoritative approved command** → **derive its canonical target locks from that command** (rank 2 `case`, 8a1 party control, 8a2 recovery control, 8b lineage, 9 accounts) → **result-first inspection**, before any economic or terminal guard. The command mutex sits at rank 0b precisely because the target locks are unknowable until the authoritative command loads; acquiring it first preserves a total order.

**Constraints.** `UNIQUE(divergence_writeoff.writeoff_command_id)`; journal `entry_key = ('JWDW', writeoff_command_id)`; every allocation and the fingerprint reference the same `writeoff_command_id`. The narrower constraint `UNIQUE(divergence_writeoff.lineage_key, approval_provenance, approval_line_id)` is retained as **defence in depth only** and MUST NOT replace the command-id constraint.

**The committed result is one consistent set:** the `divergence_writeoff` record; the JW-DW journal; a complete `receivable_allocation` set; and an immutable approved-command fingerprint containing at least `lineage_key`, `loss_entry_key`, `party`, `Z`, `approval_provenance`, `approval_line_id`.

| Observed | Outcome |
|---|---|
| **All components exist and match the approved command** | **Return the original result idempotently — even if `ρ` is now zero, the lineage is `REVERSED_INVALIDATED`, or the loss control is `REVERSED`.** No guard is evaluated; no state is touched |
| **No committed components** and the request matches the authoritative approved command | Apply R-CUR-6 (`loss_reversed` first, then `lineage_invalidated`), then `0 < Z ≤ ρ`; then commit **all components atomically** with the postings, complete allocations, `ρ −= Z`, `ω += Z` and restriction recomputation |
| **Same command identity with altered fields** | **Reject `approval_command_mismatch`** — without posting |
| **Only part exists, or any stored field disagrees** | **Severity-1 `inconsistent_divergence_writeoff`**; abort; no state advances |
| **A genuinely new approved command identity** | Evaluate as a fresh command |

**Retry guarantees.** A same-command retry returns successfully after a full-`ρ` write-off, after a later `JW-DL-R` invalidation, and after response loss or process restart, never posting twice and never modifying `ρ`, `ω` or any `ι` component twice. A full-`ρ` JW-DW moves `Z` from `ρ` into `ω`; a subsequent `JW-DL-R` moves that `ω` into `ι_w` and zeroes `ω`; an idempotent retry touches none of these, so `ι_w` continues to record exactly the written-off amount at invalidation and M23 is preserved.

### 11.10 Attributable-expense proof for a divergence loss

| Step | Journal | Effect on attributable expense | Running total |
|---|---|---|---|
| Loss recognized | **JW-DL** posts `+expense (P)` | `+P` | `P` |
| Recovery booked, total `Σ K` | **JW-DR** posts `−expense (K_i)` per booking | `−Σ K` | `P − Σ K` |
| Cures, total `H` | cure posts `+A.wallet(...)`, `−A.receivable.divergence(κ_i)` — **no expense leg** | `0` | `P − Σ K` |
| Write-offs, total `Z` | **JW-DW** posts `+expense (Z_i)` | `+Z` | `P − Σ K + Z` |

With `O + H + Z = Σ K`: `P − Σ K + Z = P − (O + H + Z) + Z = **P − O − H**` ∎

Therefore the `JW-DL-R` Case B leg `−R.usdt.divergence_loss_expense[shard] (P − O − H)` drives the attributable expense to exactly zero, with no residual.

### 11.11 `JW-DL-R` multi-party discovery (restartable)

Canonical order **8a1 → 8a2 → 8b → 9 is retained absolutely.** `JW-DL-R` cannot know its affected party set before reading the bookings that the 8a2 row protects, so it uses a **restartable protocol with no writes before the snapshot is authoritative**:

1. **Pre-read (no locks):** the distinct parties booked against `loss_entry_key`.
2. **Acquire** those `party_receivable_control[party,'divergence']` rows at **8a1**, ascending.
3. **Acquire** `divergence_recovery_control[loss_entry_key]` at **8a2**.
4. **Re-read the authoritative committed bookings and source lineages** under that lock.
5. **If a newly affected party is not in the locked set:** **abort with no writes**, release all locks, and **restart** with the expanded party set.
6. **Otherwise:** acquire all source lineages at **8b** ascending, then all ledger accounts at **9** ascending, and commit atomically.

**Booking outcomes relative to the serialization point.** A JW-DR booking that commits **before** the reversal acquires 8a2 is either included in the authoritative re-read, or triggers a safe restart after which it is included — either way it precedes the final snapshot. A booking that **loses** the control-row race observes `state = REVERSED` and fails **`loss_reversed`** (R-CUR-6 guard 1).

**Termination.** Bookings require 8a2; once the reversal holds 8a2 no further booking can commit. Across restarts the locked party set is **monotonically expanding** and the party count is bounded by the cap (`Σ K ≤ P`, every `K > 0`), so restarts are finite. A configured restart ceiling escalates to operator review rather than looping.

**A cure cannot make a previously unknown party appear in a source loss** — cures do not create lineages; only JW-DR booking does.

### 11.12 Post-reversal prohibitions

Once `divergence_recovery_control[loss_entry_key].state = REVERSED`, and applying the guard priority of **R-CUR-6** and the retry precedence of **R-CUR-8**:

| Command | Outcome |
|---|---|
| **Fresh JW-DR booking** against the loss | **`loss_reversed`** (guard 1) |
| **Fresh targeted cure** naming an invalidated lineage of that loss | **`loss_reversed`** (guard 1; the control is REVERSED) |
| **Fresh JW-DW** naming an invalidated lineage of that loss | **`loss_reversed`** (guard 1) |
| **Fresh targeted command** naming an invalidated lineage whose control is still `OPEN` (anomalous) | **`lineage_invalidated`** (guard 2) + standing-checker report |
| **Generic divergence cure** | **Skips** the invalidated lineages; raises neither code; cures remaining `ACTIVE` exposure and routes residue (R-CUR-3) |
| **Same-command JW-DR or JW-DW retry** with a committed consistent result set | **Idempotent return**; no guard evaluated (R-CUR-8) |

The reversed control row is **never reopened**.

**Later reappearance.** A subsequent finalized reappearance of the payout is recognized as a **new JW-DL at recognition sequence `k+1`**, producing a **new `loss_entry_key = ('JWDL', txid, k+1)`** and a **new** `divergence_recovery_control` row. It MUST NOT reopen or reuse the reversed control row or its invalidated lineages.

## 12. Reorg, reversal and reinstatement

### 12.1 Derecognition target rule

Every derecognition posting is derived from the **actual per-wallet `chainF` delta**; the wallet named is the one whose finalized balance is short (§9.2).

### 12.2 Lock order vs application order

**Lock acquisition order** is canonical (rank, then PK) and exists for deadlock freedom. **Journal application order** is **reverse dependency (topological)** — dependents first — and exists for accounting correctness. The two are distinct and MUST NOT be substituted for one another (L5); both are asserted separately in the acceptance suite.

### 12.3 Reinstatement scope and idempotence

**Reinstatement exists only for the object families that define it.**

| Object | Reinstatement journals | Sequence effect |
|---|---|---|
| `deposit_transfer` | **JD-RE**, **JD-REe**, **JD-REh** | `CAS(REVERSED → REINSTATED_*)`, `rseq += 1` |
| `capital_funding` | **JBF1-RE**, **JG1-RE** | `CAS(REVERSED → RECOGNIZED)`, `rseq += 1` |
| `chain_op` | **JGX** at `gas_seq + 1` | `CAS(GAS_REVERSED → GAS_RECOGNIZED)`, `gas_seq += 1` |
| **`sweep`** | **none — re-recognition is prohibited (R-CYC-2)** | no transition exists out of `REVERSED` |

Each listed reinstatement journal posts **exactly once** at its new sequence, guarded by that sequence's `entry_key` and the object's CAS. **`JS1` is not a reinstatement journal**: it applies only to the initial `CAS(sweep: BROADCAST → RECOGNIZED)`. A finalized reappearance of a reversed sweep is **not posted** and raises the severity-1 operator incident required by R-CYC-2.

### 12.4 Post-credit deposit reorg and cure

`JD-R1` opens a lineage and, where `B < D`, a receivable; the account is **restricted** while any `ρ > 0` remains for that `(party, type)`. Cure paths: **JD-C1** (direct, capped, excess to balance), **JD-C1e** (EMERGENCY, excess to hold), **JD-C2a + JD-C2b** (via balance, **prohibited in EMERGENCY**), and write-off **JD-C3**. Every crediting posting to a receivable is capped at the open balance under that account's rank-9 lock, so no receivable can become negative (M5), and every such posting carries its complete allocation set (M22).

### 12.5 FA-1 violation handling

An FA-1 violation is an **external-assumption failure**, not a modelled transition. On detection the system: (a) posts the financial-truth journal under the EXCLUSIVE risk gate; (b) sets the affected attempt and request to their frozen states; (c) **authorizes no automatic replacement and no automatic release**; and (d) raises a severity-1 incident requiring operator investigation and maker-checker resolution.

### 12.6 `JW-DL-R` — exact inverse of a `JWDL` cycle

**Boundary:** `TB-DIVERGENCE-LOSS-REVERSE` (reorg-class; always M-lock). **Trigger:** the finalized chain no longer contains the payout whose observation produced the JW-DL loss. **JW-R1 MUST NOT be applied to a `JWDL` cycle** — attempting it is rejected **`reversal_kind_mismatch`**.

**Aggregates** over the `divergence` lineages sourced from this `loss_entry_key`, computed under the locks of §11.11:
`O = Σ open ρ` · `H = Σ cured κ` · `Z = Σ written-off ω` · with `O + H + Z = Σ booked K ≤ P`.

**Case A — no recovery booking exists** (the degenerate instance `O = H = Z = 0`):
```
+A.usdt.wallet.hot                        (P)
−R.usdt.divergence_loss_expense[shard]    (P)
```
`withdrawal_payable` and `withdrawal_fee_revenue` are **never** posted by this journal.

**Case B — recovery bookings exist:**
```
+A.usdt.wallet.hot                        (P)
−A.usdt.receivable.divergence[*]          (O)      one leg per affected party, summing to O
−L.usdt.{party}.balance-or-hold[*]        (H)      one leg per affected party, summing to H
−R.usdt.divergence_loss_expense[shard]    (P − O − H)
```
Per-asset balance `P − O − H − (P − O − H) = 0`. The attributable-expense assertion of §11.10 is evaluated in-boundary. **The `O` leg is a receivable posting and therefore carries a complete `receivable_allocation` set** naming, for each affected lineage, `('divergence', loss_entry_key, booking_seq, ι_r contribution, entry_key)`.

**Effect.** Open receivables are removed (parties owe nothing), cured recovery value is returned to the parties who paid it, and the remaining net loss is reversed — leaving no residual receivable, no residual party obligation and no residual expense attributable to a payout that never finally occurred.

**`H` routing.** Each per-party `H` leg credits `L.usdt.{party}.balance[p]` when the mode admits spendable credit, and `L.usdt.hold[case]` whenever the mode prohibits it (EMERGENCY, M18). The mode is read under the rank-0a M-lock held by this boundary, so routing cannot race a mode change.

## 14. Outbox and exactly-once effects

| # | Rule |
|---|---|
| **O1** | The domain mutation, its journal entries, its audit event(s) and its outbox record(s) commit in **one database transaction**. An external effect not represented by a committed outbox record MUST NOT occur |
| **O2** | Every outbox record carries a deterministic `event_key` under `UNIQUE(outbox.event_key)`; retried boundaries produce the same key and therefore one record |
| **O3** | Delivery is at-least-once; every consumer is idempotent by `event_key`. Duplicate delivery MUST be harmless by construction: broadcasts replay persisted bytes, notifications dedupe by key, anchor writes are content-addressed |
| **O4** | No boundary blocks on delivery. Relay outage, backlog or duplication **never** changes ledger or domain state: it cannot make an expired object consumable (T4), a pending proposal approvable, an admission valid after a mode change, or a payment happen twice. The outbox carries **no value semantics** — no journal is implied or scheduled by an outbox record; chain confirmations re-enter as new boundaries |
| **O5** | For withdrawals, the persisted immutable `raw_bytes` are **the only bytes ever broadcast** — for the original attempt and every replacement — and a broadcast record becomes relay-visible only after its attempt row is committed |

## B.6 Uniqueness constraints → deterministic collision outcome

The complete table is §5.3. Outcome classes:

- **Consistent idempotent return** — `journal_entry.entry_key`; deposit `credit_key`; `chain_op(network,txid)`; `capital_funding` funding key; `chain_object_id + recognition_seq`; `allocation_release`; `encumbrance_settlement` (same `ruling_id`); `hold_release`; `recovery_booking_id`; `writeoff_command_id` (consistent set); `lineage_invalidation`; `receivable_allocation`; `outbox.event_key`.
- **State-sensitive (`sweep(network,txid)`)** — the constraint never decides the outcome alone. The existing object is resolved and locked first, then branched on state (R-CYC-2a): `RECOGNIZED` + consistent observation → **idempotent return `already_recognized`**; `RECOGNIZED` + inconsistent observation → severity-1 `inconsistent_sweep_recognition`; **`REVERSED` → `sweep_reappearance_after_reversal`: no idempotent return, no journal, no `rseq` or state change, severity-1 finalized-reappearance incident.**
- **Optimistic-concurrency rejection** — `deals.quote_id`; `deals.link_id`; `utr`; the payable-state attempt index; `withdrawal_attempt.txid`; `approval.proposal_id` with `approver ≠ proposer`; `proposal.case_id WHERE PENDING`; `evidence.case_id + content_digest`.
- **Stale or reused evidence rejection** — `(object_key, evidence_key)`; `(attempt_id, evidence_key)` across sequences → `recognition_evidence_reused`.
- **Approval command mismatch** — `writeoff_command_id` presented with altered fields → `approval_command_mismatch`.
- **Severity-1 partial-component inconsistency** — `(attempt_id, recognition_seq)` with an inconsistent pair → `inconsistent_recognition_cycle`; `writeoff_command_id` with a partial set → `inconsistent_divergence_writeoff`.
- **Encumbrance settlement by a different ruling** — `encumbrance_already_settled`.
